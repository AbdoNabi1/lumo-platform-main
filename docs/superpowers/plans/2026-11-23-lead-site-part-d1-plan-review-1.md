# Lead Site Plan D1 — review round 1

Review completed against `57049744`. Scope: plan contracts, real-code feasibility, vendor payload shapes, security, wiring, and runnable verification commands. Binding owner decisions are accepted unchanged.

## Findings

1. **BLOCKING — Task 4, registry stub mapping (lines 668–670).** The proposed `{ key, destination, fields: [] }` is not a `MappingProfile`: `packages/tracking/src/delivery/mapping.ts:79–85` requires `version: number`. `delivery-runtime.ts:287,310,379` also resolves a mapping version even on the builder path. **Fix:** append a complete, explicitly versioned stub (`version: 1` initially), keep the registry row version consistent, and test the sync-produced rows through the real `TrackingRegistrySnapshot` and recording runtime, not only an append-count fake.

2. **BLOCKING — Tasks 1/4, internal connection port mismatch (plan lines 252–257, 627–628, 657).** Task 1 produces `getLiveConnections.execute({ tenantId }): Promise<Result<readonly LiveConnection[], DomainError>>`, while Task 4 requires `connections.getLiveConnections(tenantId): Promise<readonly LiveConnection[]>`. Passing `.internal` directly cannot satisfy that contract; `openSecret` is also a use-case object rather than a named resolver function. **Fix:** specify the exact adapter that calls `.execute`, unwraps `Result`, and maps failures (only NOT_FOUND → null for secret resolution), or make the consumer port use the produced signatures. Add real wiring tests with the Task 1 service.

3. **BLOCKING — Task 3, builder render return contract (plan lines 504–506, 551–553).** The plan says `renderPayload` returns `buildVendorPayload(...)`, but builder failure is `{ ok: false, reason }`; the existing `RenderOutcome` requires `{ ok: false, failure: { gate, detail } }` (`delivery-pipeline.ts:214–217`), and `receiveAndDeliver` dereferences `rendered.failure.detail` (`delivery-runtime.ts:280–295`). **Fix:** translate every builder refusal into a mapping/formatting `EnforcementFailure`, explicitly handle missing extras and missing target, and test unsupported events/GA4 missing client id via `receiveAndDeliver` as recorded blocked outcomes without a vendor call.

4. **BLOCKING — Task 3, click-id input extraction (plan lines 492–493).** `CapturedClickId` has `name`, `value`, `capturedAt`, and optional attribution fields, not `param` or `platform` (`packages/tracking/src/envelope/click-ids.ts:108–115`). The registry's Snap platform is `"snapchat"`, not `"snap"` (`:25–26,69–73`). Following the stated extraction drops both click ids (or fails typecheck). **Fix:** use `captured.name === "ttclid"` and the preserved canonical key `"scclid"` for Snap, changing only that definition's URL `param` to `"ScCid"`; alternatively resolve the owning definition and compare `platform === "snapchat"`. Pin extraction from real `extractClickIds` output in `vendor-event-input.test.ts`.

5. **BLOCKING — Task 4, sync lifecycle comparison (plan lines 665–671).** Comparing desired values to the "latest active row" ignores a later retired version. After `active v1 → retired v2`, re-enabling the unchanged connection compares equal to v1 and never restores an active current version; repeated disable can also append retirement repeatedly. The real snapshot resolves only the latest current entry and returns null when retired (`tracking-registry.ts:165–180,220–223`). **Fix:** group all rows by kind/key, compare desired value AND desired lifecycle against the highest version of any status, and allocate `max(all versions)+1`. Test disable twice (second no-op), re-enable unchanged (active v3), and load all histories with the real snapshot. A read-only probe confirmed retired resolves null and a newly appended active v3 restores resolution.

6. **BLOCKING — Tasks 2/4/5, missing production wiring call site.** The plan says runtime composition hands the new vault/sync to admin, but does not include `apps/runtime/src/api.ts`, the actual `createAdminHttpApi` caller. Existing payment vault propagation is explicit at `api.ts:584–587`; building fields only in `composition.ts` and accepting them in `apps/admin/src/http/server.ts` does not pass them across that boundary. With omitted deps, Task 1 falls back to the stub vault/no-op sync. **Fix:** name the `RuntimeCore` fields, populate them, explicitly pass both into `createAdminHttpApi` in `api.ts`, and add a wiring test proving the saved connection reaches the real vault and sync. Preserve the proposed independent internal service instance (no runtime/admin import cycle).

7. **BLOCKING — Task 5, role tests (plan lines 729–730).** A viewer does NOT have `settings:read`: neither `SHOP_RESOURCES` nor `READ_ONLY_RESOURCES` contains `settings`, and viewer/operator receive only those resource grants plus `account:update_self` (`packages/auth/src/role-table-access-control.ts:4–53`). A real authorization probe returned false for viewer/operator on both settings permissions. The named server harness defaults to `AllowAllAccessControl` unless access control is injected (`apps/admin/src/http/server.ts:136–138`), so copying it alone can falsely pass. **Fix:** state exact expectations: admin GET/PUT allowed; viewer and operator GET/PUT 403. Inject the real `RoleTableAccessControl` and real staff tokens; remove the self-questioning "assert whatever" clause. No permission expansion is required.

8. **BLOCKING — Task 4, transactional registry store API and concurrent saves (plan lines 654–671).** `PrismaTrackingRegistryStore` has only `loadAll/count/signal/append`; it closes over the root `Database` and writes directly through it (`tracking-registry.ts:75–101,129–151`). It offers no transaction callback or transaction-bound writer. `runInTenantTransaction` gives a `TransactionClient`, not the root `Database` required by that constructor (`packages/db/src/client.ts:5`; `transaction.ts:41–50`). Merely wrapping calls to the already-created store in an outer transaction will NOT move those calls onto its connection. Also, two platform saves can read the same rule-set version and race on the append unique key; the losing sync is swallowed as success by Task 1 and stays stale until another save/backfill. **Fix:** explicitly include `tracking-registry.ts` and its tests in Task 4; define a tenant-transaction API that supplies a transaction-bound narrow registry store, scopes every query, and serializes sync per tenant in Postgres (or retries conflicts after a fresh read). Read the desired connection set after acquiring that serialization. Test rollback of a middle append and simultaneous Meta/TikTok saves producing a complete, loadable registry with contiguous versions. Do not cast a root client into a transaction client or rely on a process-local lock.

9. **BLOCKING — Task 3, secret-bearing failure paths remain recordable (plan lines 108–111,543–546,592–595).** Adding query auth after record creation does not protect failures: `HttpJsonAdapter` returns `error.message` verbatim (`delivery/adapters.ts:140–146`), and `FetchHttpTransport` returns raw response text plus parsed response data (`apps/runtime/src/tracking/tracking-adapters.ts:136–153`). `delivery-pipeline.ts:419,453–464` writes the error into DLQ; `inspector/record-delivery.ts:142–147` writes it into history. A read-only adapter probe with a transport exception containing `?access_token=xxxx-xxxx-0000` returned that secret unchanged. Moreover there is no endpoint URL field in `DestinationHistoryEntry` (`inspector/event-record.ts:106–134`), so the proposed assertion against a "recorded endpoint URL" invents a field. **Fix:** specify safe transport diagnostics/redaction for the resolved credential, encoded credential, authenticated URL, returned error text and vendor diagnostics; never mutate `request.endpoint`. Add failure/echo tests checking the whole EventRecord/history/DLQ/log capture, plus the unchanged registry destination URL and clean recorded business payload. Keep a capture of `records.append` before fake HTTP send to prove record-before-send; do not add an endpoint field just to satisfy the test.

10. **BLOCKING — Task 2, KEK validation weakens the copied payments pattern (plan line 341).** The requested `.min(1)` accepts a one-character encryption secret. The existing payments setting is `.min(32)` and explains that with the actual NodeCrypto backend the reference IS key material (`apps/runtime/src/config.ts:232–238`); `NodeCrypto.key` derives the key directly from that string (`services/security/src/infrastructure/in-memory-auth-adapters.ts:28–30`). **Fix:** require at least the same 32-character minimum for `AD_PLATFORM_CREDENTIALS_KEK_REF`, document its secret/key-material semantics, and test missing vs too-short vs valid values. Keep envelope encryption and the chosen alias unchanged.

11. **BLOCKING — Task 1, undefined unavailable error and unsafe stub-vault guard (plan lines 280–287).** `UnavailableError` is not defined/exported anywhere on this branch. The named leads presenter maps unrecognized error codes to 422 (`services/leads/src/interfaces/presenter.ts:9–27`), so a newly improvised unavailable error would otherwise be misreported as a validation failure. The guard also depends only on `NODE_ENV === "production"`, whereas the actual deployment environment is `RuntimeConfig.APP_ENV` (`apps/runtime/src/config.ts:11`); `APP_ENV=production` with unset NODE_ENV bypasses it and can persist base64-encoded plaintext using the stub. **Fix:** name and create a service-local `DomainError` subclass with an explicit stable code/retryability and map it explicitly to HTTP 503. Make persistent credential writes require a real vault independently of ambient NODE_ENV (or pass an explicit fail-closed deployment policy from runtime); reserve the stub for explicitly allowed in-memory local/tests. Add controller/HTTP tests for missing vault, including APP_ENV production with NODE_ENV absent. Do not return success, raw thrown errors, or 422 for missing credential storage.

12. **BLOCKING — Tasks 1/2/4, dependencies are introduced after their first consumers.** Task 1's exact `wireAdPlatforms` signature names `Database`, but `@platform/db` is only added in Task 2 (plan lines 131–133,285,340). Task 2 then requires runtime composition and admin dependency types to import the new service while the runtime/admin package dependencies are only added in Tasks 4/5 (lines 341–344,625,710). Task 4 also requires `STANDARD_RETRY`, which is private (`packages/tracking/src/delivery/platform-profiles.ts:18–23`), and Task 3 does not list that file for modification. **Fix:** allocate each manifest dependency/export to the task that first imports it: add the DB type dependency in Task 1 or defer the Prisma signature to Task 2; add the new service dependency in runtime/admin before Task 2 changes those packages; explicitly define/export the retry constant through the public tracking barrel or define an exact runtime-local retry descriptor. List these files in the corresponding task's staging scope and prove each task's own intermediate typecheck passes without deep imports or hoisted accidental resolution.

13. **BLOCKING — Task 3, Snap output field types contradict the saved vendor parameters (plan lines 530–533).** `external_id` is declared a string in `plan-d-docs/snap-parameters.txt:93`, but the builder emits `[keys.externalId]`. `num_items` is a string (`:120`), while `VendorEventInput.commerce.numItems` is a number and the output gives no conversion. The current lead golden omits both fields, hiding the mismatch. **Fix:** Snap emits scalar `external_id: keys.externalId` and `num_items: String(numItems)` when present; preserve the documented array-compatible fields such as em/ph. Add an external-id golden and a Snap purchase golden with `num_items: "3"`. Snap's seconds timestamp, `WEB`, wrapper and SIGN_UP lead mapping are accepted unchanged.

14. **BLOCKING — Task 3, missing vendor-required data currently produces successful invalid builds (plan lines 519–541,551).** `sourceUrl` is nullable and the blanket omission rule removes it, but Snap requires `event_source_url` (`plan-d-docs/snap-parameters.txt:173`) and TikTok requires `page` and `page.url` (`tiktok-web-setup.txt:256–262,572–578`). Snap also requires em, ph, or IP+UA for web matching, and PURCHASE requires value+currency (`snap-using-api.txt:105–133`). Sending empty keys for an already-hashed input (line 551) can reach exactly the invalid Snap match case. **Fix:** specify per-builder required-field refusal before returning `ok: true`, without echoing raw values: missing/invalid web source URL; Snap insufficient matching data; Snap purchase missing value/currency. Route those failures through finding 3's recorded blocked outcome and assert no HTTP call. Do not weaken consent or identity gates, or invent a URL, identity, value or currency.

15. **BLOCKING — Task 3, envelope-to-builder commerce contract loses existing data and leaves quantity undefined (plan lines 473–495,524,533).** Existing `EventPayload.contentIds` is independent of `contents`, and `LineItem.quantity` is optional (`packages/tracking/src/envelope/payload.ts:8–18,30–34`). The new input has no `contentIds` and requires `quantity: number` while specifying direct projection of `quantity`; a valid `{ contentIds: ["p-1"] }` cannot reach the promised vendor `content_ids`, and a valid `{ itemId: "p-1" }` cannot satisfy the input type. **Fix:** explicitly add and project content ids (prefer supplied ids, else derive from contents), specify quantity default `1` consistently with `deriveNumItems` (`payload.ts:65–68`), and state null/absent semantics for missing prices. Add input and golden cases for ids-only payloads and omitted line-item quantity. Do not require future event producers to duplicate ids in fabricated line items.

16. **BLOCKING — Global commands / Tasks 1,2,4,5 install steps (plan lines 99–101,311,383,687,736).** The commands omit the required process-only `pnpm_config_verify_deps_before_run=false` override on this already-installed pnpm 11 worktree. This is a documented Morbeh Windows prerequisite, not a repo config change: even test/exec/typecheck can otherwise reconcile/install the workspace before running. New-package links also use `timeout 600`, although the prescribed offline link workflow needs up to 1700 seconds. **Fix:** put `export pnpm_config_verify_deps_before_run=false` in every task's runnable command preamble; replace those install limits with the established 1700-second foreground install, owned by the parent once per dependency change. Keep native `C:/.../pnpm.cjs`, quoted worktree paths, and the no-next-build rule. Do not run a second install when dependencies are already linked. The targeted tests in this review were run successfully with that override.

17. **BLOCKING — Task 6, post-save state and destructive-operation UI contract (plan lines 754–786).** Each form reuses the view's `expectedVersion`, but the task specifies no action result/refresh contract and no `revalidatePath` at all. After save, an unchanged version in props causes the next save to conflict, and the saved configured/last4/live status remains stale. The existing action helpers provide only status/error state (`apps/admin-web/src/lib/api/mutation.ts:19–36`), not an updated `ConnectionView`. Also, the task adds token removal but omits the binding real-Dialog confirmation/focus rules; its bidi rule covers ids but not vendor names. **Fix:** give exact exported client/action input/output types, explicitly refresh the view/version by revalidating `/settings/ad-platforms` after every write that reached the API (including non-ok), and revalidate the storefront/public-id cache when relevant using the existing helper. Define how each card receives the new version before another submit. Add a real `@platform/ui` Dialog for token removal/disconnection: described warning, initial focus on Cancel, Escape closes, focus returned to a still-mounted trigger; vendor names in `<bdi dir="auto">`. Test two consecutive saves, non-ok revalidation, dialog keyboard/focus behavior, and non-disclosure against `document.body`. Keep DTOs/order constants browser-safe rather than importing the server service barrel into client components.

18. **OPTIONAL — Task 3, GA4 session attribution seam (plan lines 454–485,534–540).** The source summary explicitly mentions `params.session_id` (line 45), but neither `VendorEventInput` nor `browserIds` can carry it, and the GA4 builder omits it. The saved GA4 sending guide includes it alongside engagement time (`plan-d-docs/ga4-mp-send.txt:95–112`); the official MP reference recommends both for session/Realtime metrics. This is not a requirement to invent a session id or build browser capture in D1. **Fix:** add an optional GA session-id input and pass it through when available, with an absent/present golden; specify D2 supplies the genuine GA session id, not Morbeh's UUID session cookie. If deferred, document this reporting limitation explicitly.

19. **OPTIONAL — Task 2, fake-Prisma evidence and migration verification (plan lines 365–379).** The proposed migration is additive and its ENABLE/FORCE/policy form matches the existing leads migration (`packages/db/prisma/schema/migrations/20261122000000_leads/migration.sql:8–46`). However `createFakePrisma` explicitly does not model constraints/transactions (`packages/db/src/testing/fake-prisma.ts:11–15`), does not record `$executeRaw` (`:161`), and permits duplicate `(tenantId, platform)` inserts; a probe inserted two identical keys. **Fix:** use the leads-style recording Prisma helper for query/SET LOCAL assertions, a queued P2002 error for insert-conflict behavior, and the gated real-DB suite/static SQL assertions for uniqueness, RLS and migration shape. Also add empty/Google-Ads-only sync tests that load successfully through `loadTrackingRegistry`, so first sync deliberately produces an empty active rule set instead of relying on an undefined empty-registry fallback.
