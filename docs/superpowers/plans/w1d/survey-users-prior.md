### A2. Upload flow end to end

- **Direct raw-body POST, NOT presigned, NOT multipart.** Browser → (Next server action, bytes in FormData) → admin-web server → `POST ${RUNTIME_API_URL}/api/v1/media/uploads` with raw bytes (`sendAdminBinary`, apps/admin-web/src/lib/api/client.ts:278-329; timeout `UPLOAD_TIMEOUT_MS = 60_000` at :271; headers `content-type`, `idempotency-key`, `x-file-name`). The Fastify scope for that route installs a buffer parser limited to `maxBytes` (packages/http/src/server.ts:325-342, route.ts:80-93); >8 MiB → 413 before reading; other content type → 415.
- Server pipeline (`UploadImage.execute`, services/media/src/application/upload-image.use-case.ts:~102-161 of file): storage persistent && `publicBaseUrl` set else 503 → byte cap (product policy 8 MiB, image-purposes.ts:17,33-40) → **magic-byte sniff** (`sniff-image.ts`; client content-type is ignored; SVG refused) → types jpeg/png/webp/gif → no pixel/dimension rule for `product` purpose → key `tenants/<tenantId>/product-images/<yyyy>/<mm>/<id>.<ext>` via `StorageKeyBuilder` → `objectStorage.put(key, bytes, contentType, "public, max-age=31536000, immutable")` → ONE tx: `MediaAsset.create(... details{contentType, byteSize, width, height})`, no `folderRef` (always `undefined`!) → 201 `{id, url: ${MEDIA_PUBLIC_BASE_URL}/${storageKey}, width, height, alt:null}`.
- **Consequences for Files**: (1) upload cannot target a folder — `POST /media/uploads` has no folder param (UploadImageInput has none; asset created with `folderRef` undefined) → **backend change needed to upload into a folder** (or a follow-up assign-to-folder route; NOT FOUND today: no route/use-case moves an asset between folders; `MediaAsset.folderRef` is readonly, repo `save` update only writes `status, alt`). (2) Only IMAGES (jpeg/png/webp/gif ≤8 MiB). PDFs/videos/other files cannot be uploaded (415). Shopify Files accepts those — gap to flag. (3) `POST /media/assets` (register) is not usable from a browser (needs an object already in the bucket).
- **"Ready"**: there is no pending→ready state for library assets. `MediaAsset` status is only `active | archived` (`LibraryEntryStatus`, domain/value-objects/library.ts:3-22); an upload is `active` the moment the 201 returns (bytes are stored first, row second). (The legacy `Asset` model has `status registered|ready` (media.prisma:9) + `MediaAssetReady` event, but that is the old `/assets` path, not the library.) Storefront/admin consumers treat only `active` as usable (`ResolveMediaImages.usable`, resolve-media-images.use-case.ts:30).
- **Public URL / preview**: `image.url = MEDIA_PUBLIC_BASE_URL + "/" + storageKey` (publicMediaUrl, upload-image.use-case.ts:368-370; `.env.example:80-82`). The public bucket serves keys as-is (immutable 1y cache). admin-web must whitelist the origin in CSP `img-src` — `apps/admin-web/next.config.ts:36-44` (`mediaOrigin` from `MEDIA_PUBLIC_BASE_URL`). So grid thumbnails = `asset.image.url` directly (no signed URL, no resizing/CDN params). Without the env var no `image` resolves (resolve-media-images.use-case.ts:48) and uploads 503.
- **Does admin-web already upload?** YES.
  - Component: `apps/admin-web/src/components/products/editor/media-card.tsx` (`ProductMediaCard`, props at :98; calls `uploadProductImageAction` at :181; `accept={ACCEPT}` :399). Tests: media-card.test.tsx.
  - Server action: `uploadProductImageAction(formData)` — `apps/admin-web/src/app/products/actions.ts:1552-1575` (own 8 MiB check :1544; maps outcomes → `{status:"ok", image}` / `{status:"error", reason: unavailable|too_large|unsupported|failed}`).

  - Browser-side prep: `prepareImage(file)` — `apps/admin-web/src/lib/media/prepare-image.ts` (resize to ≤2048 px longest side, re-encode WebP q0.85, strips EXIF, GIF passthrough, 8 MiB cap; `MAX_UPLOAD_BYTES` :8).
  - Other uploader: `uploadOnlineStoreImage` (apps/admin-web/src/lib/api/online-store.ts:288) for theme purposes.
  - `next.config.ts:78` `serverActions: { bodySizeLimit: "10mb" }` already allows an 8 MiB upload through a server action.
  - Alt text: `updateMediaAlt(mediaAssetId, alt, idempotencyKey)` media.ts:120-130; action `updateMediaAltAction` products/actions.ts:1578-1594 (revalidates `/products/:id` only if a `productId` is posted).

### A4. Archive semantics + folder rules

- **Soft delete only.** Archive sets `status="archived"` (asset: media-asset.ts:70-76; folder: folder.ts:161-167); row, object bytes and storage key remain. Archiving twice → `BusinessRuleError("Media asset is already archived" / "Folder is already archived")` → **409** `BUSINESS_RULE` envelope (media-library.use-cases.ts ArchiveFolder :82-87 / ArchiveMediaAsset :180-185; status map services/media/src/interfaces/presenter.ts:8-16). Unknown id → 404.
- **NO restore / unarchive / delete-forever / rename / move**: NOT FOUND (no use case, no route; `LibraryEntryStatus` is only active|archived; no `unarchive` method on either aggregate). Repo `save` for existing rows writes only `status` (folder, prisma-library-repositories.ts:34-37) / `status`+`alt` (asset, :103-106) — so a rename or move needs repo changes too.
- **Folder rename: NOT FOUND** (outline mentions "folders (list/create/rename/archive)" but there is no rename route; `Folder.name` is readonly prop; update `data` only touches status).
- **Folder archive rules**: none beyond already-archived. No cascade, no "is empty" check; assets of an archived folder keep `folderRef` pointing at the archived folder; children folders stay active. `createFolder` does not validate `parentFolderRef` exists/active/is in-tenant (media-library.use-cases.ts:45-61) and no name uniqueness, no cycle check, no depth cap. `registerMediaAsset` doesn't validate `folderRef` either.
- Archived assets: still returned by `GET /media/assets` and `GET /media/assets/:id`; `ResolveMediaImages` skips them (so a product that references an archived asset loses its picture) and `existingIds` excludes them (blocks attaching). **Archive does not check whether the asset is in use** (no "used in" lookup) — risk: archiving an image used by a product/theme silently blanks it; Shopify blocks/warns on delete.
- Events: archive/create raise `MediaLibraryChanged` {entityType: media_asset|folder, action created|archived} to the outbox (domain/events/media-library-changed.event.ts); upload path also emits via `MediaAsset.create`.

## PART B — USERS & PERMISSIONS (Settings > Users)

**HEADLINE FINDING:** the routes the outline points at (`/users`, `/memberships`, Identity `User`/`Membership`) are the
legacy "Option A" access slice and are **NOT connected to native staff sign-in**. A real staff member today is a
**Security principal + a password credential (`staff:<email>`) + a Security role assignment**, created only by
`staff-owner-bootstrap.ts` / `tenant-provisioning.ts` / merchant sign-up. There is **no list-staff read, no invite, no
role-change that affects login, no last-admin guard, no self-service 2FA, and the "require 2FA" policy would lock every
staff member out** (login has no code step). So Wave 1b needs a NEW staff slice in Security + admin (see Design), not UI glue.
