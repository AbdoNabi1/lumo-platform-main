## Confirmed findings (review continues)

### R1 — BLOCKING — Task 2: fail-loud mail configuration does not match runtime wiring

- **Plan quote:** L126: “when `passwordReset`, `emailSender` or `adminPublicUrl` is missing → 503 ... BEFORE any write”.
- **Code evidence:** `apps/runtime/src/email-wiring.ts:20–33` ALWAYS supplies an `emailSender`; without `RESEND_API_KEY` it returns `LoggingEmailSender`. Presence is not delivery capability.
- **Concrete fix:** Add an explicit delivery-capability seam from runtime through admin wiring (or omit the invitation sender when logging-only), preserve reset behavior, and test `resolveEmailWiring` without a key + a configured public URL → invitation 503 and zero writes. Merely testing an omitted sender does not cover production composition.

### R2 — BLOCKING — Tasks 1–2: password writes are outside the claimed staff transaction, and accept ordering is unsafe

- **Plan quote:** L97: “else in one UoW ... set an unusable random password via `passwordRegistrar.setPassword`”; L100: “password ... set by Task 2 before calling this”; L130 instead orders acceptance/activation BEFORE `passwordRegistrar.setPassword`.
- **Code evidence:** `services/security/src/application/password-credentials.ts:42–50` has no tx argument; `infrastructure/hashed-password-auth-provider.ts:50–71` writes through its store; `infrastructure/prisma-password-credential-store.ts:56–74` opens an independent transaction and upserts both hash AND principal owner. `application/principal.use-cases.ts:60–90,109–135` each start their own UoW. `apps/admin/src/interfaces/staff-auth.admin-controller.ts:96–125` permits login once the principal is active and roles map.
- **Concrete fix:** Define a transaction-aware credential write seam and compose registration, suspension, assignments, invitation and audit through repositories/helpers using the SAME tx (not nested public use cases). For accept, persist the chosen password and accept/activate atomically with CAS/lock against revoke/expiry; do not publish an active principal with its old credential. Token consumption/retry and directory compensation need a specified recovery path. Test fault injection after credential write / invitation write / activation and a prior plain-reset password: failed accept never makes that old password usable or strands an accepted account with a consumed token.

### R3 — BLOCKING — Task 1: last-admin count/check needs serialization and real rollback

- **Plan quote:** L93: “each inside ONE `unitOfWork.run`”; L95–96: “if the result leaves zero active principals ... (rolled back)”.
- **Code evidence:** `packages/db/src/transaction.ts:15–23` requests no serializable isolation or tenant lock. `services/security/src/infrastructure/in-memory-unit-of-work.ts:3–7` provides NO rollback. Distinct target assignment/principal version checks do not serialize two admins demoting/deactivating one another.
- **Concrete fix:** Specify an infra-owned tenant-keyed staff mutation lock (like 1c), acquired before actor/target/count reads, with tx-aware readers and mutation helpers; revalidate the actor's current active/admin authority under it. Validate the invariant before mutating or ensure rejected Result values truly abort and memory snapshots restore. Add concurrent ownerless A/B cross-demotion/deactivation tests with one success/one rejection and one active admin remaining, plus rollback assertions against real memory state (not only a revocation spy). Supply both lock adapters in Task 1.

### R4 — BLOCKING — Task 2: wrap the HTTP guard too, not only the facade guard

- **Plan quote:** L155: “Wire it in `composition.ts` around the existing `accessControl` passed to `new AdminGuard(...)`”.
- **Code evidence:** `apps/admin/src/composition.ts:1240–1242` builds the facade guard, but `apps/admin/src/http/server.ts:136–140,161–165` independently builds/passes the HTTP guard using the ORIGINAL `deps.accessControl`. `packages/http/src/server.ts:461–475` authorizes through that HTTP guard. A facade-only wrapper is not the claimed single shared enforcement boundary.
- **Concrete fix:** Expose/share the same live access-control (or guarded permission seam) from `wireAdmin` and use it in `createAdminHttpApi` as well as facade controllers. Name both files and add an HTTP test for a suspended principal against a route that does not rely on a second controller guard, plus idempotency-replay denial and public/customer/service non-regression tests. Keep one cache/invalidation instance, not two independent copies.

### R5 — BLOCKING — Tasks 1–2: invited admin can bypass the owner/self guards through existing security APIs

- **Plan quote:** D14 L11: owner “cannot be demoted, deactivated or removed through these screens”; G5 L26: “no role-table edit”; L95–96 guards exist only in the new staff use cases.
- **Code evidence:** `packages/auth/src/role-table-access-control.ts:40–58,75–85` gives a mapped admin `*:*`. `apps/admin/src/http/security-authorization-routes.ts:184–210` exposes assign/revoke with only `security:*` permissions; `interfaces/security-authorization.admin-controller.ts:43–58` simply guards/delegates. `services/security/src/application/authorization.use-cases.ts:159–191,223–232` permits granting `platform-admin` to any existing principal and revoking its assignment without owner/self/last-admin guards. `apps/admin/src/http/security-identity-routes.ts:76–89` and `services/security/src/application/principal.use-cases.ts:109–126` likewise allow direct owner lifecycle transitions. A newly invited ordinary admin can make itself an unremovable owner or disable the real owner using these reachable APIs.
- **Concrete fix:** Specify how staff-facing legacy role-assignment/revoke/principal-transition routes enforce the same invariants and reject ordinary-admin assignment of `platform-admin` (and block equivalent legacy identity-provisioning paths). Use real role keys/current actor authority server-side; token `admin` alone cannot identify an owner. Preserve trusted provisioning/service seams separately. Require adversarial HTTP tests with an accepted invited admin: self-promote to platform-admin, revoke/demote/suspend owner, self-disable and remove last admin all denied; operator/viewer still denied. This flags an unsafe privilege boundary, not a request to change D14.

### R6 — BLOCKING — Tasks 1–2: revoke permanently blocks reinvitation; token reuse must not resurrect a replacement invite

- **Plan quote:** L97: “a `staff:` credential already exists ... → ConflictError”; L99: revoke “principal stays `suspended`; revoke its staff-role assignments”; L128 releases the directory row. L157: “resend ... old link still accepted only while the invitation is pending”.
- **Code evidence:** `services/security/src/application/password-credentials.ts:20–50` provides no delete/disable/replace-invitation credential operation. `services/security/src/application/password-reset.ts:10–21,65–84` binds a token ONLY to an identifier, then resolves whichever credential currently owns that identifier. `packages/db/prisma/schema/security.prisma:433–444` has no purpose, invitation ID, generation or principal binding. Releasing the directory does not remove the credential; creating another invitation for that address therefore always conflicts. Naively allowing credential reuse also lets old unconsumed links operate on a new pending invitation or change the accepted account's password through plain reset-complete.
- **Concrete fix:** Define an explicit revoke → reinvite lifecycle, including credential ownership and safe terminal-principal treatment. Bind invitation capabilities to their invitation/principal (and check pending/expiry on accept), or invalidate all prior capabilities atomically before any replacement. Keep normal password reset backward-compatible, but forbid using invitation capabilities to reset an accepted/replacement account after their invitation ceases to be pending. Tests: revoke → new invite succeeds; old link rejected through BOTH accept and plain reset-complete; accepted invitation's sibling resend links cannot reset the active account; expired/revoked invitation + normal password reset leaves the principal suspended and login denied. A plain reset on a suspended invited principal is NOT by itself an activation bypass; the missing lifecycle/capability binding is the defect.

### R7 — BLOCKING — Tasks 1–2: finish the cross-task revoke/resend/audit contracts and recovery paths

- **Plan quote:** L98 `RenewStaffInvitation { tenantId; invitationId; expectedVersion; now }`; L99 revoke returns ONLY `{ invitationId }`; L128 immediately consumes `{ email, principalExternalId }` for release/invalidation. L93 requires audit metadata `{ actor, target, … }` for every write. L130 consumes token → accepts principal → writes password → activates directory.
- **Code evidence:** `services/security/src/application/deps.ts:135–143,150–166` requires audit facts to be supplied; it does not recover an actor. `services/tenancy/src/application/staff-directory.use-cases.ts:59–80` activates by email only, opens its own UoW, and returns NOT_FOUND on a missing entry. `apps/admin/src/http/public-merchant-routes.ts:210–219` refuses a pending directory entry even when Security is active. `services/security/src/infrastructure/prisma-password-reset-token-store.ts:21–44` consumes in a separate committed transaction. Thus a directory activation failure after acceptance strands an active account behind a pending directory with a consumed token; resending is specified only for pending invitations. Revoke similarly cannot perform its prescribed cleanup from its returned fields, and a failed release has no specified retry state.
- **Concrete fix:** Pin complete producer/consumer input/output signatures: revoke must safely return the email and target external ID internally (or expose a named scoped read), renew must receive the authenticated actor, and accept audit must use an explicit public/target identity, not a nonexistent admin. Define success/failure envelopes and recovery for token-request null/throw, credential write, directory activation/release, and lost responses. Require directory activation/release to compare expected shop AND principal and status atomically, with a safe resumable completion/compensation mechanism that never activates a newly reassigned email. Add injected-failure/retry tests proving eventual merchant login, no orphan directory/credential after failed create, no deletion/activation of another shop's entry, and exact sanitized actor/target/action metadata. Coordinate the Security atomicity work with R2; do not claim one transaction across independent tenancy/password operations.

Further read-model, harness and UI evidence is being checked.
