## 0. Headline

1. There is **no staff slice at all**: no list, invite, role-change, deactivate-with-effect, self-service 2FA, login code step, last-admin guard, staff activity read. `/settings/users` is still a "Soon" placeholder. (verified, see §8)
2. A real staff member = Security **principal** (human) + **password credential** `staff:<email>` + Security **role assignment**. The legacy `/users` `/memberships` Identity routes are NOT connected to sign-in (§3).
3. Login has **no code step**; the tenant flag `mfaRequired` already exists and, if switched on today, locks every staff member out (§2). The existing TOTP/backup-code/enrol machinery is real but admin-only and cannot be used for self-service as-is.
4. **[NEW] Multi-tenant sign-in is gated by `tenancy.staff_directory` ("one store per email", PK email).** An invited colleague who is not in that directory cannot sign in through the merchant login path, and an email that already owns another store cannot be invited (§2.4, §7).
5. **[NEW]** `AdminGuard` / JWT verification never consults sessions or principal status, so deactivation / role change only bites at next login (token TTL default 7200 s) (§7).
6. Recommendation: `needs_migration: true` (one additive table, `staff_invitations`), 5–6 tasks, defer the require-2FA toggle and probably the activity UI (§9).

### 2.3 Where a code step plugs in

- `Authenticate` (`services/security/src/application/authentication.use-cases.ts:115-230`) already computes the requirement: `MfaEngine.decide` (:163-170; `services/security/src/domain/mfa-engine.ts:36-70`): `tenantMfaRequired`→`required`, elevated/high risk or `sensitiveAction`→`step_up`, **unenrolled principal under required/step_up ⇒ `required` with reason "no active enrollment — enrollment required" (:60-68)**; with `mfaSatisfied:true` (:171-172, input :86) a session is created. `profile` is read only when `principal.tenantRef !== null` (:155-158): the bootstrap owner has `tenantRef` unset (`apps/admin/src/staff-owner-bootstrap.ts:40-47`) so the policy silently skips them; provisioned/merchant owners have `tenantRef` (`tenant-provisioning.ts:138`).
- Because `authenticate` re-verifies the password, the natural 2-step shape is: step 1 = `authenticate` (password OK, `mfa_pending`, no session — the controller already detects this :82); step 2 = a **signed short-lived challenge** (separate `aud`/`typ`, e.g. 5 min, carrying sub+tenant, NOT accepted as a session token) → code verify → `security.establishSession` (existing `EstablishSession` `session.use-cases.ts:48`, route `security:establish_session` `security-sessions-routes.ts:97`) → role keys → `issuer.issue`. This avoids re-sending the password and does not need `mfaSatisfied` from a client. Alternative (simpler, weaker UX): `{email, password, code}` in one POST + `mfaSatisfied:true` server-side after verifying the code.
- New plumbing needed: `staffLoginBody` is `.strict()` (:11-16) → new route `/public/auth/staff/login/verify` (+ merchant twin, because the merchant path is first in `native-login/route.ts:33`), `NativeTokenIssuer.issueChallenge`, admin-web `/login/verify` page + route handler, `lib/auth/native.ts` + `merchant.ts` to surface a challenge on 403.

## 7. Safety constraints

- **Last-admin / self protection: NOT FOUND** (re-verified: `AssignRole`, `RevokeRoleAssignment`, `TransitionPrincipal`, identity `User.deactivate`/`Membership.changeRole` have no guard; grep "last admin|owner|self" in services/security, services/identity, apps/admin finds nothing relevant). An admin can disable themselves, revoke the only `platform-admin`, or demote the owner. Must be built in the new use cases, inside one `unitOfWork` (count + change), with `version` optimistic lock on assignments (`security.prisma:146-164`).
- **Tenant scoping of staff**: staff data is scoped by `tenant_id` + RLS in Security; one principal ↔ one tenant (`principals` unique (tenantId, externalId)), JWT carries one `tenant_id`. **No multi-store staff membership**; and `tenancy.staff_directory` hard-codes "one store per email" (§2.4). A person in two stores is unsupported (would need two emails). New routes must take the tenant from `context.tenantId` only (prior-survey defect: body-tenantId in `/users`).
- **Session invalidation**: not enforced at request time. `JwtVerifier` checks signature/claims only (`packages/auth/src/jwt-verifier.ts:61-79,105-118`); `AdminGuard.ensure(principal, permission)` ignores the guard context's `sessionId` (`packages/http/src/server.ts:~457-475` passes it, `admin-guard.ts:26` takes two args); `SECURITY_ZERO_TRUST_ENFORCEMENT=on` is refused at boot ("not supported yet", `apps/runtime/src/config.ts:447-455`). So deactivate / role change takes effect at the **next login** (≤ `STAFF_TOKEN_TTL_SECONDS`, 7200 s default). `RevokeAllSessions` (`security.session.revoked_all`, `session.use-cases.ts:246-301`) only marks Security sessions revoked + (ory mode) syncs Kratos (`session-revoked-all.consumer.ts`); in native mode nothing reads those sessions per request. Mitigations: lower TTL, add a short-TTL cached principal-active + role check in the native guard path, and call `revokeAllSessions` + show "takes effect within N min". Re-login IS blocked immediately for a `suspended` principal (`introspectSessionSubject` → inactive, `staff-auth.admin-controller.ts:96-102`) and for a user with no mapped role (:115).
- Owner identification: "Store owner" = holder of `platform-admin` (bootstrap/provisioning). `TOKEN_ROLE` maps both `platform-admin` and `admin` to token role `admin`, so an invitee given role `admin` and the owner look identical to the UI → needs an explicit `isOwner` rule (keep `platform-admin` non-assignable/non-revocable via the new API).
- Principal `disabled` is terminal; use `suspended` ⇄ `active` for deactivate/reactivate.
- Deactivated staffer in multi-tenant: directory row stays (no delete), email reserved.

## 9. Recommendation

### 9.1 Data-model decision

Keep the Security principal + credential + role-assignment model; do **not** build on `/users`+`/memberships`. Define Security roles `admin|operator|viewer` (idempotent upsert alongside `platform-admin`; permissions `[]` — real authorisation stays in `RoleTableAccessControl`) and add `ensureStaffRoles(tenantId)` inside the new use cases (existing tenants never re-run `bootstrapSecurity`). Keep "owner" = `platform-admin` (non-assignable / non-revocable via the new API). New read ports (Prisma + in-memory): `PasswordCredentialStore.listStaff(tenantId)`, `RoleAssignmentRepository.listByTenant(tenantId)`, `MfaEnrollmentRepository.listByTenant`, `SessionRepository.lastEstablishedByPrincipal`, principal created-at reader.

### 9.2 Migration — `needs_migration: true`

One additive hand-written migration (name must sort AFTER `20261125000000_customer_segments`, e.g. `20261126000000_staff_invitations`; header "written by hand, NOT applied by the agent", RLS enabled+forced with `tenant_isolation`, per `20261006000000_security_password_credentials`):

- `security.staff_invitations(id uuid pk, tenant_id text, email text (lower/btrim check), principal_external_id text, role_key text check in (admin,operator,viewer), invited_by text, status text check in (pending,accepted,revoked,expired), expires_at timestamp(3), accepted_at timestamp(3) null, created_at, updated_at, version int)`; unique partial `(tenant_id, email) WHERE status='pending'`; index `(tenant_id, status)`.
- Prisma model `SecurityStaffInvitation` in `security.prisma`; keep `schema-migration-consistency.test.ts` green.
- NOT needed: last-sign-in column (derive from `security.sessions.established_at`), MFA tables (exist), require-2FA (exists: `tenant_profiles.mfa_required`), activity (ledger exists), code-attempt counter (use `RateLimiter`), challenge (stateless signed token), staff_directory (exists).
- No-migration fallback if the owner refuses any DDL: derive "Invited" = credential exists ∧ never a session ∧ `principal.attributes.invitedBy` set; no resend/revoke history and no invite expiry other than the reset-token TTL.

### 9.3 Task split (dependency order)

- **T1 — Backend staff core** (security + admin, no UI): staff roles upsert; read ports; `ListStaff`, `ChangeStaffRole`, `SetStaffActive` (suspend/activate + `revokeAllSessions`) with guards (not self, not owner, not last active admin, same `unitOfWork`); `/staff` routes (`staff:read|invite|change_role|deactivate`, tenant from context, idempotent writes) wired next to `...mediaLibraryRoutes(admin)` (`admin-routes.ts:2337`); ledger actor/target metadata; role-table test.
- **T2 — Invitations** (needs the migration): `InviteStaff`/resend/revoke, `staff_invitations` repo, token (extend `PasswordResetService.request` with `ttlSeconds` → 7 days), `staffInviteEmail` template, fail-loud 503 when email/`ADMIN_PUBLIC_URL` missing, **multi-tenant: record+activate the invitee in `tenancy.staff_directory`** (409 → "email already used elsewhere"), accept = reuse `/reset-password` with `invite=1`.
- **T3 — Login code step** (security + admin + admin-web; prerequisite of the policy): `VerifyMfaCode` (TOTP + backup code via hash + `consumeBackupCode` + save), challenge token, `/public/auth/staff/login/verify` + merchant twin, `establishSession` after the code, per-principal attempt limit + replay guard, admin-web `/login/verify` + `native-login/route.ts` + `lib/auth/{native,merchant}.ts`. Also set `tenantRef` for the bootstrap owner (`staff-owner-bootstrap.ts:40-47`) / backfill.

- **T6 (deferrable) — Require-2FA policy + Activity log.**

### 9.4 What to defer if the wave is too big

1. **Defer the require-2FA toggle (and its card)** to the end or Wave 1e. If shipped: server-side refuse enabling unless (a) T3 is deployed (feature capability flag derived from the verify route existing), (b) caller has an active enrolment, (c) **every active staff member has an active enrolment** (otherwise unenrolled users get `required` forever, `mfa-engine.ts:60-68`), (d) bootstrap owner's `tenantRef` is fixed; wrap `ConfigureTenantSecurity` with `tenantRef = tenantId` and write actor + `mfaRequired` to the ledger. A login-time "enrol now" path is the real fix but is a further task.
2. **Defer the activity UI**; ship only the metadata enrichment (T1) so the data accumulates, then add `GET /staff/activity` (+cursor/filters) and the card later.
3. Everything else (T1–T5) is the minimal viable "users and permissions"; T3+T4 can be merged into one "2FA" task if one implementer owns both.

### 9.5 Risks

- **Lockout**: policy before T3 = nobody can sign in (verified: `mfa` reply dead-ends at `native-login-form.tsx:6-10`); policy with unenrolled members = same; adaptive step-up already forces the same dead end for elevated-risk logins; bootstrap owner bypasses the policy (null `tenantRef`) → inconsistent; **last-admin lockout** (no guard today); owner self-deactivation; credential lockout (10 fails/15 min) is an existing DoS vector on known emails.
- **Enumeration**: invite of an already-registered email (409 from the directory / credential exists) reveals membership to an admin only — acceptable, but keep login/reset/verify responses uniform (reset already uniform, `staff-auth.admin-controller.ts:128-159`); code-verify failure must not say whether the account exists; merchant path burns time for unknown emails (`burnVerifyTime`) — keep for the verify step.
- **Replay / brute force**: TOTP has no used-step memory and no attempt counter (`totp-mfa-provider.ts:56-78`, `mfa.use-cases.ts:98-102`) → add per-principal attempt limit + lockout, reject reuse of the same step; backup codes are single-use only once a consumer exists.
- **Clock skew**: ±1×30 s tolerance (`totp-mfa-provider.ts:10`); acceptable; surface "code expired, check your phone's clock" without leaking more.
- **Secret storage**: depends on `MFA_TOTP_KEY` being set (optional in config :95; absent ⇒ constant key); no key id → rotation breaks all enrolments; enrolment secret shown once via `provisioningUri` (never log/echo it; the server action must not put it in URLs/revalidated cache); ledger metadata must not carry codes.
- **Token staleness**: deactivate/role change effective ≤ 2 h (§7) — surface in UI or add a guard check.
- **Multi-tenant**: invitee not in `staff_directory` cannot sign in via merchant login; one store per email (§2.4).
- **Email**: logging sender in non-configured envs ⇒ no real invite; fail loudly.
- `identityDirectory` is in-memory (fine for same-request register); display-name of owners is a UUID (don't show it).
- Brand lock (AGENTS.md): no changes to tokens/fonts/logo; do not touch the lock tests.
