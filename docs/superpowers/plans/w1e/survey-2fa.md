## 0. Headline (what a planner must know first)

1. **The login code step does not exist yet and `StaffAuthAdminController.login` is untouched by 1d** (only `TOKEN_ROLE` gained `export`) — `apps/admin/src/interfaces/staff-auth.admin-controller.ts:21`. Nothing else in the login chain changed.
2. **[NEW — design-critical] Having an active enrolment does NOT make `Authenticate` ask for a code.** `MfaEngine.decide` returns `optional` when nothing else applies (`services/security/src/domain/mfa-engine.ts:49-50`), and `optional` counts as satisfied (`authentication.use-cases.ts:171-172`) ⇒ a session is created straight after the password even for an enrolled user. Requirement (a) ("staff with an active TOTP enrolment … enter a code") therefore needs a **new opt-in on `AuthenticateInput`** (e.g. `requireEnrolledFactor: true`, set only by the staff login — customers also use `authenticate`, `customer-auth.admin-controller.ts` passes `MFA_REQUIRED` through, so do not change the engine's default). Without it only tenant-policy / step-up users get a code prompt.
3. **[NEW] Policy `mfaRequired` is silently skipped for the bootstrap owner** (`principal.tenantRef === null`: `staff-owner-bootstrap.ts:40-47` sets no `tenantRef`; the profile is only read when `tenantRef !== null`, `authentication.use-cases.ts:155-158`). 1d-invited staff DO have `tenantRef = tenantId` (`staff-commands.use-cases.ts:382`), provisioned owners too (`tenant-provisioning.ts:138`). Cheapest fix: read the profile by `principal.tenantRef ?? input.tenantId` (the baseline profile is keyed `tenantRef = tenantId`, `tenant-baseline.ts:~115-123`) in `Authenticate` (:155-158), `DecideMfa` (`mfa.use-cases.ts:221-224`) and compliance (`compliance.use-cases.ts:~80`) — no data backfill, no migration.
4. **[NEW] The audit ledger is split across chains** (`tenant_scope`): 1d `auditStaff` writes `tenantRef` unset ⇒ scope `null` (`staff-commands.use-cases.ts:140-156`), `security.auth.succeeded` uses `principal.tenantRef` (tenantId for invitees/provisioned owners, null for the bootstrap owner), `mfa.enrolled` uses `principal.tenantRef`, `mfa.verified/revoked/backup_codes_generated` set none. `auditLedger.list(tenantRef, tenantId)` filters `tenantScope = tenantRef` exactly (`prisma-repositories.ts:908-920`) ⇒ **no single existing call returns the whole staff activity**. The activity read needs a new tenant-wide paged reader (§7).
5. With the policy on, **a newly accepted invitee can never sign in** (unenrolled ⇒ `required` forever, `mfa-engine.ts:60-68`; no enrol-at-login). The policy precondition must also cover pending invitations / reactivation (§5, §9).
6. `needs_migration: true` (recommended, one additive column `security.mfa_enrollments.last_used_step`); a no-DDL fallback exists (§8).

## 3. Challenge token

- Runtime wiring `apps/runtime/src/composition.ts:274-293`: one issuer; the HTTP authenticator is `new JwtVerifier({issuer, audience: config.AUTH_AUDIENCE ("morbeh-admin"), getKey: local JWKS})` (:288-293).
- `JwtVerifier` `packages/auth/src/jwt-verifier.ts:56-80`: `jwtVerify` with `issuer` + `audience` + clock tolerance 30 s; maps `sub/kind/roles` (:105-118; unknown/absent `kind` ⇒ `customer`). admin-web re-verifies the cookie with the same iss/aud (`lib/auth/session.ts:~52-56`, `middleware.ts:215-218`).
- **How to issue a non-session token the authenticator won't accept:** add `issueChallenge({sub: principalExternalId, tenantId, email, ttlSeconds ≈ 300, jti})` that signs with the **same key + issuer but a different audience** (e.g. `` `${audience}:mfa-challenge` ``), header `typ: "mfa-challenge+jwt"`, claims `purpose:"staff-login-mfa"`, `tenant_id`, `jti`, and **no** `kind`/`roles`/`sid`; plus `verifyChallenge(token)` (jose `jwtVerify` with that audience, `typ`, `issuer`, `clockTolerance`, required claims) on the issuer (it owns the public key and already exposes `jwks()`). Both the runtime `JwtVerifier` and admin-web reject it (audience mismatch ⇒ `null`/redirect to login) — test by feeding a challenge to `JwtVerifier.verify` (⇒ null) and a session token to `verifyChallenge` (⇒ reject). Never put the challenge in `morbeh_session`; admin-web stores it in its own short-lived httpOnly cookie (never in the URL).
- Single use: the token is stateless, so within its TTL it could be replayed for more code attempts. Mitigation: per-principal attempt limit is the real brute-force guard; optional `jti` single-use via `rateLimiter.consume("rl:mfa-chal:<jti>", 1, ttl)` after success.
- **Attempt counter pattern (existing):** `rateLimiter.consume(key, limit, windowMs)` per attempt, deny when `!decision.allowed` ⇒ 429 via `rateLimited(...)` (`public-staff-auth-routes.ts:63-82`). For 1e: key `rl:<tenantId>:staff-mfa:<principalExternalId>` (per **principal**, taken from the verified challenge, not per IP), e.g. 5–8 per 5–10 min, consumed on every attempt incl. success; fail **closed** on limiter error (credential endpoint, per the `RateLimiter` contract doc). Existing credential lockout: 10 fails / 900 s per credential (`hashed-password-auth-provider.ts:41-42,96-106`) — an attacker who knows the email can already lock a user out; the MFA limiter is keyed by the challenge-verified principal, so the attacker needs the password first (weaker DoS vector).

## 4. Finishing login after a verified code (no password resend)

- `EstablishSession` `services/security/src/application/session.use-cases.ts:48-93`: `execute({tenantId, principalExternalId, refreshFingerprint, externalRef?, deviceRef?, ttlSeconds}) → SessionOutput {id, principalRef, status, …}`; looks up principal (404 if absent; **does not check principal status**), `Session.establish(...)`, saves, telemetry, audit `security.session.established` (principalRef externalId, tenantRef principal.tenantRef). Controller `SecurityController.establishSession` (:337); admin route `security:establish_session` (owner-only, not used by login).
- Today login gets its session **inside `Authenticate`** (:185-203, TTL = `sessionTtlSeconds`, fingerprint `randomToken(24)`); `StaffAuthAdminController.login` then calls `introspectSessionSubject` (`session.use-cases.ts:~380-415`: rejects invalid session or non-active principal) → role keys → `issuer.issue`.
- **Cleanest 2-step shape (recommended):**
  1. step 1 = `authenticate` with the new opt-in (`requireEnrolledFactor`) ⇒ password ok, `authenticated:true, sessionId:null, mfaRequirement:"required"` (already detected at :82). Instead of the bare 403, return `403 MFA_REQUIRED` **plus `challenge`** (signed token) + `challengeExpiresIn`; keep `error.code:"MFA_REQUIRED"` so existing consumers (`merchant.ts`, `native.ts`) still classify it. For an **unenrolled** user under policy/step-up the 403 carries no challenge (dead end remains ⇒ §5/§9).
  2. step 2 = `POST /public/auth/staff/login/verify {challenge, code}` ⇒ `verifyChallenge` ⇒ rate-limit ⇒ `VerifyMfaLogin` ⇒ `security.establishSession({tenantId, principalExternalId, refreshFingerprint: randomToken, ttlSeconds: sessionTtlSeconds})` ⇒ **reuse the tail of `login` (lines 96-125)**: extract a private `issueSession(tenantId, sessionId, email)` from `login` and call it from both. Put the lower-cased email in the challenge so verify does not need the credential store.
  - `Authenticate` with `mfaSatisfied:true` is the alternative but it re-checks the password (needs the password again) and trusts a client flag — not recommended. Step 1 already wrote `auth.succeeded`/risk/device.
  - Re-check principal `active` + ≥1 mapped role in step 2 (the `introspectSessionSubject` tail does both) so a user deactivated between steps can't finish.
- Merchant path: `POST /public/auth/merchant/login` calls `staffAuth.login` with `tenantId: store.shopId` (:227); the 403 passes through (:234). The challenge carries `tenant_id` = store id, so **one** verify route that takes the tenant from the **verified challenge claim** (not the header) serves both paths; a thin merchant twin is only needed for the platform-tenant gate + `rl:merchant-…` symmetry. The merchant `burnVerifyTime` (:89-92) is irrelevant at verify (the challenge already proves a correct password).

### 9.2 Risks

- **Lockout:** user loses phone → needs a backup code; no admin reset path ⇒ an admin/owner who loses both is locked (support/DB recovery). Policy on + new invitee ⇒ dead end (§0.5); the toggle must never be enabled by someone without their own active enrolment; revoke/disable must refuse while the policy is on.
- **Enumeration:** keep the verify failure body identical for wrong code / outside window / no enrolment / unknown principal (generic 401 `INVALID_CODE`); an expired challenge may use a distinct 401 (`CHALLENGE_EXPIRED`) because holding the token already proves the password. Login 403 `MFA_REQUIRED` already appears only after a correct password.
- **Replay:** TOTP step rejected twice (`lastUsedStep`), backup code single-use via CAS; challenge reusable within TTL ⇒ per-principal limiter + optional `jti` burn.
- **Brute force:** 6 digits × ±1 step ≈ 3 valid codes per 10⁶; limit per principal ≈ 5–8 per 5–10 min (Redis, fail closed). Also add a counter to enrolment confirm and turn-off (`VerifyMfaEnrollment` has none, `mfa.use-cases.ts:99-102`).
- **Clock skew:** ±1×30 s (`totp-mfa-provider.ts:10`) + challenge `clockTolerance` 30 s; "check your phone's clock" hint without more detail.
- **Secret exposure:** secret/URI only in the start-enrolment response (server-action state → client; never URL, never revalidated RSC payload, never logged, never in the idempotency store ⇒ **non-idempotent** routes); backup codes plaintext once; ledger metadata never carries codes; `MFA_TOTP_KEY` is still **optional** (`apps/runtime/src/config.ts:95`) and absent ⇒ constant legacy key — refuse enrolment/policy (503 `NOT_CONFIGURED`) when the real provider/key is absent in non-local envs; no key id ⇒ rotating `MFA_TOTP_KEY` invalidates every enrolment.
- **Policy precondition:** compute "every active staff enrolled" inside the staff lock; re-check on enrol-revoke/invite/accept/reactivate while on; fix the bootstrap-owner `tenantRef` gap (§0.3) so the policy actually binds the owner.
- **Token staleness:** 1d's live check bites within 30 s for role/active changes; 2FA turn-off does not revoke existing sessions — decide whether enabling/disabling/regenerating should revoke other sessions (pattern `revokeSessionsInTx`, `staff-commands.use-cases.ts:~100-131`).
- **Brand lock (AGENTS.md):** UI tasks must not touch locked tokens/fonts/logo/lock tests/CODEOWNERS.
