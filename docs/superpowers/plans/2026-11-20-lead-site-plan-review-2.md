# Lead site — Plans A and B, round 2

Reviewed `morbeh/lead-site` at `12241096`. **A**, **B** and **Spec** refer to the revised `2026-11-20-lead-site-part-a-site-type.md`, `2026-11-20-lead-site-part-b-tracking-identity.md` and `2026-11-20-lead-site-and-tracking-design.md`. References below are worktree-relative. Two owner invariants are still not enforced: a type write can finish after activation, and a lead can be forwarded twice during one uninterrupted session.

## Findings

1. **BLOCKING — A stale pending attempt can change an active shop's type (R1 #1, not a demand to preserve the first failed request).** A:12–20,88–89,154–155,207–223 relies on one _method_, not one _execution_. `apps/admin/src/merchant-onboarding/merchant-onboarding.ts:115–118,134–150,154–169` reads directory status once, awaits several operations, then activates separately. Two requests can both observe pending. If one pauses before recording `store`, the other can record `lead_site`, activate, and return 201. The paused request can then unconditionally upsert `store`. Even its own 201 is assembled from input, not from the activation that won. **Fix:** finalize the submitted choice and the pending→active transition as one serialized, conditional operation for that directory entry, with the proper scopes for both records; or serialize the entire resume with an equivalent durable per-entry guard and re-read status under it. Return 409 for the losing attempt and the persisted type for the successful response. Test overlapping resumes with opposite choices, pausing one until after the other's activation; assert the winning 201, private GET and public GET still agree. Keep the sequential provision-failure→retry rule.

2. **BLOCKING — The pending-login ruling is true of merchant login, not of all owner sign-in paths (R1 #3).** `apps/admin/src/http/public-merchant-routes.ts:56–65,158–160,210–220` confirms pending → 401 on merchant login and completed email → 409 `EMAIL_TAKEN`. The retrier's password, settings name and country defaults really are applied (`apps/admin/src/merchant-onboarding/merchant-onboarding.ts:134–139,150–165`). But A:19–20 also says a pending store **cannot be signed in to**. The separate native staff sign-in uses the same owner credential and checks roles, not directory activation (`apps/admin/src/http/public-staff-auth-routes.ts:47–55,75–81`; `apps/admin/src/interfaces/staff-auth.admin-controller.ts:65–76,96–125`; `apps/admin/src/composition.ts:1615–1631`). The tenant lifecycle gate is not that check: a new tenant starts active, and availability reads the tenant's status, not its owner's directory status (`services/tenancy/src/domain/tenant.ts:37`; `services/tenancy/src/composition.ts:178–182`; `apps/admin/src/http/server.ts:150–159`). There is a real failure window after credential provisioning but before directory activation; the existing trial-failure test exercises that stage (`merchant-onboarding.test.ts:231–249` beside the orchestrator). **Fix:** enforce the pending-owner restriction at the shared staff authentication boundary, matching the owner **and shop** without blocking non-onboarding staff, or defer usability of the owner's credential until activation. Require both login surfaces to deny a provisioned but still-pending owner and to allow that owner after activation. This is not an objection to using the retrier's choice while pending.

3. **BLOCKING — Ordinary repository writes have two conflicting contracts (R1 #1/#5).** A:12–15,85–89 says only `recordSignupSiteType` writes the type, but A:152–153 expressly requires ordinary `save` to **create** a `lead_site` from its argument. An upsert takes the create branch on an absent row (`services/tenancy/src/infrastructure/prisma-repositories.ts:274–288`); settings legitimately have no row until first save (`services/tenancy/src/application/store-settings.use-cases.ts:47–51`). A:97–98 also presents whatever `modify` returns. Returning `change(current)` after a concurrent signup write can report `store` even when the database preserved `lead_site`; the existing save discards Prisma's returned row. **Fix:** omit `siteType` from ordinary Prisma create **and** update data, letting the DB default handle insert; mirror that in memory. Map the row actually returned by `modify`'s upsert, not the pre-write value. Test an absent-row ordinary save carrying `lead_site` → persisted `store`, and an interleaved ordinary modify → returned type equals persisted type. The dedicated signup writer's minimal create is otherwise feasible: all other columns default or are nullable (`packages/db/prisma/schema/tenancy.prisma:79–89`).

4. **BLOCKING — A1's dependency migration and A2's HTTP test setup omit real call sites (R1 #2/#5).** A:97–106,163–165 specifies the harness and new controller dependency. Besides that harness, `services/tenancy/src/application/store-settings.use-cases.test.ts:93–95,110–114,129–133,140–144` passes fresh object literals containing `unitOfWork`; production does so at `services/tenancy/src/composition.ts:157–164`. Those extra fields do not typecheck against the new constructors, and removing them leaves unused declarations/imports (`services/tenancy/tsconfig.json:2–4`; `packages/tsconfig/base.json:16–17`). Separately, A:225–227 says to seed via the tenancy controller, but `apps/admin/src/http/store-settings-routes.test.ts:32–66` returns only Fastify. `apps/admin/src/http/server.ts:116–127,183–200` builds its own admin graph; a separately wired in-memory controller seeds a different repository. **Fix:** list all constructor edits, remove now-unused test UoWs, keep the shared UoW for unrelated tenancy use cases, and change the HTTP acceptance case to sign up a `lead_site` in the existing multi-tenant HTTP harness (`apps/admin/src/http/merchant-onboarding-isolation.e2e.test.ts:200–218,240–249`). With its token, send a valid settings PUT plus `siteType: "store"`, then read it back. Alternatively inject the _same_ backing repository into both sides. Preserve the exact HTTP key checks, including `store-settings-routes.test.ts:232,284`.

5. **BLOCKING — A4's correct null behavior contradicts two existing test oracles (R1 #7).** A:287–301 correctly separates an old successful response with no field (`store`) from an unreadable response (`null`, theme/domain only). But `apps/admin-web/src/components/dashboard/setup-guide-section.test.tsx:119–125,135–142` still expects “0 of 5 tasks complete” both on all-fetch failure and on unauthorized settings. Theme is untracked; domain is the only tracked shared step (`apps/admin-web/src/lib/dashboard/setup-guide.ts:38–47`). **Fix:** explicitly replace **both** assertions with “0 of 1 tasks complete”, assert no commerce links, and retain no Dismiss on unauthorized. Keep the single shipping-fetch failure at lines 127–133 at 0 of 5: settings still resolve successfully there. Keep existing dismissal/completion visibility rules (`setup-guide.ts:50–57`).

6. **BLOCKING — The 48-hour lead claim still expires inside a live session (R1 #8).** The arithmetic at B:368–374 is right: from `2026-11-20T10:00:00Z`, the checkpoints are **172799** and **172800** seconds. The second expected outcome is wrong for an active `s-1`. `packages/tracking/src/collector/collector.ts:126,179–189` reissues the same ID on every request with a fresh 30-minute expiry. Regular page views can keep it alive beyond 48 hours without making any further lead claims. B:296–314 and Spec:60–62 prescribe one fixed `SET NX EX` and no refresh on activity. The claim expires; the session does not. **Fix:** tie the emitted flag to the resolved session's sliding lifetime. For example, expose an atomic claim plus a refresh-if-present operation and require the collector/lead route to extend retained flags on every session renewal (never create a claimed flag on a page view). Specify the hook in the handoff. Test activity less than 30 minutes apart across the 48-hour boundary → second form saved, same ID **suppressed**; genuine inactivity and a new ID → **emit**. Retain tenant isolation and concurrent first-claim tests.

7. **BLOCKING — Several verification steps are still not runnable as printed (R1 #14).** A:238–239,275,311 uses bare `--filter … typecheck` or just the storefront script name. B:137–138,267 contains the literal command prefix `…`. Bash cannot execute either prefix. This is not a package-name problem: `apps/storefront/package.json:2,11`, `apps/admin/package.json:2,14`, `apps/admin-web/package.json:2,12`, `packages/tracking/package.json:2,14` and root `package.json:21` confirm the targets. **Fix:** give each missing gate its own executable line, following the working pattern, e.g. `cd 'F:/New folder/morbeh-lead-site' && node C:/Users/Abdo/AppData/Local/node/corepack/v1/pnpm/11.9.0/bin/pnpm.cjs --filter storefront typecheck`. Repeat literally with `@platform/admin`, `admin-web` and `@platform/tracking` where needed. Referencing an earlier _complete_ command for a rerun is fine.

8. **OPTIONAL — Make B1's canonical-phone guard explicit for malformed default country codes (R1 #12).** B:69–78 rejects an international result starting with zero, but the national branch only requires nonempty country digits. With default `020` and national input `01012345678`, that branch produces a result beginning `+0`, which B:163,169 then treats as E.164. The existing normalizer also explicitly rejects an empty digit string and an empty subscriber (`packages/tracking/src/pipeline/normalization.ts:45–58`). **Fix:** preserve those guards, reject default country codes starting with zero, and add discriminating unknown-country boundary rows for 7/8/15/16 total digits. No change to the valid EG/Gulf examples or existing pipeline assertions is needed.

9. **OPTIONAL — Narrow the “no runtime path changes” claim (B:13–15).** The new platform-key builder and event-ID helpers are unwired, but B:55–78 changes the shared `normalizeIdentity` inputs to the _existing_ sender. `packages/tracking/src/runtime/delivery-runtime.ts:215–226` calls the normalizer before `hashIdentity`. Raw traffic therefore gets the new phone/name normalization immediately. **Fix:** say “no ingest, fallback or sender-wiring changes; shared normalization changes take effect in the current delivery path.”
