Specify conversion using the existing `currencyExponent`, `toMinorUnits`, and `fromMinorUnits` exports in `apps/admin-web/src/lib/products/money.ts:1–51` (including excess-precision and safe-integer checks) and display through `formatCurrency` in `lib/format.ts:11–18`. ### R2 — BLOCKING — Task 3: GET helpers discard the promised unavailable discriminator

### R3 — BLOCKING — Task 2: list and count require different bind arrays

- **Plan quote:** L149 returns `{ listSql, countSql, params }`; L151 says “`countSql` = same FROM/WHERE without cursor/limit”; L152 runs “both ... `client.$queryRawUnsafe(sql, ...params)`”.
- **Code evidence:** `packages/db/src/transaction.ts:4,67–72` supplies the actual Prisma transaction client, not a query wrapper that trims parameters. The installed generated Prisma `index.d.ts:986` declares `$queryRawUnsafe(query: string, ...values: any[])`; `services/orders/src/infrastructure/prisma-sales-summary-query.ts:97–124,178–188` constructs each statement with its own bound values. The planned list always adds a bound limit and optionally a cursor that the planned count does not reference. Sending that same complete array to count is not a valid statement/parameter contract.
- **Concrete fix:** Return two explicit compiled statements, e.g. `{ list: {sql, params}, count: {sql, params} }`; compile shared filters first, clone their parameters for the list, append cursor/limit only there, and execute each with its OWN array. Specify a no-database recording TransactionClient fake (records `set_config` before queries; queued raw answers; no mutation) that asserts exact SQL/array correspondence for page 1, page 2, filtered search and no results. Keep the count independent of the cursor and test `total` unchanged between pages. No PostgreSQL reproduction is claimed here; this is a static contradiction in the prescribed interface.

### R4 — BLOCKING — Task 2: specify zero-order and NULL comparison semantics in predicates, not just output

- **Plan quote:** L151 uses `LEFT JOIN oa` and conditions on its aggregate; L100 defines `default:not_purchased` as `orders_count eq 0`. L171–172 requests fragments and broad field cases without no-order numeric expectations.
- **Code evidence:** `packages/db/prisma/schema/orders.prisma:5–33` has no order row for an unpurchased customer, so a grouped CTE cannot produce that customer's aggregate row. The survey's `COALESCE(oa.orders_count,0)` is only in the SELECT sketch (`w1c/survey-segments.md:249–263`); it does not settle WHERE predicates. The real sales summary explicitly supplies zero aggregates (`services/orders/src/infrastructure/prisma-sales-summary-query.ts:99–112`), and the customer table allows `language = NULL` (`packages/db/prisma/schema/identity.prisma:12`). A direct `oa.orders_count = 0`/`oa.spent_minor = 0` silently excludes the very customers the default must include.
- **Concrete fix:** Bind numeric conditions AND member DTOs to `COALESCE(oa.orders_count,0)` / `COALESCE(oa.spent_minor,0)`; preserve `last_order_at = NULL`. State whether language `neq` includes unset (choose one, with its exact SQL); state NULL behavior for each negative/date operator. Add exact fixtures: no orders, cancelled-only, other-currency-only → count 0/spend 0/last null and membership in `not_purchased`; refunded-only in shop currency → count 1/spend 0/dated last order. Cover amount `eq 0`, `lte 0`, and language unset/neq. This does not change D8–D11.

### R5 — BLOCKING — Task 2: the prescribed tenant-filter count is not a per-alias isolation proof

- **Plan quote:** L171: “every table alias ... (assert by counting occurrences of `"tenant_id" = $1` ≥ number of table references)”; L172: “seeded two tenants ... tenant B rows never returned”.
- **Code evidence:** `packages/db/prisma/schema/orders.prisma:9,37–39,58–65` stores bare `customer_ref` and child FKs that do NOT include `tenant_id`; `packages/db/prisma/schema/identity.prisma:29–40,60–90` likewise has tenant columns but customer FKs on ID alone. Extra predicates on one alias can make a global count pass while another alias has no tenant filter. Disjoint tenant-A/B parent IDs also let the base customer predicate hide a missing order/consent/tag/address/event predicate. The sales-query counting test (`services/orders/src/infrastructure/prisma-sales-summary-query.test.ts:61–70`) is a precedent, not proof that this stronger multi-context query is isolated.
- **Concrete fix:** Check each concrete table occurrence/alias has its OWN bound tenant predicate in BOTH list and count, including item fallback and each separate event/consent subquery; do not substitute a total occurrence count. Add adversarial fixtures: B order references A customer; B event references A order; B consent/tag/address points at A customer, with values that would flip an A membership if the per-alias predicate were absent. Assert A counts/spend/consents/filters remain unchanged and B results stay absent; add missing-predicate mutation checks or an equivalent oracle that would fail for each alias. All execution stays gated to an explicitly disposable test DB.

### R6 — BLOCKING — Task 1: count-then-save in a transaction does not enforce the stated per-tenant cap

- **Plan quote:** L92: “`MAX_CUSTOM_SEGMENTS = 100; // per tenant`”; L119: “then in one UoW: `count ≥ 100` → ...; save”.
- **Code evidence:** `packages/db/src/prisma-repository.ts:34–43` delegates to `runInTransaction`; `packages/db/src/transaction.ts:15–23` supplies no serializable isolation or lock. At 99 segments, two different-name creates can both observe 99 and both insert; the new unique `(tenant_id,name_key)` index does not conflict. A transaction alone is not serialization of this tenant-wide invariant.
- **Concrete fix:** Specify a repository/port operation that serializes segment creation per tenant inside the SAME UoW before count and insert (e.g. an infra-owned tenant-keyed advisory transaction lock), or an explicit serializable/retry mechanism. Keep Prisma/SQL out of application code. Define memory semantics and add a gated concurrent test at 99: two different-name creates yield one success/one BUSINESS_RULE and final count 100; tenant B's capacity remains independent. If the cap is intentionally best-effort, change that requirement explicitly instead of claiming a hard maximum.

### R8 — BLOCKING — Task 1: settle persisted versions and memory snapshot semantics

- **Plan quote:** L102: “`version` from `AggregateRoot`”; L110: `save(...): Promise<void>` with “bump”; L114: memory has “same semantics incl. ... version check”; L120: update returns `{ segmentId; version }`.
- **Code evidence:** `packages/domain/src/shared/aggregate/aggregate-root.ts:13–22` makes `_version` private AND readonly; it does not change after `save`. `services/identity/src/infrastructure/prisma-customer-repository.ts:48–75` increments the DB version, not the input object's version. The existing memory customer repository stores/returns the SAME aggregate reference (`in-memory-customer-repository.ts:39–56`) and does not bump/reconstitute it; it is not a valid CAS template for the new segment repository. Returning `segment.version` after the planned void save returns the old token, and retaining references lets a rejected stale mutation alter stored state before CAS.
- **Concrete fix:** Explicitly prescribe create version 0 → persisted 1, update snapshot v → persisted v+1, never mutate AggregateRoot's readonly version. Return the successful persisted token (`expectedVersion + 1` after save, or a tx read-back) and have memory persist immutable snapshots and return fresh reconstituted aggregates. Add parity tests: create/get v1; update expected1→response/get v2; second update expected2→v3; two separately-loaded v1 objects, one wins and the stale one's save fails without changing stored name/conditions. Do not copy memory CustomerRepository's reference semantics.
