## Findings

1. **BLOCKING — A1 steps 2, 4–5: two first choices can both win, and a settings route can undo a choice without accepting `siteType`.** A:151–155 specifies read/null-check/save; `services/tenancy/src/infrastructure/prisma-repositories.ts:267–288` reads ordinarily and unconditionally upserts the whole mapped row. General Save and Dismiss both take snapshots (`services/tenancy/src/application/store-settings.use-cases.ts:74–79,99–105`). The CHECK enforces membership, not immutability. Two pending resumes can each return `changed:true`; a stale settings save can even restore `store/null`. **Fix:** add a tenant-keyed atomic first-choice operation to `services/tenancy/src/domain/repositories.ts:42–46` and both adapters. Handle the absent row and conflict cases; update only an unchosen row and return the *persisted winner* to both callers. Never include either choice column in an ordinary settings/dismiss update; read back the persisted value for the response. Define eligibility so migrated existing stores are not treated as new sign-ups just because their timestamp is null. Test competing choices (exactly one `changed:true`, same winner and first timestamp), and a paused ordinary save/dismiss completing after the claim (choice and timestamp unchanged).

2. **BLOCKING — A1 step 4: the specified transaction lacks the new shop's RLS scope.** `services/tenancy/src/composition.ts:211–214` supplies `PrismaUnitOfWork`; `packages/db/src/prisma-repository.ts:34–43` calls unscoped `runInTransaction`. Passing that transaction makes the settings repository skip its own tenant wrapper (`prisma-repositories.ts:249–257,283–288`). The table's forced policy checks `app.tenant_id` on writes (`packages/db/prisma/schema/migrations/20261013000000_store_shipping_taxes/migration.sql:19–24`). In-memory success does not prove production sign-up works under the enforcing role. **Fix:** run the choice and onboarding settings work under `runInTenantTransaction(prisma, shopId, ...)` or an equivalent per-call scoped port (`packages/db/src/transaction.ts:41–55`); do not substitute the platform tenant. Add a Prisma-adapter assertion that scope is set to the shop before reads/writes, plus a two-shop isolation case. No real DB migration is needed to review or implement the adapter.

3. **BLOCKING — A2 steps 1, 3: a retry can replace the choice submitted on the original sign-up.** A:201–205 places the claim after settings and stubs the retry result. In reality the pending directory entry survives a provisioning failure *before* that point and stores no choice (`apps/admin/src/merchant-onboarding/merchant-onboarding.ts:33–38,131–163`); the existing test already exercises that failure (`merchant-onboarding.test.ts:200–228`). Thus first request `lead_site`, provision fails, retry `store` produces `store`. **Fix:** durably bind the original choice at the same commit that makes onboarding resumable (e.g. atomically record pending ownership and choice, or store immutable original intent with the pending record and use it on resume). A separate call with a crash window is insufficient. Run that existing failure path with opposite choices and real in-memory persistence. Require `lead_site` in settings and the created response; warn only on an actual mismatch, not on an identical retry.

4. **BLOCKING — A1/A2 interface and response assembly: `AdminResponse` is the wrong tenancy-layer type, and the port is not a void port.** Tenancy uses `ControllerResponse`/`present(result, 200)` (`services/tenancy/src/interfaces/tenancy.controller.ts:48,107–112`; `interfaces/presenter.ts:4–7,20–27` relative to that service's `src`). `AdminResponse` belongs to `apps/admin/src/interfaces/admin-response.ts`. `expectSuccess` returns **void** and `body` is `unknown` (`apps/admin/src/composition.ts:1559–1563,1602–1606,1629–1631`). The route constructs two independent 201 bodies and copies neither arbitrarily from the outcome (`apps/admin/src/http/public-merchant-routes.ts:164–185`). **Fix:** name `Promise<ControllerResponse>` on the raw tenancy controller only; have the onboarding closure check status, narrow/read `{siteType,changed}` and return it. Extend only the `created` outcome; include its recorded `siteType` in **both** 201 bodies. Test token and `signInRequired` branches, including a result different from the submitted choice; update the stub and exact-body assertion at `public-merchant-routes.test.ts:272–297`.

5. **BLOCKING — A1 steps 1–3, 6: the prescribed harness and regression expectations cannot pass as written.** `services/tenancy/src/application/store-settings.use-cases.test.ts:12–20` returns `{settings,get,update,publicStore}`, not the unbound identifiers at A:111–139; its existing exact comparisons at lines 35–46,76–87 exclude `siteType`. The Prisma fixture at `services/tenancy/src/infrastructure/prisma-store-settings.test.ts:41–52` lacks the new fields, so strict mapper validation will reject it. The real admin HTTP assertions also require the *old* exact read shape (`apps/admin/src/http/store-settings-routes.test.ts:97–139`), outside A1's test command. **Fix:** specify a fresh named harness and fixed clock per test, assert the stored timestamp after claim, retry, save and dismiss, add a valid row plus the corrupt `"shop"` case in a named mapper/adapter test, and update exact view and HTTP expectations rather than weakening them. Exercise a crafted post-sign-up `PUT /store/settings` attempting both choice fields, then GET and confirm neither changed; keep the existing write allow-list (`store-settings-routes.ts:5–11,30–46`). Include both packages' affected tests in the gate.

Keep write/dismiss permissions unchanged. Add component tests for a public `lead_site` with private settings unauthorized and the store case, and update required fixtures in `apps/admin-web/src/components/dashboard/setup-guide.test.tsx:33–43` and `src/lib/dashboard/setup-guide.test.ts:4–18,57–65,115ff`. 8. **BLOCKING — B3 steps 1, 3: the lead claim times out while the same collector session is still active.** `packages/tracking/src/collector/collector.ts:179–189` reissues `morbeh_sid` on **every** request; `collector.test.ts:153–176` tests the sliding lifetime. B:301–305 explicitly requires another emission for the *same* ID 30 minutes after the first claim. Submit at 10:00, page view at 10:25, submit at 10:31: that cookie is still live, but the proposed ledger emits twice. B:270,310–313 also allows every submission missing a cookie to emit without establishing a session. **Fix:** bind suppression to the resolved collector session, not elapsed time since first lead. Specify how the emitted flag survives every session refresh (including page views), how a new/missing cookie is minted and returned before deciding, and that production claims are atomic across concurrent submits. Change the contract/test to require a resolved session. Test the timeline above → `emit,suppressed` for the two submissions; after 30 minutes of inactivity, a **new cookie ID** → `emit`; two concurrent claims for one session → one emit. Suppression applies only to forwarding, never saving the second lead (Spec:14–16).

9. **BLOCKING — B3 ID validation: the producer and validator accept different languages.** B:250–255,269–270 rejects reserved business refs in the factory, but the proposed regex accepts `lead_undefined`, `ord_NULL`, `cnl_NA` and `mb_x`. Spec:38–41 specifies `mb_<uuid>`, and the ingest boundary accepts untrusted collector fields (`packages/tracking/src/collector/collector.ts:281–294`). `newBrowserEventId` has an injected arbitrary string supplier. **Fix:** share the business-ref predicate between generation and recognition; separately validate canonical browser UUIDs, preserving the stated lowercase factory output. At the ingress boundary distinguish absent `undefined` from the literal string `"undefined"`; reject present empty, malformed and non-string values as `dedup_id_invalid` without throwing or echoing the value. Test the examples above, `null`, an otherwise valid business ID, a generated browser ID and a real 64-lowercase-hex legacy ID. Mark the new refusal permanent.

10. **BLOCKING — B3 steps 2–4: removing the fallback before migrating producers dead-letters currently accepted traffic.** `apps/collector/src/collector-endpoint.test.ts:72,131–148` explicitly expects a session-bearing page beacon with **no** `dedupId`. `packages/tracking/src/runtime/ingest-runtime.ts:123–132,166–182` currently supplies its ID; `apps/runtime/src/tracking/tracking-ingest.ts:148–170,173–191` handles refusals. Do not revive minute buckets or generate an independent random ID at ingest. Pin missing-ID purchase/delivery/cancel behavior and legacy replay separately. Test collector → ingest: two page occurrences in the same minute have different IDs, retry is stable, producer-supplied ID survives, order copies agree. Remove the test import at `envelope/tracking-schema.test.ts:17` as well as its case; remove the now-unused **private** time parameter (`ids/dedup-id.ts:44,77`) without breaking the public input/remaining strategies (`packages/tsconfig/base.json:16–17`).
