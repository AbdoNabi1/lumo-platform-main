### BLOCKING 6 — Tasks 1–2: the reorder-only 500-ID cap makes larger valid collections uneditable

**Plan L90,132,173,176:** reorder accepts `productIds: uuid[] (max 500)`, while both the amended UI and domain require the complete permutation. The add route has no membership cap. **Evidence:** `services/catalog/src/domain/collection.ts:68–75` appends without a maximum, and `:89–98` rejects anything other than an exact permutation. `services/catalog/src/application/add-product-to-collection.use-case.ts:53–68` likewise imposes no collection-size bound; `reorder-collection-products.use-case.ts:51–62` passes the whole array to that invariant. A collection can reach 501 members through the planned API, after which every valid Move request fails transport validation and every truncated request fails the domain invariant.

**Fix:** remove the arbitrary 500-element limit from the reorder schema (retain UUID validation and the shared HTTP body-size limit), or settle and consistently enforce a real membership-size limit across all producers and existing collections. Add a regression oracle using 501 unique member IDs: a full valid reorder succeeds; missing/duplicate IDs still fail exact-permutation validation. The first option needs no catalog-domain change and fits this wave's scope.
