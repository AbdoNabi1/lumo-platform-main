## Findings

1. **BLOCKING — Task 2's mandated Prisma fake cannot execute the mandated query suite.** Plan lines 400–411 require `OR`, case-insensitive `contains`, descending `orderBy`, and rerunning the pagination/search use-case suite against `createFakePrisma()`. The real fake explicitly throws for `OR` (`packages/db/src/testing/fake-prisma.ts:56–60`), has no `contains`/`mode` operators (`:29–53`), and ignores `orderBy` (`:116–120`); it also exposes only `database` and `rowsOf`, not the claimed recorded-call log (`:136–140,158–168`). This cannot pass as printed. **Fix:** explicitly add a scoped test-double task/file and define its supported query/sort semantics and call recording (or extend the shared fake with regression tests). Specify how `$executeRaw` and delegate calls are spied so tenant-before-query assertions are real. Do not weaken the search/pagination tests or filter/sort production rows in memory to appease the fake.

2. **BLOCKING — The promised 503 for shop-facts failure is actually 500.** Plan lines 461–463 say to throw on a non-200 tenancy response and rely on transport mapping for 503. `packages/http/src/error-mapping.ts:20,28–31` maps only an error with code `UNAVAILABLE` to 503; an ordinary thrown `Error` maps to 500. **Fix:** name the exact error/envelope contract for this adapter (e.g. `AppError` with `{ code: "UNAVAILABLE" }`, caught/mapped at transport), handle rejected tenancy reads as well as non-200 responses, and test 503 with no insert/claim on both paths. Keep error details/PII out of the response.

3. **BLOCKING — Task 5's response type erases the validation envelope its action must consume.** Plan lines 662–671 declare `createLead` to return only `CreateLeadResult | null`, while lines 699–702 require reading `fields[].field` from a 422 body. The real `postItem<T>` deliberately returns parsed non-2xx bodies under its generic type (`apps/storefront/src/lib/runtime-api.ts:305–315,327–330`); it does not magically supply a typed error union. **Fix:** define a response union discriminated by status, or return `body: unknown` and provide explicit success/error-envelope guards. State malformed/null 201 handling (network, no sent cookie), and test both real 422 envelopes and malformed bodies rather than casting a success DTO into an error.

4. **BLOCKING — D1's sent marker can expire during the same still-active session.** Plan lines 28–38 promise suppression for the whole sliding session without Redis renewal, but Task 5 lines 699–700 set `morbeh_lead_sent` for a fixed 86,400 seconds, and lines 654–656 renew only `morbeh_sid` on activity. A visitor active for more than a day keeps the same sid, loses the marker naturally, and the unextended 1,800-second claim is already gone; the next valid submission emits again without cookie deletion or a new session. The actual ledger expires at `now >= storedAt + ttl*1000` (`packages/tracking/src/leads/lead-emission.ts:61–66,71–76`). **Fix:** keep the chosen cookie-plus-claim design, but slide the matching HttpOnly sent marker with the sid on every matched request, and clear/ignore a marker for a different sid. Add a cookie-jar/clock test that renews activity across 30 minutes and across 24 hours and still suppresses; inactivity/new sid emits. This is a correctness repair to D1, not a request to restore collector-side Redis renewals.

5. **BLOCKING — Task 3 ambiguously selects the wrong IP source and explicitly permits losing the cap.** Plan lines 498–500 say `context.ip`, but route handlers already call their transport context `context`: that IP is Fastify's caller (the storefront server), not the visitor (`packages/http/src/route.ts:19–23`; `packages/http/src/server.ts:552–559`; `apps/admin/src/http/public-online-store-routes.ts:60–63`). The visitor IP is instead `body.context.ip` in lines 477–482. Copying the printed name would share a five-submit bucket across a shop's visitors. Also, “no limiter configured → skip” abandons D2's per-shop cap, the stated bound on forged spam/IP signals; the named unlock template fails closed when absent (`apps/admin/src/http/public-online-store-routes.ts:40–55`). **Fix:** explicitly bind `tenantId = context.tenantId`, `visitorIp = body.context.ip`, and name both exact keys from those values; do not fall back to transport IP. Require the limiter, or return 503 when absent. Keep D2's acknowledged forgery limit rather than inventing a new authentication requirement. Test two visitor IPs behind one transport IP, null visitor IP, tenant-separated buckets, the 61st shop submission using distinct IPs, and missing/throwing limiter paths.

6. **BLOCKING — Public-route idempotency permanently snapshots transient limiter refusals.** Plan lines 464 and 498–500 combine `idempotent: true` with handler-returned 429/503. The actual transport snapshots _every_ returned handler response for 24 hours, saves only status/body, and replays before entering the handler (`packages/http/src/server.ts:136,562–592`). Copying `limiterUnavailable` therefore makes the same key keep answering 503 after Redis recovers; a cached 429 also loses `retry-after`. This was reproduced by executing the committed `executeRoute` function: first 503, retry 503, handler called once. **Fix:** specify a lead-route-compatible idempotency policy: successful 201 saves replay exactly once, transient 429/503 responses are not stored and release the claim, and replayed responses retain required headers. Name the transport changes/tests if implementing a per-route cacheability option, or a route-local idempotency wrapper if avoiding a shared policy change. Do not just remove idempotency. Test success replay, concurrent same-key requests, recovery with the same key after limiter failure/window expiry, and no second saved row after a successful replay.

7. **BLOCKING — Task 1 depends on a helper and a type it does not make available.** Plan lines 286–288 require `toLatinDigits`, but it is exported only from `packages/tracking/src/pipeline/normalization.ts:31–37`, not from the public barrel (`packages/tracking/src/index.ts:152–164`), and the package exposes only `"."` (`packages/tracking/package.json:7–9`). A deep import is not a supported package API. Also line 291 requires `prisma?: Database` while lines 102–107 omit `@platform/db` until Task 2 line 343. **Fix:** explicitly add/export `toLatinDigits` from tracking in a named task (with its public-API test), or specify a local pure search-digit helper; do not leave an implementer to choose an unsupported import. Either add the DB type dependency in Task 1 or defer the Prisma option/type to Task 2. Spell out `services/leads/src/index.ts`'s exports used by Task 3 (`wireLeads`, wiring types, `LeadsController`, `LEAD_STATUSES`, `LeadStatus`, `ShopFactsPort`, and DTO/input types), rather than relying on copying wishlist's different public surface.

8. **BLOCKING — Task 3's named server harness cannot prove its required tests without an explicit fixture change.** Plan lines 511–519 refer to the `server.multi-tenant.test.ts` harness and seeding via `settleSignupSiteType`. That harness is file-local, uses a cache that always misses and a key store that always grants (`apps/admin/src/http/server.multi-tenant.test.ts:21–31`), and supplies no real access-control adapter (`:46–54`); `createAdminHttpApi` defaults to `AllowAllAccessControl` (`apps/admin/src/http/server.ts:136–139`). It cannot prove one saved row on replay or viewer 403. `settleSignupSiteType(tenantId, siteType)` is deliberately in-process only (`services/tenancy/src/interfaces/tenancy.controller.ts:116–118`), not an HTTP seeding endpoint or a method on the guarded admin facade. **Fix:** name a new/shared leads HTTP harness and its producer contract: persistent response-cache/atomic claims, `RoleTableAccessControl`, multi-tenant claims for A/B in the same app, active tenant gate, and an exact shared-store seeding path (e.g. a fake Prisma store shared by `wireTenancy` and the HTTP app, settled before boot). The existing `apps/admin/src/http/testing/online-store-harness.ts:85–135` is a closer cache/RBAC template, but needs the tenant/seed extensions stated explicitly. Assert replay by counting inserts and test forged `x-tenant-id` against verified A claims. Do not add a public site-type mutation to make the test convenient.

Add tests for ok, conflict/validation/forbidden API responses and an unavailable/lost response, not only success. Specify the exported API/action signatures and DTOs in this task, including `changeLeadStatus`'s exact `{ status }` body and `FormState` return, so the UI cannot accidentally inherit reviews' `{ toStatus }`/`transitions` contract (`apps/admin-web/src/lib/api/reviews.ts:175–185`).
