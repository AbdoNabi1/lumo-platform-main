# Cash on Delivery — Design Spec

**Status:** Approved by product owner (2026-08-24), ready for implementation planning.
**Author:** Claude (this session), in collaboration with the product owner.
**Relationship to prior work:** builds directly on `docs/superpowers/plans/2026-08-22-critical-remediation.md` Phase 4 (C-2, "Checkout creates the order"), specifically closing the `C1` gap that phase's final review left open _for the Cash on Delivery path only_ — see "Relationship to C1" below.

---

## Problem

The product wants Cash on Delivery (COD) as a real, selectable payment method during checkout. Today, `services/payments`' `PaymentProvider` abstraction (`packages/contracts/src/payment-provider.ts`) assumes every payment method goes through an online PSP: `createIntent → capture`, confirmed asynchronously by a webhook. COD has no PSP, no webhook, and no online authorization step at all — the courier collects cash physically at delivery. Bolting COD onto the `PaymentProvider` interface as a fake "always-succeeds" provider would misrepresent what actually happened and is explicitly rejected by this design.

Separately, Phase 4's final review found that **no order created via the checkout flow (`CreateOrderFromCheckout`) ever reaches a "paid" status** — not even for card payments. The domain method `Order.completePayment()`, despite its own doc comment calling it "the ONE authoritative payment completed path" used by both the legacy and checkout/full lifecycles, only raises the `OrderPaid` domain event (topic `orders.order.paid`) when the order is on the _legacy_ `placed` lifecycle. For the checkout/full lifecycle it instead raises a plain `OrderTransitioned` event (topic `orders.order.payment_received`) — a real, independent bug, not something this design invents. The four consumers built in Phase 4 Task 17b (Finance ledger posting, Loyalty points, Customer 360 profile update, Notifications order-confirmation) all subscribe to `orders.order.paid`, so none of them have ever fired for a checkout-created order.

## Decision, made with the product owner

1. **COD marks the order "paid" immediately at checkout completion**, not when the courier later collects cash. This is a deliberate simplification the product owner chose explicitly (see alternatives considered below) — "paid" here means "no online payment is outstanding," not "cash physically in hand." If a future need arises to track actual cash collection as a separate real-world event, that is a new, later design.
2. **This design fixes the underlying `completePayment()` bug** (item above) as part of closing the loop for COD, because without that fix COD orders would reach `payment_received` but still never raise `OrderPaid`, and Task 17b's consumers would still never fire.
3. **Card payments are explicitly out of scope.** Making a card-paid order reach "paid" for real requires Checkout to receive a genuinely captured payment reference back from Payments before completing — infrastructure that does not exist anywhere in this codebase today (`CheckoutSession` has no method to record a captured payment reference; `generatePaymentIntentRequest()` is a one-way DTO export with nothing feeding a result back in). Building that is Phase 5-sized work (a real public checkout + payment-confirmation flow). This design does not touch it. Non-COD/undefined payment selections leave the order exactly as they behave today (status `created`, unresolved) — fully backward compatible.
4. **No COD business rules for now** — no amount cap, no currency/country restriction, no COD surcharge. If the product later wants limits, that's a small, additive follow-up (e.g. admin-configurable), not part of this design.
5. **Alternatives considered and rejected** for the "when is a COD order paid" question: (a) an explicit "cash collected" action tied to a fulfillment/delivery step, and (b) automatically triggered by `markDelivered()`. Both were rejected by the product owner in favor of (3) above — the simpler, immediate-at-completion model — with the explicit understanding that "paid" is a simplification, not a literal claim that cash has changed hands.

## Relationship to Phase 4's `C1` finding

Phase 4's final review found the create→paid gap and _deliberately left it open_, ruling that closing it required a product decision the session could not make unilaterally, and that fabricating a payment reference to force the gap closed would be dishonest — especially since it touches Finance's ledger. That ruling stands for the **card** path. This design is the product decision for the **COD** path specifically: since COD has no real external payment confirmation to wait for, "paid at completion" is not a fabrication — it is what COD _means_ under the model the product owner chose. The regression-pinning test Phase 4 added (`cart-checkout-pricing-security.e2e.test.ts`, asserting a checkout order stays `created` with no `orders.order.paid`) **must continue to pass unchanged for the non-COD case** — this design adds a sibling test for COD proving the opposite, without touching the existing one.

### No changes needed

- `services/checkout/src/domain/value-objects/selections.ts`'s `PaymentSelection` — already a generic `{paymentMethodRef: string, provider: string}`, no schema change. `"cod"` just becomes a valid value flowing through unchanged.
- `apps/admin/src/http/checkout-routes.ts`'s `select-payment` route — already accepts arbitrary provider strings.
- Task 17b's four consumers (`apps/runtime/src/consumers/orders-paid.consumers.ts`) — they already handle `orders.order.paid` generically; COD simply becomes the first real producer of that event they've ever received.

### Data flow (COD happy path)

1. Caller (admin backoffice today; a future public checkout in Phase 5) calls `POST /checkouts/:id/select-payment` with `{paymentMethodRef: "cod", provider: "cod"}`.
2. Caller calls `POST /checkouts/:id/complete`.
3. `CompleteCheckout.execute` builds the `OrderCreationPort.create()` input, including `paymentMethod: {paymentMethodRef: "cod", provider: "cod"}` read from `session.paymentSelection`.
4. `OrderCreationAdapter` maps this through to `CreateOrderFromCheckout`'s input.
5. `CreateOrderFromCheckout` calls `Order.createFromCheckout(...)` (status `created`, as today), then — because `provider === "cod"` — calls, in order: `order.confirm()` → `order.markAwaitingPayment()` → `order.requestPayment("cod", eventId, occurredAt)` → `order.completePayment("cod", eventId, occurredAt)`. `paymentRef` is the literal string `"cod"` — an honest value that says what it is, not a fabricated PSP reference.
6. After the fix above, `completePayment("cod", ...)` raises `OrderPaid` (`paymentRef: "cod"`, real `currency`/`totalAmountMinor` from the order's totals) alongside the `OrderTransitioned` event that same call already raises for the `payment_received` transition.
7. The order — now at status `payment_received`, with five history entries since creation (`created → confirmed → awaiting_payment → payment_requested → payment_received`) — and the six integration events those five `record()` calls raise (one `OrderTransitioned` per step, plus the one extra `OrderPaid` from step 6) are committed atomically in `CreateOrderFromCheckout`'s single existing transaction — no new nested transaction, no new cross-context call from Checkout into Orders beyond the one `OrderCreationPort.create()` call that already exists.
8. The outbox relay (Phase 2 machinery, already running) publishes the events. `orders.order.paid` reaches Finance/Loyalty/Customer 360/Notifications exactly as Task 17b built them to receive it.

Any other or missing `provider` value (a real card provider name, a typo, `undefined`): the order stays at `created`, byte-for-byte the same as today. This is intentionally conservative — only the literal `"cod"` string is special-cased; nothing about an unrecognized provider throws or logs a warning, since a future real provider integration will need its own explicit wiring anyway.

### Error handling

- No payment selected, or a non-`"cod"` provider: no behavior change from today (order created at `created`, `CompleteCheckout` succeeds as it does now).
- Any unexpected error during the COD transition walk (should not happen in practice — every precondition is guaranteed by having just created the order with valid items/addresses/totals) surfaces through `CreateOrderFromCheckout`'s existing `Result`/domain-error handling, same shape as every other failure path in that use case.

## Testing

- **Domain regression test** (new, independent of COD): `Order.completePayment()` on a checkout-lifecycle order transitioning to `payment_received` now raises `OrderPaid`. This is the direct test for the bug fix.
- **Use-case tests** (`create-order-from-checkout.use-case.test.ts`): COD provider → order ends at `payment_received`, `OrderPaid` raised with `paymentRef: "cod"`, outbox contains all five events. Non-COD/undefined provider → today's existing tests keep passing unchanged.
- **E2E**: the existing Phase 4 regression test in `cart-checkout-pricing-security.e2e.test.ts` (checkout order stays `created`, `orders.order.paid` never published) stays valid and untouched for the non-COD case. A new sibling e2e test proves the COD case: complete with `provider: "cod"` → the real order (read back through `OrderController`) is past `created`/at `payment_received` → the drained outbox genuinely contains `orders.order.paid`.
- No changes needed to Task 17b's own consumer tests (`orders-paid.consumers.test.ts`) — they already test against the real event shape; this design doesn't change that shape.

## Explicitly out of scope

- Real card payment capture reaching "paid" (needs Phase 5's public checkout + payment-confirmation flow; tracked as the still-open part of Phase 4's `C1` finding).
- COD business rules (amount caps, currency/country restriction, surcharges).
- Tracking actual cash collection at delivery as a distinct, later event.
- Any change to `packages/contracts/src/payment-provider.ts` or the PSP integration (`packages/psp-stripe`) — COD deliberately never touches the `PaymentProvider` abstraction.
