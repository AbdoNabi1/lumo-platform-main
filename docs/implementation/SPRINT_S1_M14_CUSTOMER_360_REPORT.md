# Phase S1 — Integration Completion — Milestone 14 (Customer 360 Admin Wiring) — Report

**Status:** Complete. Second (and last) milestone of the "Remaining Admin Wiring" continuation
after the original S1 12-item batch + S1.5 Security sub-milestones closed, and after Milestone 13
(Wishlist). Reuses the read-only Analytics pattern (Milestone 10), not the write-heavy
Coupons/Loyalty pattern — Customer-360's admin-facing surface (`Customer360Controller`) is entirely
read-only (`getProfile`/`getIdentityTimeline`/`getJourneyTimeline`/`getJourneyState`).

**Trigger:** the same direct audit that found Wishlist unwired (M13) also found the Customer-360
bounded context (`@platform/customer-360`, committed, working `wireCustomer360()` +
`Customer360Controller`) had zero admin-app exposure — no admin controller, no `composition.ts`
entry, no HTTP route — despite being a fully built, gate-verified context (Session
Stitching/Identity/Profile/Computed Attributes/Segmentation, Phases 6.1–6.5/9). This is a pure
additive wiring gap, not a design or contract change.

---

## 1. Scope

**In scope:** expose Customer-360's four existing read use cases through the admin app via
`Customer360Controller`, replicating the established read-only `*AdminController` →
`composition.ts` → `*-routes.ts` → `admin-routes.ts` pattern used by `AnalyticsAdminController`.

**Explicitly not touched:** `services/customer-360/**` (the context itself — already correct, zero
changes needed; note it exposes far more than these 4 read use-cases internally — identity
merge/split, profile/session/attribute/segment projections and workers — but only the 4 methods
already surfaced on `Customer360Controller` are in scope here; wiring the write-side use-cases
directly was never part of any prior milestone's pattern and would be new admin-surface design, not
pure wiring), any other context's wiring, `apps/runtime`, any public contract/event shape,
Finance M2 / Analytics V2 / Runtime module framework (out of scope per explicit user decision).

## 4. Architecture impact

None. Pure composition-root wiring addition following an existing, established pattern — no new
abstractions, no changed contracts, no cross-context coupling (Customer-360's admin controller
depends only on Customer-360's own `Customer360Controller`, same as every sibling admin controller).
The one real judgment call (excluding `customer360` from the outbox-drain array) follows the
already-established `analytics`/`platformConsole` precedent rather than inventing a new one.

---

## 5. Pattern deviation

**One, disclosed above:** the read-only Analytics pattern was reused instead of the write-heavy
Coupons/Loyalty pattern, because Customer-360's admin-facing controller is itself read-only — this
mirrors the codebase's own existing distinction (compare `AnalyticsAdminController` vs.
`CouponsAdminController`), not a new convention invented for this milestone. The querystring-array
fix (§3) was a compile-error correction to match an existing convention, not a design change.
