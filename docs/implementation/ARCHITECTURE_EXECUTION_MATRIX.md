# Morbeh Platform — Phase A Architecture Execution Matrix

**Status:** Validation only. No code was changed to produce this document.
**Scope:** the 11 Phase A remediation items from `ARCHITECTURE_REMEDIATION_PLAN.md` (§3), re-examined for cross-context blast radius before any implementation sprint starts.
**Method:** 4 parallel read-only investigations traced, for every Phase A item: every bounded context, public API, event contract, DB schema, saga/workflow, downstream consumer, and upstream producer touched — not assumed from the original plan, independently re-derived from the current code. Every claim below is backed by file:line evidence gathered in that pass.
**Purpose:** guarantee that fixing one verified finding does not silently break another bounded context or violate an ADR, and that every Phase A sprint can still be deployed independently once sequenced correctly.

**Headline result: this pass found that three Phase A items — A1, A9, and (jointly) A5/A6a — were scoped in a way that would not have worked, or would have actively broken other contexts, if implemented exactly as written in the original plan.** These are not new findings about the _audit_; they are findings about the _plan itself_. Each is called out explicitly below with the corrected scope. Nothing in this document changes the verdict on any of the 55 original audit findings — it changes how three of the fixes for them must be built.

## 1. Impact Matrix — Per Remediation Item

Each item lists the seven "identify every..." categories the review asked for, followed by the seven required assessment fields (direct impact, indirect impact, breaking-change risk, backward-compat strategy, migration strategy, rollback strategy, test strategy).

### A1 — Payment-truth enforcement _(corrected scope)_

**Corrected fix description:** (a) fix the id-correlation bug so the consumer resolves the real order; (b) route the consumer's payment-truth transition through `AdvanceOrder`'s checkout-lifecycle `transition()` mechanism (`payment_received`), **not** `MarkOrderPaid` — `MarkOrderPaid` stays scoped to legacy `placed`→`paid` orders only; (c) restrict `AdvanceOrder`'s admin HTTP surface (`POST /orders/:orderId/transitions`) so payment-bearing transitions can no longer be caller-asserted with an arbitrary `paymentRef` — this route was entirely missing from the original plan and is a second, independent caller-asserted-truth hole; (d) gate/remove the (HTTP-unreachable, confirmed dead-code) admin `markOrderPaid` action; (e) tighten the client-supplied `pspToken` check in the saga's synchronous-capture fallback. **Do not remove the saga's direct `payment_received` call until (b) is built, tested, and proven to reliably reproduce the same transition** — this must be a cutover, not a deletion-first change.

| Category                 | Findings                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Bounded contexts**     | Orders (consumer, `AdvanceOrder`, `MarkOrderPaid`, repository — needs a new `findByCheckoutRef`-style lookup method touching both Prisma and in-memory implementations plus test doubles), Payments (`CapturePayment`, sole producer of `payments.payment_intent.captured`), `apps/runtime` (saga activities, composition), `apps/admin` (admin controller, admin routes), Finance and Fulfillment (downstream, at risk if (b)/(c) aren't sequenced correctly), `packages/grpc` (a dormant but versioned `MarkOrderPaidRequest` contract already assumes the loose, pre-fix semantics — should be tightened in lockstep or flagged stale). |
| **Public APIs**          | `POST /orders/:orderId/transitions` (admin, must gain a restriction on payment-bearing transitions — **this was not in the original plan at all**); the admin `markOrderPaid` action (confirmed dead code — no route wires to it today, so "removing" it is safe but low-value; the plan's premise that this is the live risk is wrong, the transitions route is); `POST /purchase-saga/submit` (the one real entry point for the `pspToken` tightening).                                                                                                                                                                                  |
| **Event contracts**      | `payments.payment_intent.captured` (single confirmed producer, single confirmed consumer — safe to modify the consumer in isolation). `orders.order.payment_received` (must gain a second legitimate producer path — the fixed consumer — without losing its only current one until cutover is proven). `orders.order.paid` (scope of (b)/(c) changes what triggers it, but confirmed **zero production consumers today** — lower live blast radius than the plan implied, though the dormant gRPC contract and doc-comment claims about Inventory/Notifications consuming it are aspirational, not real).                                 |

| **Downstream consumers** | Finance's `PostOrderPaidJournal` and Fulfillment's `CreateFulfillment`, both subscribed to `orders.order.payment_received` — the two contexts that break completely if the cutover in (b) is done as a deletion rather than a proven replacement.                                                                                                                                                                                                                                                                                                                                                                                          |
| **Upstream producers**   | `PaymentIntent.capture()` is confirmed the sole producer of `payments.payment_intent.captured`, reached only via the saga's synchronous-capture path — correctly scoped, no other producer exists.                                                                                                                                                                                                                                                                                                                                                                                                                                         |

- **Indirect impact:** Finance and Fulfillment (via `payment_received`), the saga's own success/failure reporting accuracy, the dormant gRPC `MarkOrderPaidRequest` spec (becomes further stale unless updated in lockstep).
- **Breaking-change risk:** **High.** This is the highest-risk single item in the entire plan — it sits at the center of the purchase flow and, as this pass shows, the naive version of the fix doesn't work at all.

Only remove it once the shadow period shows zero divergence across a real traffic sample.
- **Migration strategy:** No data migration. A new repository method (`findByCheckoutRef` or equivalent) must be added to `OrderRepository` and both implementations before the consumer fix can be written.
- **Rollback strategy:** Feature-flag the consumer's new transition-based path; on rollback, the saga's direct call (kept alive per the dual-path strategy) continues to function exactly as it does today.
- **Test strategy:** New test asserting a saga-originated order correctly reaches `payment_received` via the consumer, not just an order-id-resolution unit test (the existing `payment-captured.consumer.test.ts` only exercises the legacy `placed`→`paid` path — this gap in test coverage is exactly why the original plan's flaw wasn't caught until this pass). New test asserting `/orders/:orderId/transitions` rejects a caller-supplied `paymentRef` for a payment-bearing transition without independent verification. New test for the saga's success signal staying coupled to the order's real lifecycle state.

### A5 — Postgres-backed webhook/callback idempotency stores _(now sequenced after A6a — see §0.3)_

| Category                 | Findings                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Bounded contexts**     | Payments, Fulfillment, Shipping, Returns, Notifications — all five `buildController` functions currently construct the in-memory store **unconditionally**, called identically from both the Prisma and non-Prisma branches; none of the five currently branch on `deps.prisma` for this specific store, meaning the change shape is "add a new branch," not "swap one constructor." |
| **Public APIs**          | None directly.                                                                                                                                                                                                                                                                                                                                                                       |
| **Event contracts**      | No shape change; reliability/atomicity changes only (see below).                                                                                                                                                                                                                                                                                                                     |
| **DB schemas**           | All five target tables **already exist** with correct unique constraints (`ProcessedWebhook`, `ProcessedCarrierWebhook` ×2 for Fulfillment/Shipping, `ReturnsProcessedCallback`, Notifications' provider-callback table) — no migration needed for the tables themselves.                                                                                                            |
| **Sagas/workflows**      | None of the five stores are touched by the saga or any Temporal workflow.                                                                                                                                                                                                                                                                                                            |
| **Downstream consumers** | None currently compensate for webhook-processing unreliability — meaning nothing is _redundant_ to remove, but also nothing is prepared for the new failure mode below.                                                                                                                                                                                                              |
| **Upstream producers**   | Two composition roots per context (`apps/admin`, `apps/runtime` where applicable) both need the same change — confirmed no third entry point exists for any of the five.                                                                                                                                                                                                             |

**Critical finding (drives the resequencing in §0.3):** in all five use cases, the idempotency `claim()` call happens **outside and before** the entity-mutation transaction, with no shared `tx`. With an in-memory store, a crash between claim and commit wipes both symmetrically (invisible failure). **Once Postgres-backed, the same crash leaves the claim durably committed while the entity mutation is lost** — every future retry of that exact webhook will see `claimed === false` and silently, permanently drop the real transition, with no automatic recovery path. This is exactly the failure class ADR-0005's `tx?` parameter (already implemented in `PrismaProcessedEventStore`, just never used) exists to prevent. **A5 must reuse the same tx-threading mechanism A6a builds**, not ship independently.

- **Direct impact:** all five composition roots, all five use cases' claim-then-mutate sequencing.
- **Indirect impact:** none discovered — zero existing tests exercise any of the five composition roots' Prisma branches today, so there's no regression risk from existing coverage, but also no existing safety net for correctness.
- **Breaking-change risk:** Medium if sequenced after A6a (mechanical, low-risk swap reusing a proven pattern); **High if shipped independently first** (introduces a new silent, permanent data-loss mode).
- **Backward-compat strategy:** Per-context, independently revertible (no cross-context coupling in the swap itself, only in the _timing_ relative to A6a).
- **Migration strategy:** None (tables exist); requires the tx-threading capability from A6a to exist first.
- **Rollback strategy:** Trivial composition-level revert per context.
- **Test strategy:** New integration tests (first-ever) against a real/test Postgres instance for each of the five stores, specifically including a test that simulates a crash between claim-commit and entity-mutation-commit, asserting the tx-threaded version does not lose the transition. Unit test asserting a duplicate claim on an already-processed key correctly no-ops.

### A6a — Atomic consumer idempotency _(corrected: opt-in, not blanket)_

| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**Critical finding (drives the "opt-in" correction):** of the 17 handlers, at least 4 make external network calls with **no DB write to make atomic in the first place**: `TrackingIngestHandler` (vendor delivery HTTP calls, plus its own separate, purpose-different `recordIfNew` call for destination-level dedup — conflating the two would be a design error), `RelationWrittenConsumer`/`RelationDeletedConsumer` (Ory Keto HTTP calls, no DB write at all in the handler), `SessionRevokedAllConsumer` (Ory Kratos HTTP call, no DB write). The 3 already-transactional consumers (Orders/Fulfillment/Finance) and the 5 pure-Postgres Security projection consumers are safe candidates for the atomic path; the 4 external-call handlers are not, ever.

Also confirmed a real ordering subtlety even among the safe candidates: Fulfillment's `CreateFulfillment` consumer calls `notifications.notify(...)` **after** its `unitOfWork.run` resolves, not inside it — correct today, but a naive "wrap the whole `handle()` in one transaction" implementation would pull that call inside an open transaction once Notifications' provider adapter becomes real (A7b), holding a DB connection across a network call. - **Breaking-change risk:** **High if implemented as a blanket change** (breaks 4 working consumers); **Medium if implemented opt-in** (additive capability, existing handlers unaffected until they opt in).
- **Backward-compat strategy:** Opt-in by construction — existing handlers keep working unchanged; only handlers that explicitly adopt the new capability get atomic semantics.
- **Migration strategy:** None (reuses the existing `platform.inbox_processed_events` table and the already-implemented `tx?` parameter).
- **Rollback strategy:** Revert to non-atomic recording — the pre-existing exposure returns, nothing new breaks, since it's opt-in.

## 4. Readiness Note

This pass did not find that Phase A's _targets_ were wrong — every one of the 55 originally-verified findings still stands, and closing all of Phase A is still the correct gate for production readiness. No code should be written from the original plan's item descriptions alone — implementation should reference this document's corrected scope for A1, A5, A6a, A6b, A6c, A6d, A7a, A7b, A8, and A9.
