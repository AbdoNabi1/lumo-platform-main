# Final Architecture Audit — Steps 1–6 (ExecutionTrace, Explanation API, Pipeline Executor, Transformation Metadata, Registry Graph, Documentation Generator)

**Scope.** Production-readiness review of everything implemented across Steps 1–6:
`packages/tracking/src/execution/{trace,trace-builder,explanation,executor,executor-destinations,execution-context}.ts`,
`packages/tracking/src/definitions/{transformation-metadata,registry-graph}.ts`, and the Step 6 extension to
`scripts/governance/generate.mjs`. No new feature was implemented. Every fix below is a correctness, safety,
clarity or hygiene change to code that already existed at the start of this audit.

**Method.** Every file was re-read in full. Dependency-direction claims were verified by direct `grep`, not by
trusting module-doc prose. Public-API claims were verified against the actual barrel exports and cross-checked
against FF-API-01's own compiler-driven surface, not eyeballed. Complexity claims were verified against actual
line spans, not estimated from memory.

### Finding 3.1 — the directory name is ambiguous; the boundary itself is unenforced

**Risk: Medium.** `.dependency-cruiser.cjs` was read in full: it contains **zero** rules scoped to `packages/tracking` internals. `pnpm arch` passing "0 violations" says nothing about any of the four rules above — none of them has a machine-checkable rule backing it. All four hold today purely by manual inspection (this audit). Nothing stops a future change from importing a `*RegistryPort` into `executor.ts`, or `browser/` from reaching into `runtime/`, and `pnpm arch` would stay green throughout.

**Recommended fix (deferred — not implemented in this audit; adding a new dependency-cruiser rule is a new capability, out of scope for a review pass that must not add features):**
A file-scoped forbidden rule such as:

```js
{
  name: "tracking-execution-never-touches-registry",
  from: { path: "^packages/tracking/src/execution/(executor|executor-destinations|execution-context|trace|trace-builder|explanation)\\.ts$" },
  to: { path: "RegistryPort" }, // or a more precise path/name matcher
}
```

would turn this from "true because I checked" into "true because CI checks." Recommended for the next infrastructure pass, not this one.

| `fingerprintTrace`                     | `stripTiming` rebuilds the entire node tree (new object per node) before `canonicalize` digests it, rather than passing a key-filter into `canonicalize` directly. | Opt-in, not called by `execute()` itself — only by replay-verification/tests. O(n) once per explicit call, on traces of a few dozen nodes. Microseconds. Not measurably slow; not touched.                                                                                                                                                                                                                                                                |
| `edgesFrom` / `edgesTo`                | Linear scan of `graph.edges`, not indexed. `reachableFrom`'s BFS calls `edgesFrom` per dequeued node — O(V·E) worst case for one call.                             | Fine at current registry scale (seed data: 9 destinations, 9 mappings; realistic event/parameter counts in the dozens–hundreds). Flagged as a candidate for an adjacency index **if** a consumer starts calling `edgesFrom` in a per-node loop over a registry that grows to thousands of events — not before. | `recordDestinations` sequential loop   | Destinations are processed one at a time, not with `Promise.all`.                                                                                                  | **Not a performance bug — a documented, deliberate tradeoff.** The code comment already explains why: concurrent execution would attribute one shared wall-clock window to every destination's timing section, making the trace's own timing data wrong. Correctness over throughput here is the right call; fan-out concurrency belongs to the queue layer, which owns it across _events_, not within one event's destinations.                          |

## 5. Memory audit

No issue found; nothing changed under this heading.

- **`ExecutionTrace`**: one canonical frozen tree per execution. Carries only `planId`/`planFingerprint`/`eventName` from the plan — small identity strings, not a reference to the plan object itself. Nothing pins the whole `ExecutionPlan` in memory via a live trace.
- **`ExecutionResult`**: `delivered`/`failed`/`excluded` are small derived label arrays _alongside_ `trace`, not a duplicate of its heavy structure — exactly the "derive, don't accumulate" pattern the code's own docs argue for elsewhere.
- **`RegistryGraph`**: built via a `Map` during construction, discarded (GC'd) once `buildRegistryGraph` returns a plain sorted array. Scales with registry size (small, bounded), never with event volume.
- **`ParameterDictionary` / `DependencyGraph`** (pre-existing, unaffected): Registry Graph _ingests_ their output rather than duplicating their structure — confirmed by test 1.1 under Section 1.
