# WP-7 — Make the growth engines real: recommendations and experimentation

> **Read first:** [`../README.md`](../README.md) and [`README.md`](README.md), completely.
> **Depends on:** WP-2 and WP-3 for the behavioural half. The order-derived half (below) needs neither.
> **Conflicts with:** WP-2, WP-8 (`apps/storefront/src`) and WP-3, WP-5, WP-6, WP-9, WP-10 (`composition.ts`).
> **Closes:** G-46, G-47.

## Why this exists

Two contexts present a complete, well-modelled surface — aggregate, status transitions, Prisma
repository, admin routes, admin screen — with nothing behind it.

**Recommendations.** `services/recommendations/src/application/recommendation.use-cases.ts:130`:

```ts
const scoredRefs: ScoredProductRef[] = relatedRefs.map((productRef, index) => ({
  productRef,
  score: 1 / (index + 1),
}));
```

`relatedRefs` comes from `SearchQueryPort`, whose only implementation is
`InMemorySearchQueryPort` — it returns `[]` unless a test seeds it, and its own doc comment says
production "swaps this for a real cross-context adapter at the composition root (deferred)". So the
seven strategies in `recommendation-strategy.ts` (`related`, `frequently_bought_together`,
`recently_viewed`, `personalized`, `trending`, `popular`, `similar`) are a string enum: **all seven
produce identical, empty output.** Nothing in the storefront requests a recommendation at all.

**Experimentation.** `Variant` carries an `allocationPercentage` validated to sum to 100 — and
nothing allocates against it. Grep the context for `assign`, `bucket`, `hash`: no hits.
`ExperimentResult` is `{variantKey, metricValue, sampleSize, occurredAt}` with no significance
computation. Nothing in the storefront reads an experiment, so no visitor has ever seen a variant.

## Part A — Recommendations

### Decisions, already made

1. **Compute offline, serve precomputed.** A `RecommendationSet` is generated by a job and read at
   request time. The aggregate is already shaped for this (`generate` / `regenerate` /
   `RecommendationSet`) — follow its grain rather than fighting it.
2. **Two data sources, two strategy families.** `frequently_bought_together` and `related` come from
   **order co-occurrence in Postgres** — real, available today, no dependency on WP-2/WP-3.
   `trending`, `recently_viewed` and `personalized` come from **behavioural events**, so they need
   WP-2/WP-3. `similar` comes from catalog attributes. Build the order-derived family first; it
   gives real value with no upstream dependency.
3. **Cross-context data arrives through ports**, never by importing another context. `pnpm arch`
   enforces this.

### Tasks

- [ ] **T7.1 — Replace `SearchQueryPort`'s stub with real adapters.**
      Read `services/recommendations/src/application/ports.ts` and
      `infrastructure/in-memory-port-adapters.ts` first. Add real adapters at the composition root
      (`apps/admin/src/composition.ts` — see the existing `apps/admin/src/infrastructure/cross-context/`
      adapters for the exact pattern). The port may need reshaping to serve more than "related
      product refs"; if so, change the port, do not smuggle a second data path in beside it.

- [ ] **T7.2 — Implement the strategies as real, separately tested functions.**

      - `frequently_bought_together`: co-occurrence across order line items. Do **not** use raw
                counts — a product in every order (a bag, a warranty) will dominate every list. Normalise
                (lift, Jaccard, or PMI); pick one, justify it in a comment, and test that a universally
                popular item does not crowd out genuinely related ones.
              - `related` / `similar`: catalog attributes, categories, collections, brand.
              - `trending`: view/purchase velocity over a window (needs WP-3).
              - `recently_viewed`: per-identity, from the event store (needs WP-2/WP-3).
              - `personalized`: combine the above with the customer's own history via
                `services/customer-360`.

              Each strategy must produce **materially different output** for the same product. A test that
              asserts two strategies differ is the one that would have caught the current state.
              Exclude: the anchor product itself, unpublished products, and out-of-stock products (make the
              last one configurable — some merchants want back-in-soon shown).

- [ ] **T7.3 — Generation job.**
      Register a scheduled job through `apps/runtime/src/scheduler.ts` (read how the existing jobs
      there are registered, including the distributed-lock usage — `composition.test.ts` references
      an outbox-prune job that respects it). Regenerate sets on a cadence and on catalog changes.
      Tenant-scoped.

- [ ] **T7.4 — Public routes and storefront rendering.**
      A `/public/recommendations` route in the shape of `public-catalog-routes.ts` (DTO-mapped,
      unguarded, published-only), and recommendation strips on the product page, the cart, and the
      order confirmation. Emit a `recommendation_shown` / `recommendation_clicked` tracking event
      via WP-2's SDK so the engine's own effect is measurable — an engine you cannot measure is one
      you cannot improve.

## Part B — Experimentation

### Decisions, already made

1. **Assignment is a deterministic hash, computed at the edge, never stored per visitor.**
   `hash(experimentId + assignmentUnit) → [0,1) → bucket`. Deterministic means the same visitor
   always sees the same variant with no lookup, no cookie round-trip and no database write on the
   hot path.
2. **The assignment unit is explicit per experiment**: `visitorId`, `sessionId` or `customerId`.
   Defaulting silently is how experiments get invalidated.
3. **Exposure is an event, not a database row.** The visitor was exposed → emit `experiment_exposed`
   through the tracking pipeline. Analysis reads events. This is also what makes WP-3's event store
   the analysis substrate rather than a second bespoke table.
4. **Statistics are computed on read, from exposures and conversions.** Do not accumulate counters —
   they cannot be recomputed after a bug, and there will be a bug.

### Tasks

- [ ] **T7.5 — The assignment function.**
      Pure, deterministic, uniformly distributed, in `services/experimentation/src/domain/`.
      It must honour `trafficAllocation` (the eligible fraction, already modelled — read
      `variant.ts`'s comment at the `trafficAllocation` definition) **before** the variant split.
      Tests: distribution is uniform across 100k synthetic units within tolerance; the same unit
      always maps to the same variant; adding a _new_ experiment does not reshuffle an existing
      one's assignments (salt the hash with the experiment id — the classic bug is a shared hash
      that correlates every experiment on the same visitor).

- [ ] **T7.6 — Exposure events.**
      Emit `experiment_exposed` with the experiment id, variant key and assignment unit, exactly
      once per visitor per experiment per session, through the WP-2 SDK. Never emit on a page that
      does not actually render the variant — a phantom exposure biases the result toward null.

- [ ] **T7.7 — Statistical evaluation.**
      Given exposures and conversions per variant, compute conversion rate, lift versus control,
      a confidence interval, and a significance verdict. Two rules:

      - **State the test you used and its assumptions in a doc comment**, and surface the same
                statement in the UI. An operator reading "significant" without knowing what was tested
                will make a bad call.
              - **Guard against peeking.** Report the sample size reached and the sample size required for
                the configured minimum detectable effect, and mark a result "not yet conclusive" until
                then. Repeatedly checking a running test and stopping at the first green is the single
                most common way A/B testing produces false results, and the UI is where it is either
                enabled or prevented.

- [ ] **T7.8 — Storefront integration.**
      A way for the storefront to ask "which variant of experiment X for this visitor" and render
      accordingly, plus a worked example (a PDP element). Assignment must be **server-side** so the
      page does not flicker from control to variant after hydration.

- [ ] **T7.9 — Results screen.**
      Extend `apps/admin-web/src/app/experiments/[experimentId]/page.tsx`: per-variant exposures,
      conversions, rate, lift, interval, significance verdict, the required-sample-size line, and
      the named test. Strings in `en.ts` and `ar.ts`.

## Definition of done

- [ ] Two different recommendation strategies return materially different, non-empty results for
      the same product, from real order data.
- [ ] Recommendation strips render on the storefront and their impressions/clicks are tracked.
- [ ] A visitor is deterministically bucketed, sees the same variant on every visit, and their
      exposure is emitted exactly once per session.
- [ ] The results screen reports lift with an interval, a named test, and a not-yet-conclusive state.
- [ ] G-46 and G-47 closed. Repo-wide gates green, plus `pnpm arch`.

## Known traps

- **A recommendation that leaks an unpublished or draft product is a data leak.** The repo already
  had a draft-price leak (Phase 0). Filter on the read path, not only at generation.
- **Do not store an assignment per visitor.** It defeats the point of a deterministic hash, and it
  puts a write on the storefront's hot path.
- **Do not compute significance from counters you increment.** Compute from events, so a bug can be
  fixed and the history recomputed.
- **`InMemorySearchQueryPort` will keep tests green while production returns nothing.** Make at
  least one test run against the real adapter shape, or you will ship the current bug again.
