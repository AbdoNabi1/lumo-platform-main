# DECISIONS — architecture decision log

> Every significant decision, with its reason and trade-offs. **Never redesign a decision without
> explicit approval + a new ADR** (`architecture/adr/`). Newest ADRs win; this log mirrors them in
> brief. Format: Decision · Reason · Trade-offs.

### D-001 — Modular monolith first, extract by Strangler Fig

- **Decision:** Build the transactional core as one deployable with strict module boundaries; run only high-throughput capabilities as separate services; extract others on measured need. ([ADR-0001](architecture/adr/0001-modular-monolith-with-strangler-extraction.md))
- **Reason:** Avoid premature distribution cost; keep velocity; preserve a clean extraction path.
- **Trade-offs:** Requires discipline to keep boundaries; some intentional duplication (e.g. order-time product snapshots).

### D-002 — DDD bounded contexts; one DB schema per context; no cross-context FKs/joins

- **Decision:** Each context owns its data; cross-context references are bare ids; integrity via the owning service + events.
- **Reason:** Makes extraction mechanical; enforces independence.
- **Trade-offs:** No DB-level cross-context integrity; more application-level coordination.

### D-003 — Clean Architecture; dependencies point inward

- **Decision:** `kernel → domain → application → infrastructure → presentation`. Inner layers never import outer.
- **Reason:** Testability, replaceable infrastructure, longevity.
- **Trade-offs:** More interfaces/indirection; ports + adapters overhead.

### D-004 — `Result`/`Either` live in `@platform/types`

- **Decision:** One `Result<T,E>` type + helpers (`ok`/`err`/`map`/`match`/…) in the kernel.
- **Reason:** Usable by every layer without coupling; single source.
- **Trade-offs:** Kernel `types` gains a small runtime surface (acceptable).

### D-005 — Error hierarchy lives in `@platform/utils` (kernel)

- **Decision:** `AppError` + `DomainError` subclasses (`ValidationError`, `NotFoundError`, `ConflictError`, `ConcurrencyError`, `BusinessRuleError`, `UnexpectedError`) + `toErrorEnvelope` in utils.
- **Reason:** The domain layer can use errors without depending on the application layer.
- **Trade-offs:** "Domain"-named errors sit in a kernel package (documented; single error home).

### D-006 — Repository ports in `@platform/repository`; adapters in infrastructure

- **Decision:** Interfaces (`Repository`, `ReadRepository`, `WriteRepository`, `UnitOfWork`, `TransactionalUnitOfWork`) in `repository`; the Prisma adapter foundation in `@platform/db`.
- **Reason:** Dependency Inversion — application depends on ports, never on Prisma.
- **Trade-offs:** Extra port package; adapter wiring via DI.

### D-007 — CQRS lives only in the Application layer

- **Decision:** Command/query buses, handlers, use-cases, middleware in `@platform/application`. Domain has none of it.
- **Reason:** CQRS is an orchestration concern, not a domain concern.
- **Trade-offs:** Buses are type-erased internally (handled with localized, sound casts).

### D-008 — Domain is pure and deterministic

- **Decision:** No id generation, no clock reads, no infrastructure/framework/messaging/HTTP/DB in `@platform/domain`. Depends only on the kernel.
- **Reason:** Reusable by every bounded context; fully unit-testable; no hidden side effects.
- **Trade-offs:** Ids/timestamps must be supplied from outside (more explicit construction).

### D-009 — ID generation through abstraction (Dependency Inversion)

- **Decision:** Domain exposes only `UniqueEntityId` + `UniqueEntityId.from(value)`. The `IdGenerator` **port interface** lives in `@platform/contracts` (D-018); its `ID_GENERATOR` DI token lives in `@platform/application`; the `CryptoIdGenerator` **adapter** lives in infra `@platform/id` (UUIDv7, D-022). The application generates ids and passes them in; repositories rehydrate via `from()`.
- **Reason:** Keeps the domain deterministic and infrastructure-independent.
- **Trade-offs:** Infra adapter + DI wiring; aggregates can't self-mint ids.

### D-010 — Domain events are infrastructure-free

- **Decision:** `DomainEvent` carries supplied `eventId`/`aggregateId`/`occurredAt`; `AggregateRoot` only collects events. No bus, outbox, or publishing in the domain.
- **Reason:** Determinism + keeps messaging an infrastructure concern.
- **Trade-offs:** Event id/time supplied externally; dispatch wired later (outbox).

### D-011 — Frozen UI contract

> **SUPERSEDED by [D-052](#d-052--morbeh-design-system-is-the-canonical-design-system) (2026-08-08).** The frozen prototype, its five `docs/ui/` specifications, and its tokens have been retired and removed. Retained here as history — this contract no longer binds.

- **Decision:** `docs/ui/` (+ `apps/admin/prototype/admin-dashboard.frozen.html`) is the visual source of truth. Extend functionality only; never redesign; new surfaces require approval.
- **Reason:** Stable, approved UX; prevents churn.
- **Trade-offs:** New features must fit existing screens or request a UI change.

### D-012 — Strict quality bar

- **Decision:** No `any`/`@ts-ignore`/`eslint-disable`/TODO/placeholder/mock in shipped code; strict TS; type imports; Prettier/ESLint enforced; Conventional Commits.
- **Reason:** Five-year maintainability; merge-ready always.
- **Trade-offs:** Slower to write; occasional localized sound casts at type-erasure boundaries.

### D-013 — DI without decorators

- **Decision:** Token-based DI container (values + singleton/transient factories + scopes); no `reflect-metadata`.
- **Reason:** Composition over inheritance; no metadata/runtime magic.
- **Trade-offs:** Manual registration; no auto-wiring.

### D-014 — Object storage S3-compatible; secrets env/file (Vault-ready); observability OpenTelemetry

- **Decision:** MinIO (dev) behind an S3 abstraction; `SecretProvider` (env + Docker file, Vault-ready); OTel for tracing/metrics + the kernel logger.
- **Reason:** First-party, portable, vendor-neutral.
- **Trade-offs:** Vault/Sentry concretes deferred to later sprints.

### D-015 — No business DB models yet

- **Decision:** Prisma schema is infrastructure-only (no models) until business sprints; first migration lands with the first bounded context.
- **Reason:** Foundations before features; avoid speculative schema.
- **Trade-offs:** Repository adapter is abstract until a concrete model exists.

### D-016 — Toolchain pins

- **Decision:** `packageManager = pnpm@11.9.0`; pnpm-11 lockfile; `minimumReleaseAge` supply-chain policy; `allowBuilds` allowlist; npm scope `@platform/*`; root folder `lumo-platform`.
- **Reason:** Reproducible installs in the available environment; supply-chain safety.
- **Trade-offs:** Fresh resolves need policy-aware handling; scope/folder names are fixed.

### D-017 — Architecture changes are ADR-gated

- **Decision:** Any change to the contract in `docs/architecture/` (or a frozen invariant) requires a numbered ADR before code.
- **Reason:** Prevent silent architecture drift across AI sessions.
- **Trade-offs:** Slight process overhead for changes.

### D-018 — Outbound ports live in dedicated contract packages, never inside a layer

- **Decision:** Outbound port **interfaces** live in leaf packages, not inside `@platform/application`. Persistence ports stay in `@platform/repository` (D-006); other cross-cutting outbound ports (`IdGenerator`, `Clock`) live in `@platform/contracts` (interfaces only, no runtime deps). **DI tokens stay in `@platform/application`** (co-located with the container). Infrastructure adapters depend only on the contract package, never on the application layer. ([ADR-0002](architecture/adr/0002-outbound-ports-in-contracts-package.md); resolves review finding M1.)
- **Reason:** Consistency with D-006; lean adapters (no dependency on the whole application kernel); dependency direction stays inward.
- **Trade-offs:** One extra package; a port's interface and its DI token live in different packages (contract vs. wiring handle).

### D-019 — Time through a `Clock` port (Dependency Inversion)

- **Decision:** Reading the current time is an outbound port: `Clock` interface in `@platform/contracts`, `CLOCK` token in `@platform/application`, `SystemClock` adapter in infra `@platform/clock`. The domain never reads the clock (timestamps are supplied, D-010); application/infra obtain time via the port. _(Resolves review finding M3; abstraction only — no business wiring.)_
- **Reason:** Symmetry with the `IdGenerator` port (D-009); deterministic testing (inject a fixed clock); no hidden `new Date()` side effects.
- **Trade-offs:** One extra package + DI wiring for a small concern.

### D-020 — Value objects are deeply immutable

- **Decision:** `ValueObject` deep-freezes its props at construction (plain objects + arrays, recursively; no cycle handling — props are acyclic data), replacing the previous shallow `Object.freeze`. _(Resolves review finding M4.)_
- **Reason:** Composite value objects (nested objects/arrays) must be truly immutable for sound equality and aliasing safety.
- **Trade-offs:** Small construction cost; nested props must be acyclic plain data.

### D-021 — `UniqueEntityId` rejects empty/whitespace values

- **Decision:** `UniqueEntityId.from(value)` validates with `Guard.againstEmpty` and **throws** the kernel `ValidationError` for empty or whitespace-only input. The public API stays `from(value): UniqueEntityId` (not `Result`). _(Resolves review finding M5.)_
- **Reason:** An empty identity is an invariant violation / corrupt input — fail loud at the construction boundary. Reuses the existing Guard + kernel error (D-005).
- **Trade-offs:** `from()` can throw (an exceptional path, distinct from expected input validation, which uses `Guard` + `Result`).

### D-022 — Application-generated ids are UUIDv7 (RFC 9562)

- **Decision:** `CryptoIdGenerator` produces **UUIDv7** (48-bit ms timestamp + random) using `node:crypto` only — no external dependency. Aligns the implementation with the documented time-ordered id strategy. _(Resolves review finding M2; chosen over an ADR for v4.)_
- **Reason:** Time-ordered ids preserve B-tree/index locality; removes the prior v4 drift. No new dependency keeps the supply-chain policy (D-016) intact.
- **Trade-offs:** UUIDv7 embeds a creation timestamp (minor information exposure) — acceptable for internal ids; hand-rolled generation is covered by format + ordering tests.

### D-023 — Event backbone: classic outbox in two packages

- **Decision:** Cross-context integration-event **contracts** (envelope, topic/versioning helpers, `EventSerializer`) live in `@platform/domain-events` (a leaf — the only async coupling surface). The **runtime** (transactional outbox write-side, `EventPublisher`/`EventConsumer`, `ProcessedEventStore`, `DeadLetterStore`, `RetryPolicy`, in-memory adapters) lives in `@platform/messaging`. Classic DDD + Outbox — **no CQRS/Event Sourcing**. The `OutboxWriter` is invoked by infrastructure (the persistence boundary) and writes only to the outbox inside the aggregate's transaction; `correlationId`/`causationId` live only on integration events (domain events stay pure). Messaging ports stay in `@platform/messaging` (not `@platform/contracts`, which keeps only universal ports). Dependency direction `domain ← application ← messaging ← infrastructure`. (Sprint 0.6; no ADR — the architecture contract docs 02/05 are unchanged.)
- **Reason:** Reuses `@platform/domain` events + `@platform/repository` transactions; lean coupling surface; testable without a broker.
- **Trade-offs:** Two packages; the outbox write is an infrastructure responsibility (the application stays messaging-free).

### D-024 — Serialization is an abstraction; production codec deferred

- **Decision:** `EventSerializer` is an interface; the **production** implementation (Avro/Protobuf via the schema registry) is intentionally **unimplemented** in Sprint 0.6. A **test-only** `InMemoryEventSerializer` lives at `@platform/domain-events/testing`. There is **no JSON production default**. The envelope uses only primitive field types so it is already Avro-compatible (no future migration). Redpanda/Debezium/Apicurio adapters are deferred to the broker-wiring sprint (D-A). (Sprint 0.6; no ADR — defers adapters the contract already names, without changing its rules.)
- **Reason:** YAGNI + the current environment has no broker/registry; avoids committing to a wire codec prematurely while keeping the contract stable.
- **Trade-offs:** No end-to-end broker test until the wiring sprint; the in-memory serializer encodes via JSON internally (test-only, not the production format).

### D-025 — Auth/authz seams as ports; minimal feature flags

- **Decision:** Authentication + authorization are **ports added to `@platform/contracts`** (`Principal`/`PrincipalKind`; `Authenticator` → `Principal | null`; `Permission`; `AccessControl` → `boolean`) — **no `@platform/security` package** and **no audit subsystem** (deferred until a real producer). `AuthenticationError` (401) + `AuthorizationError` (403) added to `@platform/utils` (single error home, D-005). `@platform/feature-flags` ships only `FeatureFlags` + `EvaluationContext` + `InMemoryFeatureFlags`; rollout/percentage/multivariate/targeting + the source of truth belong to the future Experimentation implementation. **No DI tokens** (consumers inject by constructor at their composition root). (Sprint 0.7; no ADR — contract docs 07/12/14 unchanged.)
- **Reason:** YAGNI — only seams with an immediate Phase-1 (1.x) consumer; provider-agnostic like 0.6; `@platform/contracts` stays a leaf because the ports return `Principal | null` / `boolean` (no `Result`/error coupling).
- **Trade-offs:** RBAC/Ory/Keto/audit/rollout deferred to focused later work; resource-level authz is added later via an optional argument (non-breaking).

### D-026 — Phase-1 bounded-context conventions (Catalog + Media)

- **Decision:** Business contexts are independent `services/<context>/` Clean-Architecture slices. (a) **VO factories return `Result`** for expected input validation (via `Guard`); **aggregate invariant violations throw `DomainError`** (caught by the use-case into the `Result` channel) — matching `UseCase` semantics. (b) **Value objects are context-local** (`Money`, `Slug`, …) until ≥3 contexts need identical semantics (rule of three), then promoted to the shared kernel. (c) **Cross-context references are bare ids** (`MediaRef` → a Media asset id); no cross-context source import or DB FK. (d) **Interfaces are framework-agnostic** — controllers + a `present()` mapper (`Result` → status + the `@platform/utils` error envelope); no HTTP server yet. (e) **In-memory persistence + outbox** (Prisma/broker deferred). (Sprint 1.1; no ADR — conforms to docs/architecture/02–05 + the 0.5 design.)
- **Reason:** YAGNI + bounded-context independence; extend the existing kernel/contracts/messaging rather than add abstractions; keep `pnpm arch` green.
- **Trade-offs:** No real ACID/durability until Prisma is wired; minor `present()` duplication across contexts (promote to a shared interfaces-kit when HTTP lands).

### D-027 — Pricing + Inventory conventions (Sprint 1.2)

- **Decision:** Extends D-026 for two more contexts. (a) **`Money` stays context-local** — now duplicated in Catalog + Pricing (2 contexts); promote to the shared kernel only at the **third** consumer (rule of three). `Currency` is a new Pricing-local VO. (b) **Inventory emits a single `inventory.adjusted` integration event** carrying a `reason` (`received`/`adjusted`/`reserved`/`released`) + resulting levels — covering all stock mutations; separate `stock.reserved`/`released`/`low` events are deferred (per the 1.2 scope). (c) **`StockLevel` is a rich immutable VO** whose `receive`/`reserve`/`release`/`adjustTo` return new levels and throw `BusinessRuleError` on invariant violations (caught into the `Result` channel). (d) Cross-context refs by bare id (`ProductRef` in both contexts; reservation order/cart reference). (Sprint 1.2; no ADR — conforms to docs/architecture/02–05, the 0.5 design, and D-026.)
- **Reason:** YAGNI + bounded-context independence; reuse the kernel/messaging; keep `pnpm arch` green.
- **Trade-offs:** `Money`/`present()`/`InMemoryUnitOfWork`/`ProductRef` now duplicated across Phase-1 contexts — candidates for kernel/shared-kit promotion once shapes stabilise (deferred).

### D-028 — Cart conventions + deferred kernel promotion (Sprint 1.3)

- **Decision:** `@platform/cart` follows D-026/D-027. (a) **Caller-supplied price snapshot** — `AddItem` takes `unitPriceAmountMinor` + `currency`; the line stores the snapshot and Cart never imports/calls Pricing (the live Pricing-quote gRPC client is deferred). (b) **`cart.checked_out` is published via the outbox** as the trigger for the Sprint 1.4 checkout saga, which owns stock reservation against Inventory — Cart does **not** call Inventory and does not validate stock in 1.3; `cart.abandoned` is also emitted (consumer deferred). (c) **Single-currency cart invariant** (enforced in the aggregate and by `Money.plus`). (d) **No `CartId` VO** — the aggregate id is `UniqueEntityId` (a branded id would duplicate it; YAGNI). (e) Cart's `Money` is context-local but **carries `times`/`plus` arithmetic** the Catalog/Pricing copies lack.
- **Rule of Three — reached, promotion deferred:** with Cart, `Money` is now in **3** contexts (Catalog/Pricing/Cart) and `ProductRef` in **3** (Pricing/Inventory/Cart). Promotion to `@platform/domain` is the correct next move, **but it requires migrating the already-committed Catalog/Pricing/Inventory contexts** — out of scope for 1.3 (refactoring previous sprints was not required to complete Cart) and complicated by the three `Money` copies differing in behaviour. **Recommendation:** a dedicated `MoneyKernelPromotion` refactor introduces a reconciled kernel `Money` (+ `ProductRef`/`EntityRef`) and migrates all consumers in one focused change. (Sprint 1.3; no ADR — conforms to docs/architecture/02–05, the 0.5 design, D-026, D-027.)
- **Reason:** YAGNI + bounded-context independence; honour "don't refactor previous sprints unless required" while recording the rule-of-three trigger as actionable debt rather than silently adding a 3rd local copy without note.
- **Trade-offs:** a third context-local `Money`/`ProductRef` persists until the promotion refactor; the price snapshot can go stale (price-refresh-on-read is a deferred Pricing-client concern).

### D-029 — `Money`/`ProductRef` kernel promotion scheduled as Sprint 1.4 step 0 (Architecture Debt Policy)

- **Decision:** Under the Architecture Debt Policy, the Rule-of-Three promotion deferred in D-028 is **no longer open-ended**: it is **scheduled as the first, independently-gated task of Sprint 1.4**, performed **before** any Checkout/Orders/Payments code. Requirements: (1) design the **final kernel API** for `Money` and `ProductRef` accounting for **all** consumers — Catalog, Pricing, Cart, **and the incoming Orders + Payments** (which raise `Money` to 5 consumers and make promotion unavoidable) — reconciling the divergent `Money` shapes (Pricing's `Currency`-VO form vs Cart's `currency: string` + `times`/`plus` arithmetic); (2) promote both to `@platform/domain`; (3) **migrate every existing context in the same refactor**; (4) run the full gates (lint, typecheck, test, build, arch) — all green — as a discrete step; (5) only then begin Checkout. The refactor must be independent, behaviour-preserving, documented, and clearly separated from the 1.4 feature work.
- **Reason:** Rule of three is already reached (Money ×3, ProductRef ×3) and 1.4 forces it further; deferring indefinitely accumulates debt, while promoting now (no active sprint) would fix a kernel API before its heaviest consumers define it. Pinning it to 1.4 step 0 resolves both.
- **Trade-offs:** the duplicate VOs persist one sprint longer; in exchange the kernel `Money` shape is designed once, against the complete consumer set, instead of being promoted then reworked.

### D-030 — `Money`/`ProductRef` promoted to the kernel (Sprint 1.4 Step 0, executed)

- **Decision:** Executed the D-029 refactor as Step 0. `Money` and `ProductRef` now live **only** in `@platform/domain` (`shared/value-objects/`); the six context-local copies (catalog/pricing/cart `Money`, pricing/inventory/cart `ProductRef`) were deleted and every consumer migrated. **Canonical `Money`:** `create(amountMinor, currency: string)` (a **string** currency, not a `Currency` VO) requiring a **non-negative** integer; `zero`; arithmetic `plus`/`minus`/`times` + comparisons `isGreaterThan`/`isZero`, all currency-checked and throwing `BusinessRuleError` on a mismatch or negative result. This reconciles the three prior shapes (Catalog's getters-only, Pricing's `Currency`-VO form, Cart's `string` + `times`/`plus`): the kernel uses the **string** currency (Pricing keeps its own `Currency` VO for code validation and passes `.code` in) and the **superset of arithmetic** Orders/Payments need. **Canonical `ProductRef`:** unchanged (`Guard.againstEmpty`). `Currency` (Pricing) and `Quantity` (Inventory/Cart) stayed context-local — not at rule of three, and out of the promotion's scope.
- **Behaviour preservation:** all five gates green before continuing; the only behavioural tightening is `Money` now rejecting negative amounts (previously Catalog/Pricing accepted any integer) — no existing test or call relied on negatives, and non-negativity is the correct invariant for all consumers. Independent + separated from the feature work (its own recommended commit).
- **Reason:** Architecture Debt Policy + D-029. Rule of three was reached and Orders/Payments raise `Money` to 5 consumers; promoting once, against the full consumer set, removes the duplication for good.
- **Trade-offs:** a one-time edit touched four previously-committed contexts (imports + Pricing's `Money(Currency)`→`Money(string)` call sites); justified and required to complete the promotion. `present()`/`InMemoryUnitOfWork` remain intentionally per-context (not at a clean rule-of-three for promotion yet).

### D-031 — Checkout + Orders + Payments conventions (Sprint 1.4)

- **Decision:** Three independent Clean-Architecture slices following D-026/D-027/D-028, all on the kernel `Money`. (a) **Orders** — `Order` aggregate with status **derived** from an append-only `OrderEvent` history (`placed`→`paid`→`refunded`); line products are immutable **snapshots** (`ProductSnapshot`/`AddressSnapshot`), never live refs; a `RefundPolicy` **domain service** gates refunds (paid-only); events `order.{placed,paid,refunded}`. (b) **Payments** — `PaymentIntent` aggregate (`Charge`/`Refund` entities; `PspToken`/`PaymentStatus` VOs); refunds bounded by the captured amount via `Money` arithmetic; events `payment.{captured,failed,refunded}`; never stores raw card data. (c) **Checkout** — `CheckoutSession` aggregate (`CheckoutState` VO) emitting `checkout.{completed,failed}`. (d) **The cross-context purchase-saga orchestration is deferred** (needs Temporal + gRPC clients — no Docker host): each context is independent, references others by **bare id**, and communicates via outbox integration events; the saga will drive these aggregates. No cross-context imports. (Sprint 1.4; no ADR — conforms to docs/architecture/02–05 + the 0.5 design.)
- **Reason:** YAGNI + bounded-context independence; deliver the aggregates + lifecycle events the saga needs without prematurely building orchestration that requires deferred infrastructure.
- **Trade-offs:** Checkout cannot yet _drive_ the end-to-end purchase (no orchestrator/clients); Orders/Payments are exercised directly. `present()`/`InMemoryUnitOfWork` duplicated per context (intentional). No `CheckoutId`/`OrderId` branded VOs (`UniqueEntityId` suffices; YAGNI).

### D-032 — Identity conventions (Sprint 1.5)

- **Decision:** `@platform/identity` (the last Phase-1 context) follows D-026/D-031. `Customer` aggregate (raises `customer.registered`, `consent.changed`) with `Address` + append-only `ConsentRecord` entities and `Email` + `ConsentScope` VOs. (a) **Consent is derived** from the latest record per scope — `ConsentRecord` is insert-only, never mutated (mirrors Orders' append-only `OrderEvent`). (b) **`Email` is the natural key** — `RegisterCustomer` enforces uniqueness via `CustomerRepository.findByEmail` and returns a `ConflictError` (409) on a duplicate (a correctness rule, not a speculative abstraction). (c) **`Email`/`ConsentScope` stay context-local** — Identity is their only consumer (not at rule of three; `Address` here is an owned **entity**, distinct from Orders' `AddressSnapshot` VO). (d) **`ConsentScope` is a closed Phase-1 set** (`marketing`/`analytics`/`data_sharing`). (e) **Auth is not implemented** — the `Authenticator`/`AccessControl` **ports** already exist in `@platform/contracts` (0.7); an Ory adapter + encrypted PII are deferred. Households/child-profiles/ReBAC are explicitly out (YAGNI, per the 0.5 design). (Sprint 1.5; no ADR — conforms to docs/architecture/02–05 + the 0.5 design.)
- **Reason:** YAGNI + bounded-context independence; deliver customer/address/consent only, reusing the kernel/messaging and the existing auth ports.
- **Trade-offs:** email uniqueness is enforced via a store scan (fine in-memory; a Postgres unique index replaces it); consent fields are not yet encrypted; `present()`/`InMemoryUnitOfWork` duplicated per context (intentional). **Phase-1 contexts are now complete (9 of 9).**

### D-033 — Admin wiring lives in `apps/admin` as a framework-agnostic facade (Sprint 1.6)

- **Decision:** The Phase-1 admin wiring is a new **app** package `@platform/admin` at `apps/admin` — a composition/BFF layer, **not** a bounded context. It wires the six frozen Phase-1 admin screens (Products, Inventory, Orders, Customers, Discounts, Coupons) to their owning contexts (Catalog, Inventory, Orders, Identity, Pricing) via thin **facade controllers** that delegate to each context's existing public controller and return its `ControllerResponse` unchanged (aliased `AdminResponse`). **No business behaviour is added or changed**; presentation stays owned by each context's presenter (never re-mapped). (a) **Placement in `apps/`** is deliberate and required: the `no-cross-service-internals` fitness rule forbids a _service_ importing another service, but `apps/` is the composition root and is exempt — so only an app may legally aggregate several contexts' public APIs (`pnpm arch` stays green; 0 violations). (b) **Typed pass-through** uses `Parameters<Controller["method"]>` so the admin never re-declares or needs the contexts to export input types. (c) **Only actions backed by an existing use-case are exposed**; unbacked screen actions (fulfillment, returns, transfers, segmentation, dedicated coupon/discount-rule codes) are **deferred, not stubbed** — the Discounts/Coupons screens map to Pricing's existing Price/PriceList surface (the 0.5 design's `Coupon`/`DiscountRule` aggregates were not built in Sprint 1.2). (d) **No HTTP server** (framework ban): an HTTP/RPC transport adapter that lets the Morbeh Design System call these facades is deferred, along with the admin cross-cutting baseline (tracking, audit-on-mutation, RBAC/ReBAC, flag gating, bulk-action jobs — `docs/admin/01` §2/§4). The 19 non-Phase-1 admin screens belong to later phases. (Sprint 1.6; no ADR — conforms to `docs/admin/01`, the roadmap, and the frozen-UI contract.)
- **Reason:** Wire functionality **behind the frozen controls** without touching UI or domain logic, honouring the framework bans; `apps/` is the only arch-legal home for cross-context composition.
- **Trade-offs:** the facades are thin (near-passthrough) — accepted, because their value is the screen→context mapping + the arch-legal composition seam, not new logic; the wiring is only reachable in-process/tests until the transport adapter lands.

### D-034 — Transaction context flows through repository ports (ADR-0003)

- **Decision:** Every repository port method takes a trailing optional `tx?: unknown`; use cases pass the context received from `TransactionalUnitOfWork.run(async (tx) => …)` to every repository call inside the boundary; infrastructure forwards it to the outbox append. Prisma adapters narrow `tx` and fail loudly when it is missing. ([ADR-0003](architecture/adr/0003-transaction-context-through-repository-ports.md))
- **Reason:** The transactional-outbox guarantee (aggregate write + outbox row in one transaction) was structurally unimplementable — the context never reached repositories. Explicit propagation keeps D-013 (no runtime magic).
- **Trade-offs:** An `unknown` parameter on otherwise persistence-free domain ports; callers must pass `tx` (adapter fail-loud is the backstop).

### D-035 — Tenant-ready event envelope; canonical 3-segment event names (ADR-0004)

- **Decision:** `IntegrationEvent` reserves optional `tenantId` + `producer` (also stamped as headers); `EventContext` carries optional `tenantId`; every composition names its `producer`. Event naming is canonically `<context>.<aggregate>.<event>`; doc 20 gains a reconciliation table of implemented topics as the source of truth. The tenancy _model_ (per-deployment vs shared) remains an explicit open decision required **before Phase 2**.
- **Reason:** Adding fields to live topics later is a breaking schema migration; reserving them now is free. 17 implemented events had already drifted from the catalog.
- **Trade-offs:** Optional fields cannot enforce tenancy yet; `trace_id` propagation still deferred to the broker sprint.

### D-036 — Atomic consumer idempotency: `recordIfNew` (ADR-0005)

- **Decision:** `ProcessedEventStore` replaces `record()` with atomic `recordIfNew(messageId, processedAt, tx?) → boolean`; `has()` is a fast pre-check only. The consumer logs a detected concurrent duplicate; production adapters implement a unique-constraint INSERT, ideally inside the handler's transaction.
- **Reason:** `has→handle→record` was check-then-act; duplicate execution of financial handlers is a money bug, and the old port shape made the correct implementation inexpressible.
- **Trade-offs:** Full exactly-once _effect_ still requires the handler's side effects and the marker in one transaction (Prisma adapter, broker sprint); handlers stay idempotent regardless.

### D-037 — Integration events carry no raw PII; logger redacts by default (ADR-0006)

- **Decision:** Translators publish identifiers, not PII (`customer.registered` now carries `{ customerId }` only); consumers fetch profile data from the owning context. The kernel logger redacts a built-in sensitive-key list (credentials + direct PII) recursively and by default; extending is additive, disabling is an explicit opt-out.
- **Reason:** Long-retained, effectively immutable topics containing raw PII turn GDPR erasure into crypto-shredding/topic rewrites; opt-in shallow redaction leaks by default.
- **Trade-offs:** Consumers pay an owning-context lookup for profile data; default redaction may occasionally mask a benign field.

### D-038 — Admin actions authorize an explicit `Principal` (ADR-0007)

- **Decision:** Every admin facade method takes `principal: Principal` first and authorizes `"<module>:<action>"` via the `AccessControl` port before delegating; denial is a transport-neutral 403 envelope (the only admin-owned response shape). `wireAdmin` defaults to a permissive `AllowAllAccessControl` until Ory/Keto lands; context controllers stay principal-free until a transport exposes them.
- **Reason:** The Sprint-0.7 auth ports had zero consumers; retrofitting principals after the transport sprint would churn every signature and test at the worst time. BOLA is OWASP API #1.
- **Trade-offs:** Authorization is permissive until Phase 2 (wiring is in-process only today); ReBAC/ownership checks remain future per doc 07.

### D-039 — Tenant-aware core with tiered physical isolation (ADR-0008)

- **Decision:** Every commercial aggregate belongs to exactly one tenant; `tenantId` is a platform primitive propagated boundary→context→envelope (never modeled inside domain contexts). Default physical model is pooled shared-schema with `(tenant_id, natural_key)` uniqueness, `tenant_id`-led indexes/shard keys, and Postgres RLS as defense-in-depth; enterprise/white-label/residency tenants get dedicated schema/database/deployment tiers via composition only. Prisma schemas carry `tenant_id` from the first migration. A future `Tenancy` context owns merchants/organizations.
- **Reason:** SaaS/marketplace/white-label are the stated future; tenancy is the most expensive retrofit in the system and Phase 2 freezes schemas and topics.
- **Trade-offs:** Composite-key tax on every query/index now; RLS+adapter double enforcement must be tested; `Tenancy` context is deferred scope with a fixed id contract.

### D-040 — Immutable audit trail port; guards are policy-enforcement points (ADR-0009)

- **Decision:** `AuditTrail` (append-only by contract) joins `@platform/contracts`; the admin boundary's `AdminGuard` authorizes **and** audits every action decision (`allow`/`deny`) in one seam, failing the action if the audit write fails. Production adapter appends via the outbox as `audit.entry.recorded` to 7-year archival storage; tamper evidence via append-only + hash chaining at the archive.
- **Reason:** Audit is a SOC2/ISO/PCI blocker that was pure plan; decision-level audit from day one is cheap now and impossible to reconstruct later.
- **Trade-offs:** Outcome-level audit (what changed) still lands with transport middleware + the outbox adapter; in-memory trail is volatile by design.

### D-041 — Third-party extensions out-of-process; themes declarative + sandboxed (ADR-0010)

- **Decision:** Third-party apps are external services touching the platform only via OAuth-scoped public APIs, signed webhooks, and declarative UI slots (the Shopify model); in-process loading of untrusted code is rejected outright. First-party plugins keep doc 11's port/adapter model. Themes are versioned data packages (layouts/templates/sections/blocks/settings) rendered by a sandboxed Liquid-compatible engine — no server-side theme code, allowlisted object model, render budgets, escaping by default. Manifests (id, semver, scopes, webhooks, slots, settings schema, apiVersion) are the contract for both; all lifecycle transitions are tenant-scoped and audited. Contracts: doc 24 (app platform), doc 25 (theme + storefront platform).
- **Reason:** Where untrusted code executes is the platform-defining security/availability decision; the WordPress/Magento in-process model is the documented failure mode at app-store scale.
- **Trade-offs:** Apps pay network latency (bulk APIs + webhooks mitigate); some deep in-process customizations are impossible by design; the sandboxed renderer is a major storefront-phase investment. WASM edge functions remain a revisit-later option.

### D-042 — Persistence adapter conventions (Sprint 2.2)

- **Decision:** Every Prisma repository follows one shape: (a) constructor deps `{ prisma, outbox, context, tenantId }` — tenant scope is injected and applied to every query (ADR-0008 §2); (b) `save` REQUIRES the unit of work's transaction client and fails loudly without it; the outbox append shares that transaction (ADR-0003); (c) optimistic locking is `updateMany WHERE id AND tenant_id AND version` with 0 rows ⇒ `ConcurrencyError` — no retry, no silent overwrite; creates persist `version = 1` (in-memory fresh = 0); (d) aggregates rehydrate via `static reconstitute(...)` (no domain events; persisted version carried) and closed-set VOs via `from(value)`; derived state (order status, consent, payment remaining) is never stored; (e) mapping lives in dedicated mapper classes using structural row interfaces — Prisma types never leave infrastructure, domain imports nothing new; (f) append-only children (order events, consent records, charges, refunds, addresses) persist via `createMany({ skipDuplicates: true })` keyed by entity id; mutable child sets (cart items, reservations) are replaced within the transaction.
- **Reason:** One reviewable pattern across 9 contexts; the transactional-outbox and tenancy guarantees become properties of the shape, not per-repo diligence.
- **Trade-offs:** delete+recreate for mutable child sets is simple but write-amplifying (revisit per-aggregate if hot — inventory's answer is the G-7 ledger); version is not bumped in-memory after save (one save per unit-of-work run by convention).

### D-043 — Infrastructure foundation conventions (Sprint 2.2.5)

- **Decision:** (a) Debezium is the production outbox relay: pgoutput + publication `lumo_outbox`, EventRouter routed by the outbox row''s `topic` column, ByteArrayConverter — the wire envelope is byte-identical to what `OutboxWriter` persisted; (b) every business topic ships with `.retry` and `.dlq` companions pre-created (broker-side redelivery replaces in-process sleep, per ADR-0005 note); retention follows doc-20 keys (30d/13mo/7y-class); (c) four least-privilege compose networks (data/messaging/observability/tools); (d) the OTel Collector is the only telemetry endpoint applications will ever know (OTLP), fanning out to Tempo/Prometheus/Loki; (e) MinIO buckets are purpose-scoped (media/exports/imports/backups) with tenant-prefixed keys — never bucket-per-tenant; (f) prepared-not-enabled: RLS (migration #2), PITR/replica settings, outbox partitioning, `lumo_app` DML-only role.
- **Reason:** Compose is the deployable contract that maps 1:1 onto Kubernetes later (doc 26 §7); every service sits behind an existing port and is replaceable without touching application code.
- **Trade-offs:** Redpanda Console instead of generic Kafka-UI (native Connect integration; Redpanda-flavored ops tooling); single shared Postgres hosts Apicurio''s database locally; publication/connector registration are manual first-boot steps until migration #2 automates the publication.

### D-044 — Redis layer conventions (Sprint 2.3)

- **Decision:** (a) `Cache`/`DistributedLock`/`RateLimiter`/`IdempotencyKeyStore` are outbound ports in `@platform/contracts` (D-018); `Cache` moved there from `@platform/redis` (type re-exported for back-compat). (b) Locks are **efficiency only** — correctness always stays with optimistic locking + idempotency; single-instance token-guarded locks, Redlock rejected. (c) Rate limiting is fixed-window Lua v1 (2× edge burst accepted); adapters throw on infra failure and the enforcement point picks fail-open vs fail-closed. (d) Client-request idempotency (`Idempotency-Key`) is a Redis TTL claim with token-guarded release-on-failure — event idempotency remains `ProcessedEventStore` in Postgres (ADR-0005). (e) Caches hold **mapper row DTOs, never aggregates**; reads rehydrate through the context''s mapper; writes **delete** cache entries (rollback-safe), transactional reads bypass the cache; keys are tenant-prefixed (ADR-0008). Cart: Postgres stays the source of truth (D-042); `CachedCartRepository` decorates the durable repository.
- **Reason:** Flash-sale cart reads, future transport rate limits, and duplicate-request protection need Redis primitives without coupling anything to Redis or weakening the tx/outbox invariants.
- **Trade-offs:** Fixed-window burst at edges; one more port family; delete-on-write costs a miss after every save (correct beats warm).

### D-045 — Storage layer conventions (Sprint 2.4)

- **Decision:** (a) Object keys are immutable, produced ONLY by `StorageKeyFactory` (`tenants/<tenantId>/<namespace>/<yyyy>/<mm>/<uuid>[.ext]`); a new version is a new key; `put` is a conditional write (`If-None-Match: *`) and overwrite is a provider-enforced error. (b) Buckets are purpose-scoped (media/exports/imports/backups), tenants are key prefixes — never buckets. (c) Soft delete and retention ride bucket versioning + lifecycle policies (configuration); `delete` in the port is permanent. (d) Upload constraints are allowlist `UploadPolicy` objects validated before bytes move; the `FileScanner` hook is fail-closed for user-upload namespaces (quarantine until `clean`). (e) `ImageTransformer` produces deterministic derived keys and never mutates sources. (f) Contracts stay runtime-agnostic: streams are `ByteStream = AsyncIterable<Uint8Array>`. (g) Descriptor metadata (tenant/owner/context/aggregate/checksum/creator/tags) rides as provider user-metadata and round-trips through `head`.
- **Reason:** CDN-cache-forever media, tenant isolation/erasure by prefix, and 10-year evolvability (scan/transform/one-time-download all have seams) without vendor lock-in.
- **Trade-offs:** Conditional-write capability becomes a hard adapter requirement; immutability means storage growth is managed by lifecycle, not overwrite; the scanner/transformer stay unimplemented until their consuming surfaces exist.

### D-046 — Broker runtime conventions (Sprint 2.5)

- **Decision:** (a) `@platform/kafka` is the broker adapter package (kafkajs; included in the dependency-cruiser layer rules). (b) Producers publish the exact outbox bytes — events are never rebuilt; ordering rides the aggregate-id key + idempotent producer with one in-flight request; the main business publication path remains outbox→Debezium. (c) Consumer groups use `KafkaConsumerRuntime`: `has` → handle → `recordIfNew` (recording first loses crash-between-claim-and-handle messages), failure republishes ORIGINAL bytes to `<topic>.retry` with attempt/due-time headers (5s/30s/2m/10m/1h, then `.dlq`) — in-process sleep retries never reach a consumer group. (d) Dead letters go to both the `.dlq` topic (forensic headers: original topic, group, tenant, trace, attempts, error+stack, timestamp) and `platform.dead_letters` (byte-identical replay). (e) `traceparent`/`tracestate`/`baggage` propagate verbatim through every redelivery hop. (f) Consumer fleets are owned by `ConsumerSupervisor` (health = readiness probe; lag via admin). (g) Cross-context consumers live in the consuming context''s `interfaces/` and call use cases only; `orders.order.paid` may only be caused by the payments-captured consumer or backoffice action (doc 22).
- **Reason:** Broker-side redelivery is the only retry model that survives consumer groups at scale; byte fidelity keeps the outbox the single envelope of record.
- **Trade-offs:** Single retry topic per topic (due-time wait) — tiered retry topics are the scale-up; kafkajs over librdkafka (pure JS today, swappable behind `EventPublisher`); metrics/spans are a seam until G-19.

### D-047 — Transport conventions (Sprint 2.6)

- **Decision:** (a) HTTP transport is `@platform/http`: Fastify strictly as infrastructure; routes are framework-independent `RouteDefinition`s (zod schema + permission + version + handler on parsed input) delegating to the existing controllers — zero business logic in transport, repositories/use cases never called directly. (b) Pipeline order is fixed: authenticate → resolve tenant FIRST (no application code tenant-less, no default tenant) → authorize via ONE policy engine (the injected structural `AdminGuard` twin — packages never import apps) → rate limit per (tenant, principal), fail-closed on admin/API surfaces → zod boundary validation → idempotency claim/replay for unsafe methods → uniform code→status error mapping. (c) OpenAPI is GENERATED from the same zod schemas that validate — one source of truth, spec cannot drift. (d) gRPC contracts are versioned proto packages (`morbeh.<ctx>.v<n>`), runtime-loaded (no manual serialization); static codegen arrives with `@platform/api-clients` (G-18); interceptors are the middleware seam; in-mesh insecure creds only (mTLS at mesh, doc 14 §5). (e) **G-22 resolved:** the Sprint-0.3 CQRS bus stays formally parked — transport delegation to controllers is the adopted composition idiom; revisit only if per-use-case cross-cutting middleware materializes.
- **Reason:** Shopify-shape exposure of the existing contexts with every hardening seam (2.3 Redis ports, ADR-0007/0009 guard, ADR-0008 tenancy) becoming enforced reality at the boundary.
- **Trade-offs:** Fastify/zod/proto-loader are swappable infrastructure choices behind our own abstractions; ajv is bypassed (zod parses); process-level /metrics until G-19.

### D-048 — Identity adapter conventions (Sprint 2.7)

- **Decision:** (a) All identity infrastructure lives in `@platform/auth` behind the frozen ports — business contexts and transport stay provider-agnostic; **no Ory SDK** (raw REST with injectable fetch; three endpoints used). (b) Self-service flows (registration/login/logout/reset/verification/MFA/WebAuthn/social/OIDC/SAML-via-IdP) are Kratos configuration, never platform code; the platform validates sessions, looks up identities, revokes (audited), and receives flow events via webhooks. (c) JWTs verify against JWKS with pinned issuer/audience and bounded clock tolerance; refresh rotation is the issuer''s contract — refresh tokens never reach the verifier; invalid tokens are uniformly `null` → 401. (d) Keto is the `AccessControl` adapter: permission `"<module>:<action>"` = tuple check, roles/hierarchy = subject-sets, tenant-scoped grants extend the tuple object later; **fail-closed always**. (e) Session-validation and authorization-decision caches ride the Sprint-2.3 `Cache` port; the TTL is the explicit revocation-latency window (15s/30s defaults, per-surface). (f) `ClaimsAuthenticator` is an additive contracts extension; the transport consumes verified claims for tenant resolution (claim → header → domain order).
- **Reason:** Shopify-grade identity without owning credential storage or flow orchestration; every seam already had a consumer, so adapters drop in at composition roots only.
- **Trade-offs:** Revocation latency = cache TTLs; Ory API drift is absorbed by contract tests + the tiny REST surface; Hydra (OAuth2 for apps) deferred to the app-platform phase.

### D-049 — Saga implementation conventions (Sprint 2.8)

- **Decision:** Workflow logic lives in a DETERMINISTIC framework-free core (`runPurchaseSaga`) with all effects behind an activities port; the Temporal workflow is a thin adapter (signals/timers/retry profiles only). Two retry profiles: bounded (pre-payment, 5 attempts) and convergent (post-payment truth — unbounded, 5m cap; never auto-unwind a paid order). Capture truth reaches the saga ONLY as a signal originating from the webhook→outbox event. Workflow ids are `purchase:<tenant>:<checkoutSession>`. PSP calls go through the `PaymentProvider` contracts port with per-step idempotency keys; adapters are raw REST (no SDKs, per D-048). Native build scripts required by Temporal are approved via the D-016 allowlist.
- **Reason:** Determinism, replay-safety and compensation semantics become unit-testable without a Temporal server; ADR-0012 stays enforceable in code review (the core cannot import a clock).
- **Trade-offs:** Two layers (core + adapter) to keep in sync — the adapter is deliberately too thin to drift; live workflow execution validates only on a Docker host.

### D-050 — Runtime composition conventions (Sprint 2.9)

- **Decision:** (a) `apps/runtime` hosts the three production processes (api/worker/scheduler) over ONE composition root; every dependency is wired there — application code never instantiates infrastructure. (b) `loadRuntimeConfig` is the only `process.env` reader (zod-typed, field-named startup failures). (c) The composition graph is side-effect-free (lazy clients); connect/start happens only in entrypoints — which is what makes composition unit-testable without Docker. (d) Secure defaults are structural: no JWKS ⇒ no api (no fake identity, D-048); no Keto outside `local` ⇒ composition fails closed. (e) Consumers/activities compose against context APPLICATION layers only (the payments-captured slice is the reference). (f) Scheduler jobs are injected, idempotent, and single-flight via the Redis lock; the interval loop is disposable — the job contract is not. (g) Missing composability is NAMED, never faked: G-39 (production context wiring behind the admin facade), G-40 (payments carries the checkout-session ref so the capture event can signal `purchase:<tenant>:<session>`).
- **Reason:** Turn the component collection into runnable processes without inventing business logic or weakening a single seam.
- **Trade-offs:** The api serves in-memory facade data until G-39 closes; the Temporal worker waits for its activities'' prerequisites; JSON serializer until Apicurio.

### D-051 — Engineering-memory update contract (Sprint 3.0A)

- **Decision:** The repository is the source of truth; chat history is disposable. The memory set is: AI_CONTEXT (append-only dated addenda), PROJECT_STATE (sprint table + current/next), DECISIONS (append-only; ADR first for architectural changes per D-017), MASTER_PROMPT + DEVELOPMENT_PROCESS (workflow), ARCHITECTURE_OVERVIEW (diagrams), CHANGELOG_AI (sprint index), KNOWN_GAPS (open mirror of doc 23 — doc 23 remains master), RELEASE_PROCESS. **No sprint is complete until all applicable files are updated in the same change set** (the sprint-close contract appended to MASTER_PROMPT/DEVELOPMENT_PROCESS). History is never rewritten — corrections append.
- **Reason:** Ten sprints proved the pattern; codifying it makes any future AI session self-sufficient without conversation context.
- **Trade-offs:** Two gap views (doc 23 + KNOWN_GAPS) must both be touched — accepted for the different audiences (full ledger vs open-items triage); drift is caught at sprint close.

### D-052 — Morbeh Design System is the canonical design system (supersedes D-011)

- **Decision:** The **Morbeh Design System** ([docs/ui/MORBEH_DESIGN_SYSTEM.md](ui/MORBEH_DESIGN_SYSTEM.md)) is the platform's one and only design system. Brand primary `#635BFF`; cool-neutral (slate) palette; Geist (Latin) + IBM Plex Sans Arabic (Arabic) at weights 400/500/600; 4px spacing grid; radius 4/6/8/12/16/full; four restrained elevations; Lucide as the sole icon library; motion 100/150/200/300/400ms. Tokens are layered primitive → semantic → Tailwind utility in `packages/design`; components in `packages/ui` consume semantic tokens only and never hard-code a value. `apps/admin-web` is the reference surface (the Morbeh Dashboard). The previous frozen-prototype design system is **retired**: `apps/admin/prototype/` and the five `docs/ui/` prototype specifications are deleted, and `packages/design`/`packages/ui` were evolved in place rather than forked — there is no second system.
- **Reason:** The frozen prototype was a 2026-06 chat-era HTML artefact that had never been implemented in React, defined a flat borders-only visual language with no accessibility guarantees, and blocked every UI change behind an approval gate. A single canonical, token-driven, accessibility-tested system removes that gate and the duplication risk at the same time.
- **Trade-offs:** (a) The admin React surface needed a host — `apps/admin` is a Fastify/facade package with zero `.tsx`, so `apps/admin-web` was added as the Next.js app; it is a new _app_, not a new design system, and it has no deployment pipeline yet. (b) The prototype's 25-screen inventory was documentation of an artefact that was never built; it is gone with the artefact, and screen specs now live with the screens. (c) `--input` is a heavier neutral (500) than a purely aesthetic choice would pick, because a control boundary must clear 3:1 (WCAG 1.4.11).

### D-053 — Per-request tenant scoping, extending ADR-0003's tx threading; RLS as defense-in-depth

- **Decision:** Option A (per-request repository scoping, not a per-tenant composition cache). Repository port methods gain `tenantId` as an explicit per-call parameter — reads take it as a parameter, writes derive it from the aggregate being saved — matching the shape `services/identity`'s access repositories already use; composition builds every repository once, as a process-wide singleton. `PrismaUnitOfWork.run` and a new `runReadScoped` helper both issue `SET LOCAL app.tenant_id` (parameterized `set_config`) as the first statement of the transaction they open, before any query runs — the same choke point ADR-0003 already routes every transactional write through. Kafka consumers switch from `rootEventContext(idGen, TENANT_DEFAULT_ID)` to the already-existing `followOnEventContext`, reading `tenantId` off the incoming envelope instead of a hardcoded default. The live database's RLS layer (G-63 — 130 policies, found already deployed but enforcing nothing because the connection role bypasses it) is adopted as real defense-in-depth via a two-phase rollout (wrapper first while still on the bypassing role, verified by an assertion at every entry point; role switch to the narrower `lumo_app` — its grants first revoked on `vault.secrets`/`_prisma_migrations`/`storage.*`, none of which this runtime's code path uses — only after that assertion holds everywhere). ([ADR-0014](architecture/adr/0014-per-request-tenant-scoping.md))
- **Reason:** This is ADR-0004's own deferred follow-up ("a follow-up ADR must decide... before Phase 2 freezes DB schemas and topics") and ADR-0008's tiered-isolation model's runtime half, both now overdue — Phase 2 froze schemas over two months before this ADR. T10.1's reading pass found the request-level tenant resolution already correct and fail-closed (`packages/http`'s `resolveTenant`/`server.ts`); the gap is entirely that composition never consumes its result. Extending the existing `tx` parameter (ADR-0003) to also carry `tenantId`, rather than introducing `AsyncLocalStorage` or a new mechanism, keeps the codebase's no-runtime-magic ethos (D-013) and reuses a pattern already proven in one context.
- **Trade-offs:** Every repository port method touched changes its signature — the ~40-context cost `WP-10` always estimated for Option A, not a new one. `runReadScoped` adds a transaction round trip to reads that previously ran as bare queries, a latency cost to benchmark once a slice exists. Narrowing `lumo_app`'s grants is one more precondition before the RLS rollout's second phase, but shipping `DELETE` on `vault.secrets` live on the request-serving role, even briefly, was judged worse.

### D-054 — Principal carries the request tenant (shape B); authorization decisions are per tenant

- **Decision:** `Principal.tenantId` is required and bound once by the transport from the resolved tenant (anonymous public principal included); authenticators return a tenant-less `AuthenticatedIdentity`. The authorization decision cache is keyed by tenant + principal + permission and the audit record carries the tenant (ADR-0015, G-67). Rejected: tenant inside `Permission` (conflates what with where) and a `tenantId` parameter on `authorize` (every caller can pass the wrong one).
- **Reason:** The Keto tuples carry no tenant (all seeds and `relation-sync.consumer.ts` write a bare permission and a bare principal id), so no TypeScript-only change can scope a grant. The tuple rewrite touches the live Ory Network project and is deliberately not done here: G-70, decided as `tenant/<tenantId>/<permission>`, dual-write then switch reads then delete bare, with a bare-vs-qualified count gate before the delete.
- **Trade-offs:** About sixty test fixtures gained a tenant, and the authenticator port splits its return type. The change fixes the cache and the audit record but does NOT make `TENANT_MODE=multi` safe: grants stay global per principal (G-70) and G-68 is open.

### D-055 — Storage keys are validated against the tenant, not minted, at both doors (G-68 / F-22)

- **Decision:** A storage key is usable by a tenant only if `StorageKeyFactory` could have produced it for that tenant (`storageKeyBelongsToTenant`, the strict inverse parse in `@platform/storage`). It is checked at registration (before the shared bucket is probed) and again at signing, behind a required `StorageKeyPolicy` port. Registration never accepts an unprefixed legacy key; signing an existing legacy row is `"refuse"` by default and `"allow"` only under `TENANT_MODE=single`, passed explicitly by `createAdminHttpApi`. Rejected: server-side minting now (needs a new permission granted in the live Ory project — G-71, done with G-70), and a `startsWith` prefix test (accepts `tenants/a/../b/x`).
- **Reason:** The bucket is one namespace shared by all tenants, so isolation has to come from the application refusing foreign keys; two doors because a registered row is otherwise a laundering step to a signed URL. The verifier sits beside the only producer so they cannot drift.
- **Trade-offs:** The client still names the key, so safety rests on the verifier and on every key-taking use case depending on the port; a NEW such use case that skips the port would reopen the gap. Under `TENANT_MODE=multi` legacy rows will not sign until migrated, and the live count is unknown (not queried). Does not close G-70: `TENANT_MODE=multi` stays forbidden.

### D-056 — Keto grants are qualified with the tenant from the event envelope; an untenanted event fails closed (G-70)

- **Decision:** Tuple object `tenant/<tenantId>/<permission>`, subject bare; rolled out dual-write, backfill, count gate, switch reads, delete bare. `relation-sync.consumer.ts` takes the tenant from `event.tenantId` (the outbox envelope, `EventContext.tenantId`). **When it is absent (or empty) the write handler writes NOTHING — not even the bare tuple — and logs at warn; the delete handler still deletes the bare tuple (that only narrows access, and is what it did before) and warns that the qualified twin was not removed.** There is no fallback to a default tenant and none to a bare tuple.
- **Reason:** `IntegrationEvent.tenantId` is optional on the type (making it required is G-64, a separate change with wider blast radius). A silent bare write is exactly the global grant G-70 closes, so an untenanted event is treated as "grant not applied", never "grant applied to every tenant". A default tenant would be a guess that is right in `single` mode and a cross-tenant grant in `multi`. The delete path differs on purpose: a dropped revocation is the worse failure, so it does the part it can and says loudly what it could not.
- **Trade-offs:** An untenanted `security.relation.written` is skipped, not retried or dead-lettered (retrying cannot supply a tenant), so it surfaces only as a warn line. Today every Security event is published with the tenant (`outbox.publish(events, input.tenantId, tx)`), so nothing is skipped in practice. Security's ReBAC check (`KetoRelationshipCheck`) qualifies with the tenant it is already handed, so both readers agree. Reads are switched in the same rollout as the dual-write, so the live tuples must be backfilled before a runtime uses the shared Ory project (runbook: `docs/operations/KETO_TENANT_MIGRATION.md`). G-70 stays open until that migration has run.
- **Amended 2026-09-21 (contract step, after the live migration ran and was verified):** the four writers now write the tenant-qualified tuple only; the bare write is gone. The delete handler is **changed**: an untenanted `security.relation.deleted` now logs at error and THROWS, so it goes to retry/DLQ, instead of deleting the bare tuple and warning. Reason: with reads checking only the qualified object, deleting the bare tuple revokes nothing, so the old branch acknowledged a revocation it had not applied. A skipped write denies; a skipped delete allows — the two paths must fail in opposite directions. With a tenant, the handler deletes the qualified tuple and then sweeps the bare object (idempotent).

### D-057 — Guest-to-account upgrade is verification-gated: no account exists until the email is proven (G-72)

- **Decision:** Signup with a guest-checkout email creates nothing usable — it issues a single-use, hashed (SHA-256), 24h-expiry token bound to `(tenantId, customerId)` (`services/identity`'s `RequestSignupLink`/`SignupToken`/`SignupTokenRepository`) and emails a link. Only opening that link and submitting a password (`CompleteSignup`, then `apps/admin`'s `CustomerAuthAdminController.completeSignup`) upgrades the guest `identity.customers` row IN PLACE — same customer id (so Customer 360/every reader keeps stitching by id), `is_guest` → false, `email_verified_at` set — then runs the same Security `RegisterPrincipal`/`setPassword` provisioning `register()` already performs. The password submitted at the initial signup request is never stored or used for this branch; only the completion form's password survives. Rejected: upgrading the guest row immediately and hiding prior orders/loyalty until verified — that needs filtering in every context reading by customer id and leaves a half-upgraded state; the token gate has no such state.
- **Reason:** The guest row's customer id already carries order history, addresses, and a loyalty balance. Upgrading it on signup with no proof of email ownership would hand all of that to whoever typed the email — T1.8's escalation moved from checkout to signup. No verification primitive existed anywhere in the platform (no token, no email-sending port, no reset-by-email flow) before this.
- **Trade-offs:** A guest who never opens the link can never register with that email through this surface — by design, since the alternative is the identity-theft hole this closes. The token's raw value exists only in memory between issuance and the outbound email call; a caller that logged the full request/response cycle around `RequestSignupLink` could still leak it, same exposure every one-time-token design carries. `CompleteSignup` and `provisionCredentials` are two separate calls (Identity's own upgrade, then admin's Security provisioning) rather than one transaction spanning both contexts — matches the existing `register()` boundary (Identity stays unaware Security exists, ADR-0023) and the same narrow window `register()` already has between its own two steps.

### D-058 — Signup responses for a guest email and an already-registered email are byte-identical (G-72)

- **Decision:** `POST /public/auth/register` (repointed to `CustomerAuthAdminController.requestSignup`) returns the IDENTICAL `202 {outcome: "link-sent"}` — same status, body, and headers — whether the submitted email belongs to a guest-checkout row or an already-verified account; only the dispatched email's content differs ("complete your account" vs "you already have an account, log in"), never anything that crosses the HTTP boundary. A brand-new, never-seen email keeps today's `201 {customerRef}` immediate registration, unchanged — that case was never an oracle (no prior email existed to leak) and D2's stop condition was that it need not change. `RequestSignupLink`'s three-way `"new"`/`"already-registered"`/`"guest"` discriminant exists precisely so the caller has the information to collapse the latter two before anything reaches the wire.
- **Reason:** Before this, a signup conflict (`409`) revealed "this email has bought from the store" — a purchase/account-existence oracle a storefront's own signup form should never be able to answer. D1's verification gate makes the guest case require a genuinely different code path (token issuance) from the already-registered case (no token, since there is nothing to complete) — without D2, that difference would have leaked through the response shape even if the status code matched.
- **Trade-offs:** The storefront's signup form necessarily shows the same "check your email" UI regardless of which of the three paths (well, two — brand-new still differs) applied, so a shopper who mistypes their existing email and expects an immediate account gets a delayed, email-gated flow instead with no client-side way to tell why. Rate limiting the request-signup route (D3, per-`(tenant, email)`, 5/hour) is a secondary defense against timing-based enumeration attempts, not a substitute for the identical response — both are needed.

### D-059 — The payment provider is resolved per request from the tenant and the shopper's selected method; nothing else picks one (WP-13, F-19)

- **Decision:** `PaymentProvider` stops being a construction-time singleton. `PaymentLifecycleDeps.paymentProvider` is replaced by a `PaymentProviderResolver` port (`resolveForNewPayment` / `resolveForExisting`), implemented by `TenantPaymentProviderResolver` (`services/payments`). It holds no tenant and no merchant credential — only the settings repository, the credential vault, the platform's own Stripe adapter and factories — and it builds a merchant's Paymob provider on **each call** from that tenant's sealed credentials (`@platform/secrets` envelope, sealed under `(tenantId, provider)`; never cached, so there is no per-tenant map to read the wrong slot of). It has **no fallback**: a missing method, vault, factory or credentials throws `PaymentProviderUnavailableError` — it never substitutes the in-memory stub. `provider` is a required input to `CreatePaymentIntentLifecycle` and is persisted on the intent (`payment_intents.provider`), so capture/refund/webhooks resolve the provider the shopper chose, not whatever the merchant has configured since (`resolveForExisting` deliberately does not require the method to still be enabled — a merchant who switches a method off must still be able to refund what it took). The shopper's choice enters at exactly one place — `SelectPayment`, validated against what the merchant offers — and `InitiatePayment` reads it back from the session; its route body is `.strict()` and accepts no method or amount. Merchant settings (`payments.merchant_payment_settings`, one row per tenant, RLS policy in the migration itself) store `region`/`integration_id` in the clear and the three Paymob secrets only as a sealed envelope; the DTO has no field a secret could occupy. The Stripe adapter stays **platform-level** (one Stripe account, env-configured, exactly as before) — per-merchant Stripe would be Stripe Connect, a different product.
- **How it satisfies ADR-0014:** point 3/4/7 and Amendments 6-8 forbid capturing a tenant at construction — repositories, adapters, ports and stores alike. `assertMultiTenantReady` walks the composed graph (`admin.paymentProviders` included) for `tenantId` fields and refuses to boot; the resolver has none, and `merchant-credentials-never-leak.test.ts` walks its graph after serving a request to prove neither a tenant nor a credential is retained. `apps/admin/src/http/merchant-payments.e2e.test.ts` runs the whole flow under `tenantMode: "multi"`, so that guard executes on this graph on every run. A webhook is verified against the **receiving** tenant's own secret, so a callback signed for merchant A and replayed at merchant B is rejected (tested). Mutation-checked: resolving one Paymob provider and sharing it turns 3 payments tests and 2 admin tests red.
- **Production guard:** `assertProductionPaymentProviderConfigured` (`apps/runtime/src/api.ts`) is **extended, not paralleled**: it now takes the payments inputs and reports, in the same aggregated boot error, a Paymob adapter composed without a real envelope vault. `buildRuntimeCore` composes the Paymob factory and a real vault together or not at all (`PAYMENT_CREDENTIALS_KEK_REF`), so that state is a tripwire on an invariant. The stronger property is that a stub can never back a method a merchant switches on: `UpdateMerchantPaymentSettings` refuses to enable Stripe or Paymob unless the platform reports a real backing for it, and the resolver has no stub to fall back to.
- **Reason:** A provider holding one merchant's API key in a singleton is the bug ADR-0014's conversion spent weeks removing — this time with real money attached. WP-13 decision 3 ("the orchestrator never chooses") is only enforceable if the method is a required input at every layer and no layer has a default.
- **Trade-offs / limits found:** (a) `PaymentPort.requestCapture` (Orders) carries no method and was not widened; `OrdersPaymentAdapter` now looks up the shopper's selection from the order's checkout session and **refuses** for an order with none (e.g. operator-created), rather than choosing. That operator-triggered path could not settle against a real PSP before either (create never authorizes, so the capture hits `created → capture_requested`). (b) The vault's KEK is `NodeCrypto`-derived from `PAYMENT_CREDENTIALS_KEK_REF` — the ref _is_ the key material, like `STRIPE_SECRET_KEY`; a KMS `CryptoPort` satisfies the same `KeyWrapCipher` shape and can replace it without touching Payments. (c) Under `TENANT_MODE=multi` a Paymob callback must be attributable to a tenant by the request's resolver chain (verified claim, then `x-tenant-id`); Paymob cannot send either, so multi-tenant Paymob callbacks need a per-tenant callback URL/host that the resolver can read — **open, see G-73**. Single-tenant works today. (d) `billing_data` is required by Paymob's API but the port carries no customer identity and was not widened, so the adapter sends Paymob's own `"NA"` placeholders; whether Paymob accepts them for `phone_number` could not be verified without a live call.

### D-060 — Cash on delivery is created unpaid and settled only by an explicit, amount-checked collection confirmation (WP-13, decision 2)

- **Decision:** COD is a payment method (`cod`) with a `CashOnDeliveryProvider` behind the same port, and the places where the port's `create/capture/refund/verify` shape does not fit are marked in the code and **refuse rather than no-op**: `createIntent` yields an unpaid intent with no client handle; `capture` **throws** (there is nothing to charge — a silent success would mark an order paid before anyone handed over cash); `refund` **throws** (cash is returned outside the platform; recording it is a follow-up); `cancel` succeeds (nothing exists externally, so the idempotent no-op is true); `verifyWebhook` is always `false`. The only thing that settles a COD payment is `ConfirmCodCollection` (`POST /payment-intents/:id/cod-collection`, permission `payments:confirm_cod_collection`, idempotent): it walks the intent to `capture_requested` in one committed transaction, then runs the **same** `CapturePaymentLifecycle.settle()` a card capture uses. It accepts only a **full** collection (amount and currency must equal what is due) and is a no-op on a repeat. Three other doors are closed and tested: `CapturePaymentLifecycle` rejects a capture request for a direct-capture intent; `RecordWebhook` refuses any webhook naming `cod` (the test written for this found the hole — a `captured` webhook attributed to `cod` settled it through the direct-capture path); and order creation, intent creation and payment initiation never transition anything.
- **Courier integration:** checked `services/shipping` before assuming an operator action: it has a `CarrierProviderPort` and a `RecordCarrierWebhook` status use case, but **no real carrier adapter and no collected-amount field** — a "delivered" status does not say cash was collected or how much. So confirmation is an operator action for now; a courier-sourced confirmation is a follow-up that needs a real adapter reporting the collected amount.
- **Direct-capture providers and the paid signal:** Paymob (`sale` integrations) and COD have no "request capture" step, so they are **direct-capture** providers: `PaymentIntent.prepareDirectCapture` walks `created → processing → authorized → capture_requested` (bookkeeping to respect the transition table, in the same transaction as the verified signal), then `settle()`. For these providers `markCaptured` also raises the legacy `PaymentCaptured` event (`payments.payment_intent.captured`) — the only event Orders' `PaymentCapturedConsumer` and Finance's captured consumer subscribe to, and therefore the only thing that ever drives an order to paid. The lifecycle transition alone raises `payments.intent.captured`, which nothing subscribes to; **that pre-existing gap also affects Stripe's authorize→capture path and is left as found** (the backfill's own doc comment records it) — flagged, not fixed, because changing it alters Finance posting for the existing provider.
- **Paymob webhooks:** the HMAC covers only 20 fields (source: Paymob's published "HMAC Transaction Callback", updated 2026-06-01, worked example pinned in `webhook-signature.test.ts`). `merchant_order_id` and `extra` are unsigned, so correlation uses the signed `order.id` (= the `intention_order_id` stored as the intent's PSP reference) and the signed amount/currency are checked against the intent; the webhook's provider must equal the intent's. A signed missing/null field fails closed (Paymob does not document its rendering). Failed attempts leave the intent open (Paymob allows retry on the same intention); voids, dashboard-initiated refunds, child transactions and auth-only transactions are recorded but not applied — refunds we initiate are already recorded by `RefundPaymentLifecycle`, and dashboard-side reversals are not reconciled (**G-73**).
- **Reason:** A COD order reporting paid before cash changed hands is a financial error, not a UX one; the only defensible shape is one explicit action with one owner.
- **Trade-offs:** A partially collected COD payment cannot be recorded (refused, not settled). A COD refund cannot be recorded through the platform at all yet. The hosted-checkout handle for Paymob is returned once, on the call that opens the intent; the session persists only the intent id, so a repeat initiation resumes the intent without re-issuing the handle (**G-73**).

### D-061 — Morbeh's own billing charges through Morbeh's own PSP account, recorded on the Invoice, never as a PaymentIntent (WP-14, T14.4, decision 3)

- **Decision:** Where Morbeh charges a merchant, the money moves from the merchant to Morbeh, so the credentials on the wire are **Morbeh's**. They come from a dedicated env pair, `PLATFORM_BILLING_STRIPE_SECRET_KEY` + `PLATFORM_BILLING_STRIPE_WEBHOOK_SECRET` (`apps/runtime/src/config.ts`), composed by `buildPlatformBillingPayments` into a `StripePaymentProvider` and handed to `PlatformBillingPaymentsAdapter` (Licensing's `PaymentsPort`) as a **bare `PaymentProvider`**. Both are required (either absent ⇒ no adapter, never a stub); the webhook secret must **differ** from `STRIPE_WEBHOOK_SECRET` (composition throws) so billing events cannot be delivered to the merchant-store handler. Stripe only for now: Paymob is a hosted-redirect flow that has no server-side capture for an off-session merchant. The `STRIPE_*` pair is the STORE's account and is never reused for billing.
- **Which tenant:** none. A billing charge writes **no `payments.payment_intents` row at all** — it is recorded on the `licensing.invoices` row (`paymentReference` = the provider's intent id) under the platform-operator tenant that raised it, with the merchant as `tenantRef`. The adapter never goes through `PaymentController`/`wirePayments`, so nothing tenant-scoped in the store's ledger can hold Morbeh's revenue, no store read can surface it as a shopper's payment, and `RecordWebhook` finds no intent for a billing intent id. The PSP call carries `orderRef = billing:<invoiceId>:<version>:collect`, and the merchant only as the payer in PSP metadata.
- **What is deliberately not reused:** `TenantPaymentProviderResolver` (WP-13). It opens the MERCHANT's sealed credentials for the MERCHANT's store — reusing it here would charge the merchant through their own account. The adapter's dependency has no tenant parameter, so it cannot be wired that way by accident; `apps/runtime/src/platform-billing-isolation.test.ts` observes the outbound HTTP so any wiring that reaches a merchant credential fails.
- **Reason:** decision 3 of WP-14 (a merchant's chargeback must never look like a Morbeh billing failure) and Trap 1 (whose PSP account).
- **Trade-offs:** the port is on-session (`createIntent` → payer confirms → `capture`); with no stored payment method a real capture of an unconfirmed intent fails closed and the invoice is `failed` (**G-74** (1)). A shared Stripe account is possible (separate webhook endpoints); a dedicated account is the operator's choice.

### D-062 — Plans are platform-global; a subscription pins an immutable version; the management surface is platform-only (WP-14, T14.2, F-16)

- **Decision:** `licensing.plans` carries no tenant and no RLS policy (a tenant-scoped policy would hide the catalogue from every merchant). What protects it instead: (a) `LicensingController` refuses (403) every plan/subscription/override/capability/invoice/credit/renewal operation from a tenant that is not `platformTenantId` (the deployment tenant under `TENANT_MODE=multi`, the ADR-0014 8f scope; absent under single-tenant, where the one tenant is the platform) — at the controller, not per route, so a new route cannot forget it and a merchant holding `licensing:plan:manage` still cannot price its own bill; (b) `PlanVersion` deep-freezes its spec and validates price (integer minor units) and currency at the door; (c) `CreateSubscription`/`RepinSubscription` resolve the pinned ref to a real, **published** version, and `BillSubscriptionRenewal` reads the price from `subscription.planVersionRef`, never `plan.publishedVersionId`. The existing `Plan.versions` JSONB + `publishedVersionId` **is** the versioning convention and was kept — no second one.
- **Mapping of existing rows (migration `20260924000000_wp14_platform_plans`):** every row kept, one platform plan per row, **id unchanged** so `planVersionRef` (`<planId>-v<n>`) still resolves; `tenant_id` renamed `origin_tenant_id` (provenance, never a scope); a key collision is disambiguated deterministically (earliest-created keeps the key, the rest become `key@origin_tenant_id`) — **nothing merged, nothing dropped**, because deciding two tenants' rows are one plan is a business decision the data cannot make and merging would rewrite pinned ids. Legacy `versions[].spec.pricing.basePrice` (unit and currency never recorded) is moved to `legacyBasePrice` with `currency = 'XXX'` (ISO "no currency"), which `BillSubscriptionRenewal` refuses — a migrated version entitles but cannot charge until a new priced version is published and re-pinned. Live `plans` were 0 rows on 2026-09-24 (read-only, RLS-bypassing role).
- **Reason:** the merchant must not be able to price their own bill (Trap 2), and a price change must never silently reprice a subscription (decision 1).
- **Trade-offs:** no DB-level write guard on `plans` (no RLS by design — **G-74** (5)); the guard is unrestricted in single-tenant mode (**G-74** (4)).

### D-063 — Billing money is integer minor units, summed with the shared-kernel `Money` (WP-14, Trap 3)

- **Decision:** invoice line items are `{ description, amountMinor }` and plan pricing is `{ basePriceMinor, currency, ... }` — an integer count of the currency's minor units, the convention `payments.amountMinor` and `@platform/domain`'s `Money` (D-029) already use; no third convention, no new package. `Invoice.total` is `Money` (exact integer addition, `Number.isSafeInteger` guarded), `totalMinor` is what goes to the PSP; a fractional, negative or non-integer amount, a malformed currency, or a zero-total collection is refused. `PaymentsPort.collect`/`FinanceLedgerPort.postSettlement` take `amountMinor`. `InvoiceMapper` refuses to read a line without an integer `amountMinor`; `SubscriptionMapper` now revives the JSONB renewal date (JSON returns a string).
- **What was converted:** JSONB has no migration that can decide a unit. Plan pricing: see D-062 (moved to `legacyBasePrice`, `XXX`). Invoice lines: a legacy `{ amount }` has no recorded unit, so the migration **aborts** with a count rather than guess (live: 0 invoices); an operator-approved rule (e.g. major units × currency exponent, round half away from zero) must be applied first.
- **Reason:** `Invoice.total` summed a JS number with float `+` (0.1 + 0.2), the F-07 defect WP-11 closed for the columns but which escaped through a JSONB column — and it is the number Morbeh charges.
- **Trade-offs:** `Credit`/`UsageCounter` amounts stay `Decimal(19,4)` major-unit (T14.3 owns reconciling them); no discount lines yet (`Money` is non-negative).

### D-064 — Payment providers are registered at composition time and the payments domain reasons about declared capabilities, never provider names (WP-13, G-73)

- **Decision:** a provider is a `ProviderRegistration` — a key, four declared capabilities, its credential field names, an optional `parseConfig` for its own non-secret routing data, and a `create` factory — registered once at the composition root (ADR-0014) into a `PaymentProviderRegistry`; resolution stays per request (`TenantPaymentProviderResolver`, `create` is called afresh per resolution and never cached). The registry answers only BY KEY (`get`/`has`/`list`/`defaultEnabled`); it has no operation that picks a provider, and `provider-registry.test.ts` fails if one is added (the shopper's explicit choice remains the ONLY selector — WP-13 decision 3). `stripe` (the platform's own binding) and `cod` ship with `services/payments` as ordinary registrations; Paymob is registered by `apps/runtime` (`paymob-registration.ts`), which owns `@platform/psp-paymob`.
- **The capability set, derived from the branches that existed** (no speculative taxonomy): `settlesAtPayTime` (was the `DIRECT_CAPTURE` name set: Paymob, COD), `deliversWebhooks` (was `hasProviderWebhooks`, `provider !== "cod"`), `requiresMerchantCredentials` (was the Paymob-only settings field and resolver branch), and `chargesOffSession` (new — WP-14's follow-up: a provider without it is refused by `resolveForOffSession`, so it cannot be selected for recurring billing; Paymob declares `false` until its tokenization task lands). "Settled only by an operator confirming the collection" is DERIVED (`settlesAtPayTime && !deliversWebhooks`), not a fifth flag; it is what `ConfirmCodCollection` used to test with `provider === "cod"`.
- **Refusals stay refusals:** a capability a provider lacks yields a refusal, never a permitted no-op — `VerifyPaymentWebhook` returns false and `RecordWebhook` rejects for a provider without `deliversWebhooks` before asking the provider; a capture request for a `settlesAtPayTime` provider is rejected before any transition or provider call; COD's `capture`/`refund` still throw and its `verifyWebhook` is still always false. An intent whose provider is no longer registered fails closed (nothing can say what it may do).
- **Per-merchant config is one opaque object per provider** (`provider_settings` JSONB: `{ "<key>": { "config", "sealedCredentials" } }`). The sealed envelope is unchanged — same vault, same tenant+provider binding, moved byte-for-byte; only where config is SHAPED changed. Each provider's package validates its own `config` (`parsePaymobConfig` shares `isPaymobRegion` with the adapter, so `PAYMOB_REGIONS` left the domain and the `apps/runtime` pin now asserts the registration accepts exactly the adapter's regions). Credentials are validated against the registration's declared `credentialFields` (no missing, no extra) before anything is sealed.
- **The database:** migration `20260924010000_open_payment_provider_registry` DROPS `payment_intents_provider_check` (an open registry cannot be enumerated in SQL; validation moved to the registry at the boundary; the column stays `TEXT NOT NULL`, historical `'stripe'` rows are untouched and readers check only that a stored key is well-formed) and folds `paymob_region`/`paymob_integration_id`/`paymob_credentials` into `provider_settings`, RAISING (rolling back) on a partial or impossible Paymob shape, verifying every mapped row round-trips before the columns are dropped, and setting `row_security = off` so FORCE RLS cannot silently hide rows from the guards. Created, NOT applied.
- **The production guard scales:** `assertProductionPaymentProviderConfigured` loops over `composePaymentProviderRegistrations` — the same function `wirePayments` uses — so N providers are N checks: any registration not `backing: "real"` (the offline stub) is refused outside `local`, and any registration that `requiresMerchantCredentials` needs a real vault. A provider registered tomorrow is checked without editing the guard.
- **Port:** `PaymentProvider` in `@platform/contracts` is unchanged; every capability is expressible without widening it. `PaymentProviderResolver` (a payments application port) gained `resolveForOffSession` and `capabilitiesOf`.
- **Reason:** adding a provider required editing the domain, its database columns and a `switch` on a name (G-73). It now requires one registration.
- **Trade-offs / still closed:** webhook INGRESS is still one route per provider (`/payments/webhook`, `/payments/webhook/paymob`) because interpreting a provider's payload is provider-specific — a webhook-capable new provider needs a route (or a narrow webhook-interpreter port, not built here); the storefront's `OFFLINE_PROVIDERS` set (`apps/storefront/src/app/checkout/actions.ts`) and `paymentMethod.{stripe,paymob,cod}` labels remain (an unknown key already renders as-is and is treated as hosted, fail-safe); the admin settings body is now `providerSettings` (was a named `paymob` field — an API change with no consumer outside the e2e tests).

### D-065 — Off-session charging is a separate narrow port, and the type system ties the capability to it (WP-14 follow-up, G-74 (1), G-73 (9))

- **Decision:** `@platform/contracts` gains `OffSessionCharger { chargeStoredMethod(request): Promise<{ providerReference }> }` beside `PaymentProvider`, plus `OffSessionPaymentProvider = PaymentProvider & OffSessionCharger`. `PaymentProvider` is NOT widened (WP-13 and WP-14 both forbid it): `createIntent` → payer confirms → `capture` cannot express "charge this saved token", and a method on the shared port would sit on every provider that cannot.
- **The capability and the port cannot drift.** `ProviderRegistration` became a discriminated union on `capabilities.chargesOffSession`: `chargesOffSession: false` → `create` returns a plain `PaymentProvider`; `true` → `create` must return an `OffSessionPaymentProvider`. A registration declaring the capability with nothing behind it does not compile (`off-session-port.test.ts` pins that with `@ts-expect-error`). `resolveForOffSession` returns `OffSessionPaymentProvider` and re-checks at runtime what a cast or plain JS could bypass (`PaymentProviderUnavailableError`, "declares off-session charging but implements no off-session port"). Licensing's `StoredMethodBillingPaymentsAdapter` takes a bare `OffSessionCharger`, so a provider without the capability is not assignable there either.
- **Found and fixed:** the Stripe registration declared `chargesOffSession: true` while `StripePaymentProvider` is on-session only — a declaration nothing implemented. It is now `false`, and a test walks every composed registration and fails if the flag and the port disagree.
- **Paymob:** declares `true`; `PaymobPaymentProvider` implements both ports. The MIT flow is Paymob's own (official Postman collection, "Pay with saved card" → MIT): an intention on the MOTO integration, then `POST /api/acceptance/payments/pay` with `{ source: { identifier: <token>, subtype: "TOKEN" }, payment_token }`. It resolves only for `success: true`, not pending, no error flag, `txn_response_code: "APPROVED"` and exactly the requested `amount_cents`; anything else throws. No MOTO integration id ⇒ it throws before any request (`PaymobMitNotConfiguredError`) — never a fallback to a normal sale.
- **Two signing schemes, two verifiers.** The card-token callback signs 8 fields in lexicographical order (`card_subtype, created_at, email, id, masked_pan, merchant_id, order_id, token`), HMAC-SHA512 — confirmed against Paymob's "HMAC Card Token Callback" page on 2026-09-24, which also publishes a worked example the tests pin. The transaction callback is a different, fixed 20-field scheme. `card-token-signature.ts` is separate from `webhook-signature.ts`, and a test signs a hybrid body under each scheme and proves the other verifier rejects it.
- **Where the seam for a shopper's saved card would be:** a merchant-tenant-scoped store beside `payments.merchant_payment_settings`, feeding `resolveForOffSession(tenantId, provider)` (which already yields the narrow port). Nothing here is shared with it: whose card, whose row and whose PSP account all differ.
- **Trade-off:** the registry union costs every test double a small helper (`permissiveProvider` now implements the port). That is the price of the compiler saying so.

### D-066 — Morbeh's saved card is platform-scoped, sealed, and reachable only by Morbeh (WP-14 follow-up, G-74 (1))

- **Decision:** the token lives in `licensing.billing_payment_methods`, scoped to the PLATFORM tenant (`tenant_id`, `tenant_isolation` RLS forced, like `subscriptions`/`invoices`) with the merchant as `tenant_ref` — never in the merchant's own tenant data. A merchant who could read, edit or delete the token that bills them would control whether they get billed. The token is sealed with the payments credential vault's envelope (`@platform/secrets`), bound to the payer, under a vault key (`platform-billing-card-token`) distinct from every merchant-credential key so blobs do not cross-open. `BillingPaymentMethod` serialises display fields only (masked PAN, card brand); its sealed blob leaves through two named doors (`sealedTokenForCharge`, `toPersistence`).
- **Who can reach it:** nothing merchant-facing reads or deletes it — there is no route. Begin-enrolment and revoke are platform-only at `LicensingController` (403 from a merchant tenant); the token-callback path is authenticated by the callback HMAC (Morbeh's billing secret, the card-token scheme) and pins the platform tenant scope whatever tenant the request resolved to; under RLS a merchant-scoped session matches zero rows. One active card per merchant (partial unique index; the use case revokes the previous one in the same transaction).
- **Flow:** `POST /invoices/:id/card-enrolment` starts the merchant's interactive first payment on Morbeh's card integration (amount read from the invoice, never a caller) and records the PSP order id on a `pending` method; Paymob's card-token callback (`POST /platform-billing/paymob/card-token`, its own public route — never the store's `/payments/webhook/paymob`) is verified, correlated on the SIGNED order id, sealed and activated; renewals feed the unchanged `CollectInvoice` through `StoredMethodBillingPaymentsAdapter`, whose `collect` gained an optional `scopeTenantId`. No stored card ⇒ `NoStoredPaymentMethodError` before any PSP call ⇒ `CollectInvoice` marks the invoice `failed` and nothing reports a collection.
- **Whose account:** Morbeh's own, from `PLATFORM_BILLING_PAYMOB_*` — never a merchant's, never the store's; the merchant's own Paymob account is configured in the isolation test on purpose and must never appear on the wire. All-or-nothing group; needs `PAYMENT_CREDENTIALS_KEK_REF`; a stub sealer is refused outside `local` by the boot guard.
- **Operator steps:** enable a MOTO-type integration on Morbeh's Paymob account and set `PLATFORM_BILLING_PAYMOB_MOTO_INTEGRATION_ID` (absent ⇒ every renewal fails visibly, nothing is sent); set the account's card-token callback URL to `/platform-billing/paymob/card-token`; ask Paymob to force save-card on the checkout; deploy migration `20260924020000_billing_payment_methods`.
- **Not built (follow-ups G-74 (8)-(10)):** the first invoice is not settled by a PSP callback; no card update/expiry; Paymob MIT idempotency is unproven live. Nothing here schedules renewals — G-74 (7) stays open.

### D-067 — The event envelope requires a tenant; a consumer that cannot find one never defaults, and fails in the direction that keeps protection (G-64)

- **Decision:** `IntegrationEvent.tenantId` is required. Consumers read it per message (`readEnvelopeTenant` returns `null` for absent/blank/non-string; `requireEnvelopeTenant` throws `MissingEnvelopeTenantError`). The six event-path sites that pinned `TENANT_DEFAULT_ID` at builder time (the four orders-paid consumers, finance settlement, payment-captured, tracking ingest, the Identity/consent projections, security provisioning) read the envelope instead; the seventh class-D row, `bootstrapSecurity`, is boot-time provisioning and stays. `OutboxWriter` throws when the context names no tenant, and the collector refuses to publish one. Nothing falls back to a default. The rule that decides every edge case is the one `relation-sync.consumer.ts` set: **a skipped write denies, a skipped delete allows** — so the two must fail in opposite directions.
- **Direction per handler (no tenant on the envelope):** _throw to retry/DLQ_ — the three Finance ledger consumers (orders-paid, payments-captured, refunds-issued: a payment with no ledger entry is missing money), `PaymentCapturedConsumer` (a capture that cannot be applied leaves a customer charged and an order unpaid), `IdentityUserDeactivatedConsumer`, `IdentityMembershipRoleChangedConsumer`, `DisablePrincipalOnUserDeactivated` and a consent WITHDRAWAL in `ConsentChangedConsumer` (each removes or narrows standing; acking a skip would leave the wider projection live). _Refuse — write nothing, log at error, ack_ — Loyalty earn, Customer 360 profile projection, order-confirmation notifications, the three Identity creates, a consent GRANT, `ProvisionPrincipalOnUserCreated` and `AssignRoleOnMembershipCreated` (each adds standing; a skipped add denies). _Dead-letter and ack_ — tracking ingest, for a missing tenant and for an envelope tenant that disagrees with the payload's own `tenancy` (the same visible sink it already uses for a permanently bad event).
- **Reason:** under `TENANT_MODE=multi` the bug this prevents is a cross-tenant WRITE — tenant B's event landing in tenant A's ledger — so a guess is never acceptable. A default is right in `single` and a cross-tenant write in `multi`.
- **Why the expand → migrate → contract sequence was skipped:** the field was optional because "adding it later to live topics would be a breaking schema change". The operator states that nothing has been deployed to a broker, and the repo agrees statically (only unapplied k8s/Debezium manifests and a manual `workflow_dispatch` deploy; no broker, relay or consumer record). What cannot be checked from code is whether `platform.outbox` in the live database holds persisted rows; that needs an operator query. Any old row without a tenant is fail-closed by the table above (a write is refused, a removal throws), never mis-attributed.
- **Trade-offs:** tracking ingest builds one registry + hot-reload watcher per tenant lazily on the first event naming it (`TenantRuntimes`), so an unseeded tenant registry is found on its first event, not at process start. `OutboxWriter`'s refusal is a runtime check, not a compile-time one, because `EventContext.tenantId` stays optional (base contexts are built untenanted and merged per call, see the outbox guard).
- **Worker guard:** `EVENT_PATH_TENANT_PINS` is now empty and a test forces it to equal the `event-path-pin` class in `TENANT_DEFAULT_ID_SITES`, so a new pin cannot be added silently. The guard keeps refusing multi for `bootstrapSecurity` (`BOOT_TENANT_PINS`) while `SECURITY_PRINCIPAL_PROVISIONING` is on — per-tenant provisioning is T10.6. `TENANT_MODE=multi` is not enabled anywhere.

### D-068 — Tenant lifecycle: suspension is enforced at tenant resolution, provisioning converges on stored state, cancellation ends service and erases nothing (G-32, G-25 narrowed)

- **Date:** 2026-09-26 (T10.6)
- **Suspension enforcement point.** `packages/http` `executeRoute`, step 2b: immediately after the tenant is resolved and before authorization, through an optional `TenantGate` port. It is ONE place, so an endpoint added tomorrow is gated the day it is registered; no feature is asked. Mounted by `createAdminHttpApi` only under `TENANT_MODE=multi` (single mode has one deployment tenant and no lifecycle row).
- **What a suspended tenant may still do** (`suspendedTenantMayCall`, an explicit function, not an accident of routing): authenticated, non-public `GET` (read/export its own data), and routes that opt in with `allowWhenSuspended: true` — today the two invoice-payment routes (`POST /invoices/:invoiceId/card-enrolment`, the Paymob card-token callback), because refusing payment would make suspension for non-payment incurable. Refused: every other write and ALL public storefront traffic (a suspended store takes no orders and shows no catalog). A **cancelled** tenant is refused everything. Refusal is the same 403 body (`TENANT_SUSPENDED` / `TENANT_CANCELLED` / `TENANT_UNKNOWN`) whichever endpoint is called.
- **Fail closed.** A status that cannot be read is a 503 (retryable, `Retry-After`), never a pass; a failed read is not cached and an expired cache entry is never served in its place. A tenant with no row is 403 `TENANT_UNKNOWN`.
- **Cost and staleness.** No database read per request: `CachedTenantGate` holds each tenant's status in process for `tenantStatusTtlMs` (default 10 s), with single-flight loading. A suspension/cancellation/activation takes effect **immediately on the instance that performs it** (the lifecycle routes invalidate the entry) and **within one TTL (≤10 s) on every other instance**. There is no cross-instance push: the API process has no event consumer and adding one to shave seconds off a billing action was judged not worth a second moving part. Lower the TTL to tighten the bound; it costs one read per tenant per TTL per instance.
- **The platform tenant** (WP-14; `platformTenantId`, and the deployment scope it is under ADR-0014 8f) is always served by the gate without a read, and `SuspendTenant`/`CancelTenant` refuse its id with a 409 before any row is read (`protectedTenantIds`). Suspending it would stop Morbeh billing anyone, including the means to recover.
- **Provisioning.** `TenantProvisioner` runs `bootstrapSecurity` (moved to `@platform/security` so `apps/admin` can use it; `apps/runtime` re-exports it) FOR THE NEW TENANT, then, if an owner is named, registers the owner, assigns `platform-admin`, and writes the enforcement grant through `SecurityController.writeRelationTuple` — which emits `security.relation.written`, so the relation-sync consumer writes the **tenant-qualified** tuple (G-70); nothing here builds a bare or pre-qualified tuple. It cannot be one transaction (several writes, one of them external), so it is **idempotent and resumable**: baseline use-cases upsert by key, and the two owner steps that are not upserts are skipped when stored state already shows them. `complete` is computed from `SecurityController.tenantBaseline` (what is stored after the run), not from "no step threw"; an incomplete tenant reports `complete: false`, `missing: [...]` and the error, from any process, later. **Not claimed:** that Keto already holds the grant — that propagation is asynchronous through the outbox relay and the consumer. **Known race, recorded not solved:** two API instances provisioning the same tenant at the same instant can both see "no admin assignment" and both assign (`AssignRole` is not upsert-by-key); in-process calls are single-flighted and the only caller is the operator route.
- **A half-provisioned tenant** is created (its row stays; it is not rolled back), is served (the gate reads lifecycle status, not provisioning), and is visibly incomplete: `POST /tenants` returns `provisioning`, `GET /tenants/:id/provisioning?owner=…` reads it, `POST /tenants/:id/provision` resumes it (200 when complete, 202 when not). The gate deliberately does not refuse an unprovisioned tenant: an unadministrable store is a support problem, not a leak, and refusing it would make it impossible to resume provisioning through the store's own admin.
- **The existing deployment tenant** was provisioned by the boot path and needs nothing: it is the platform tenant, exempt from the gate, and `bootstrapSecurity` still runs for it at boot (classified `platform-boot`). It has no `Tenant` row and none is created. Any non-deployment tenant row that existed before this change has never been provisioned; `GET /tenants/:id/provisioning` will say so and `POST …/provision` fixes it. How many such rows exist needs an operator query (not run here).
- **What cancellation does:** `cancelled` is terminal (`Tenant` transitions) and the tenant is refused everything at the boundary. It stops service. It does NOT delete, anonymise, revoke Keto grants, disable Kratos identities, cancel the Licensing subscription, or touch any stored row.
- **G-25 / G-32 — narrowed, neither closed.** _G-32 closed:_ a tenant can be provisioned with a working security baseline; suspension/cancellation are real and enforced; the platform tenant is protected. _G-32 open:_ custom-domain registration, seeding defaults for any context but Security, per-tenant backup/restore, deletion, billing hooks (a subscription is not suspended/cancelled with the tenant), cross-instance immediacy. _G-25 narrowed only_ in that cancellation now exists as a defined, enforced end-of-service state and emits `tenancy.tenant.cancelled` — the trigger an erasure would hang off. _G-25 open:_ all of erasure.
- **What erasure would have to do (not built; do not build as a sweep).** A separate, deliberate, audited operation with a runbook and a dry-run manifest, run only against a `cancelled` tenant after a retention hold, with a second approver. It must (1) enumerate every tenant-scoped table per context and classify each as _erase_, _anonymise_ or _retain_; (2) **retain** Morbeh's own accounting records — the tenant's invoices, subscriptions and billing payment methods live on the platform tenant and are Morbeh's records, not the merchant's to erase — and any merchant financial records a statutory retention period covers (finance ledger, settlements, tax documents); (3) reconcile erasure of personal data with the hash-chained WORM audit log (anonymise the subject, keep the chain verifiable); (4) delete the tenant's Keto tuples (`tenant/<id>/…`), Kratos identities/sessions, object-storage prefix, ClickHouse partitions, Redis keys and search index entries; (5) reach backups (expiry, not rewrite); (6) be idempotent, resumable and itself recorded. Which records are legally retained, and for how long, is a legal determination this task did not make.
- **Trade-offs:** the gate adds one in-process map lookup to every request under multi; `Tenant` rows stay pinned to the deployment tenant (ADR-0014 8f exemption unchanged — the loader reads through the existing pinned tenancy repository, so no second entry was added to `TENANT_PIN_EXEMPTIONS`). No migration: provisioning state is derived from Security's own tables, deliberately, so there is no second record that can disagree with the truth.

### D-069 — WP-10's definition of done is a mutation-verified guard table, not a green suite; multi mode stays off (G-53 not closed, G-75, G-76 opened)

- **Date:** 2026-09-26
- **Decision.** "Every T10.5 test fails if you remove the guard it covers" is verified by deliberately removing each guard and recording which test goes red (`docs/plans/phase-7/WP-10-multi-tenant-runtime.md`, "Definition-of-done pass"). A guard whose removal turns nothing red is reported as a gap that existed, then covered. 145 guards were mutated in the first pass, 31 survived; they are listed there with what was done about each.
- **Isolation rests on application code alone.** The connecting role bypasses RLS and nothing on the write path sets `app.tenant_id` (ADR-0014 Amendment 9). So the Prisma `where: { tenantId }` is the only wall, and before this pass removing it from orders, catalog and inventory turned nothing red. `scripts/dev/check-prisma-tenant-where.mjs` (run by `packages/db/src/prisma-tenant-where.guard.test.ts`) now fails the suite for any tenant-owned Prisma read/update/delete without the tenant in its `where`. It proves the tenant is named, not that it is the right one.
- **Fixed in this pass** (each with a test that was red first): blank/padded `tenant_id` claims resolved as tenants; the boot probe accepted the G-69 chain (its fixture used the very resolver G-69 removed); Kratos user-editable traits could override the tenant claim; two consumers accepted `null`/blank/non-string envelope tenants and the relation-sync **delete** acknowledged a revocation it never applied; `createAdminHttpApi` under multi without a deployment tenant left the tenancy routes open to every tenant.
- **Found and deliberately NOT fixed: G-75.** Tracking event records are read and appended by `eventId` alone although the key is `(tenantId, eventId)` and clients supply the id. Fixing it changes the `EventRecordWriterPort` contract, and the rule for this task was to report a leak, not fix it in the pass that found it. Held as an `it.fails`.
- **Consequence.** `TENANT_MODE=multi` is not set in any env file, manifest or CI job and is **not safe to enable** while G-75 is open. G-53 stays open with G-75 as its close condition. Enabling the mode for a real deployment remains a separate operator decision. Phase 2 of ADR-0014 (the `lumo_app` role) was not started and is further away than its own text says: `PrismaUnitOfWork` does not set `app.tenant_id` and the N-of-N assertion its gate requires does not exist.
