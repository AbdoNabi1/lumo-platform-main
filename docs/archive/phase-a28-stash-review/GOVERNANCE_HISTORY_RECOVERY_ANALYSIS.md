Written per explicit user instruction, before any hook or governance-script change. Nothing in
`.husky/pre-commit` or `scripts/governance/` has been modified while producing this. It exists to
answer three questions: what the hook currently does, why it blocks incremental historical commits,
and which fix preserves governance guarantees instead of weakening them.

## 1. What is currently executing

`.husky/pre-commit` (working tree, uncommitted relative to `HEAD`):

```
pnpm lint-staged
node scripts/governance/run.mjs
```

Two independent steps:

- **`pnpm lint-staged`** — driven by `.lintstagedrc.json`. Runs `eslint --fix` / `prettier --write`
  scoped to files matched by the staged-files glob. This step behaved correctly during the Tier 9
  attempt: it touched exactly the 8 staged docs and nothing else.
- **`node scripts/governance/run.mjs`** — a standalone script, run unconditionally, with **no
  arguments, no staged-file scoping, no git-awareness of any kind**. This is the step that failed.

## 2. What `run.mjs` actually checks

19 fitness-function checks (`FF-TYPE-02/03/04`, `FF-CX-01`, `FF-DEP-01`, `FF-API-01`, `FF-EVT-01`,
`FF-ARCH-*`, tenant scoping, ownership freezes, barrel presence, etc.). The one that failed is
**`FF-API-01` (public API stability)**.

Every check's file discovery goes through `tsSources()` / `walk()` in `scripts/governance/lib.mjs`:

```js
export function walk(dir, predicate = () => true, out = []) {
  if (!existsSync(dir)) return out;
  for (const entry of readdirSync(dir)) {
    if (["node_modules", "dist", ".next", ".turbo", ".git", "coverage"].includes(entry)) continue;
    ...
```

This reads **the live filesystem** under `packages/`, `services/`, `apps/`. It has no concept of
`git status`, the index, or `HEAD` — a file is scanned if it exists on disk under those roots,
whether it is committed, staged, modified-unstaged, or entirely untracked. Staged and unstaged
content are indistinguishable to it.

`FF-API-01` specifically (`scripts/governance/api-surface.mjs`) asks the real TypeScript compiler
to compute the exported signature of every workspace package's public entry point — again, from the
files on disk — and diffs that against a stored baseline:

```js
const baseline = loadBaseline("public-api"); // scripts/governance/baseline/public-api.json
return diffApiSurface(baseline, apiSurface()); // apiSurface() reads the live tree
```

## 3. Root cause

Two independent facts combine to make this circular:

**(a) The check has no staged/HEAD scoping.** It always evaluates "everything currently on disk,"
never "what this commit is about to change." This alone would be tolerable if the comparison
baseline were fixed and correct — the problem is (b).

**(b) The baseline file itself is uncommitted, and it is not frozen at the Sprint A0 boundary.**

```
git ls-files -- scripts/governance/baseline/     → (nothing — the whole directory is untracked)
git status --porcelain -- scripts/governance/baseline/  → ?? scripts/governance/baseline/
```

`scripts/governance/baseline/public-api.json` was last written **today, 2026-07-27 11:03 AM**
(filesystem timestamp) — i.e., generated by some prior `pnpm governance:update` run against
whatever the working tree looked like at that moment. Confirmed: it already contains
`services/orders`' checkout-lifecycle API (Tier 2 / C7, uncommitted relative to `HEAD`) but **not**
Sprint A1's `Order.completePayment` / `MarkOrderPaidDeps.shadow` (Tier 10 / A1, added after the
baseline was captured). So the baseline is a snapshot from _partway through_ the very backlog this
recovery is reconstructing — not a snapshot of the frozen `HEAD` (`830138a`), and not a snapshot of
"nothing yet."

**(c) The governance suite and the hook line that invokes it are themselves uncommitted.**

```
git show HEAD:.husky/pre-commit  →  "pnpm lint-staged"                      (that's the whole file)
working tree .husky/pre-commit   →  "pnpm lint-staged\nnode scripts/governance/run.mjs"
git status --porcelain -- scripts/governance/  →  ?? scripts/governance/    (untracked, all of it)
```

At the frozen Sprint A0 `HEAD`, the pre-commit hook only ran `lint-staged`. The entire governance
script suite (19 checks, ~750 lines across `run.mjs`/`lib.mjs`/`api-surface.mjs`/`layer-cycles.mjs`),
the `node scripts/governance/run.mjs` hook line, and the three baseline JSON files are **all part of
the same uncommitted pile the recovery plan is trying to sequence into history** — not a pre-existing
gate we must satisfy from outside. `REPOSITORY_HISTORY_RECOVERY.md` does not currently assign this
work a tier (it isn't K1–K7, and doesn't obviously belong in R3 "Operational Hardening" either,
though that's the closest fit). **This is a gap in the plan, flagged here rather than assumed.**

Net effect: because (a) the check always reads the full live tree, and (b) the baseline it compares
against already reflects a later, arbitrary in-progress state, _any_ commit — no matter how small or
unrelated — gets diffed against "the whole uncommitted backlog minus whatever was on disk at
11:03 AM today," which is not a meaningful comparison for a historical-reconstruction commit at all.
It was never designed to be one; it was written once, late, for day-to-day development against an
already-assembled tree.

## 4. Possible solutions

### Option A — Scope the check to the staged index, not the working tree

Make the governance step observe "`HEAD` + staged changes" instead of the raw filesystem, by running
it _inside_ `lint-staged`'s own task sandbox rather than as a second, unscoped hook line.

`lint-staged` already does this correctly for `prettier`/`eslint` in this exact hook (verified: the
Tier 9 attempt only touched the 8 staged docs). It works by stashing unstaged/untracked changes
before running configured tasks and restoring them after — a standard, battle-tested mechanism, not
something we'd be writing. Concretely: add an entry to `.lintstagedrc.json` (e.g. a glob covering
`packages|services|apps` sources, or a function-form config) whose command invokes
`node scripts/governance/run.mjs`, so it executes under the same stash while `lint-staged` is active.

- **Risk:** Low technical risk — no change to `run.mjs`'s detection logic (`walk`, `tsSources`,
  `apiSurface`, `diffApiSurface` are untouched), so `FF-API-01`'s actual comparison semantics don't
  change, only _what tree it sees_ when it runs. Main risk is configuration mismatch: lint-staged's
  glob-to-task matching needs a pattern that reliably triggers the governance run whenever any
  `packages/services/apps` source is staged (not just when a _matched_ file itself changed), which
  needs verifying against the installed lint-staged version's docs/behavior before relying on it.
- **Does not by itself fix (b)** — the baseline snapshot problem remains; Option A only fixes the
  "wrong tree" half of the root cause.

### Option B — Use `pnpm governance:update` as part of each milestone's own commit procedure

The "approval act" mechanism already exists (`updateBaselines()` in `run.mjs`, wired to
`pnpm governance:update`). Treat baseline regeneration as a required step of _this specific recovery
sequence_: before staging each milestone's files, run `governance:update` against the tree as it
will exist immediately after that commit (i.e., only that milestone's files added on top of the true
prior state), committing the refreshed baseline JSON alongside the milestone's own commit (or as a
trailing `chore(governance): update baseline` commit right after it).

- **Risk:** Procedural discipline, not a code change — matches the plan's own §0 note that gates
  should be "re-run per landed commit, the same discipline Sprint A0 used." Low technical risk. Cost
  is repetition: 24 planned commits means 24 potential re-baseline steps. Also does not by itself fix
  (a) — without Option A, `governance:update` itself would still capture the _entire_ live tree
  (including everything not yet committed further down the sequence) as if it were part of "this"
  milestone's approved surface, silently pre-approving future milestones' APIs before they're
  historically justified. **B without A is unsound** for a multi-commit sequence — it would make the
  ratchet accept the whole backlog on the very first `governance:update` call.

### Option C — Add a git-ref-aware mode to `run.mjs` (e.g. `--against=<ref>`)

Reimplement `apiSurface()`/`tsSources()`/etc. to read blobs from a specified git ref (via
`git show <ref>:<path>` or a populated in-memory TS compiler host) instead of the filesystem,
making the comparison "this commit vs. its own parent" natively, without lint-staged or a stashed
baseline file at all.

- **Risk:** Highest. This touches the core file-reading primitives (`walk`, `read`) shared by _all
  19_ checks, not just `FF-API-01` — a bug here has the largest blast radius of any option, and this
  is precisely the surface the user has flagged as not-to-be-weakened. Building a correct in-memory
  compiler host (module resolution, `node_modules` handling, cross-package aliasing — the exact
  concerns `api-surface.mjs`'s own comments describe fighting) is substantial new engineering in a
  script whose current version has no test coverage for this alternate mode. Most principled
  long-term design, least appropriate to build under recovery-sequence time pressure.

## 5. Recommended solution

**Combine A + B**, in that order, without touching C:

1. **Option A** (route the governance run through `lint-staged`'s staged-only sandbox) closes the
   "wrong tree" hole with no change to detection logic — lowest risk, reuses infrastructure already
   proven correct in this exact hook this session.
2. **Option B** (treat `governance:update` as a required step of each milestone's own procedure, run
   _after_ Option A is in place, so it only ever captures "prior true state + this milestone") closes
   the "wrong baseline" hole using the mechanism the script's own author already built for exactly
   this purpose (the code comment literally calls it "the approval act").

Together, every future milestone commit is gated against its **true** predecessor state, not the
current uncommitted backlog snapshot — restoring the incremental ratchet FF-API-01 is meant to
provide, rather than disabling or weakening it.

**Before implementing either**, two things need your call, since both are judgment questions, not
technical ones:

- **Where does the governance suite itself (script + hook line + baseline files) belong in
  `REPOSITORY_HISTORY_RECOVERY.md`'s tier sequence?** It has no assigned tier today (§3 gap above).
  It plausibly needs its own milestone — landed _before_ Option A/B can be exercised on anything
  else, since the hook can't correctly gate its own introduction.
- **What should the very first baseline (the one Option B produces for the very first real code
  milestone, e.g. K1) be diffed against?** The honest answer is "nothing" — `HEAD` (`830138a`) has no
  `packages/repository` or `packages/types` in the shape K1 will introduce, so the first real
  `governance:update` is establishing a baseline, not ratcheting an existing one. Worth confirming
  that's the intended semantics before the first `--update` run of the sequence.

doing all sequencing inside the single, fully-loaded working tree, `git add`-ing one milestone's

that merely happens to be present on disk right now" without either (a) being told to look somewhere
narrower, or (b) the somewhere narrower actually being the only thing that physically exists.

This reframes the recommendation space: fixes that change **where commits are executed** (so the
tree the hook reads is naturally correct) are addressing the real cause. Fixes that change **the
hook's code** are treating a symptom, and carry the risk of touching detection logic that has already
been shown to be subtle to get right.

## 8. Guarantee-weakening proof, per proposed solution

"Weakened" is defined precisely: a change is a weakening if it causes the _set of states the checks
would have flagged_ to shrink, or if it causes a check's own detection logic to become less complete
or unproven relative to today. A change that only alters **which tree** the existing, unmodified
logic is pointed at is not a weakening by this definition unless that new tree is a strict subset of
what a correct per-commit check should see.

| Solution                                                                                                                  | Detection logic touched?                                                                                       | Tree it evaluates                                                                                                                                                                                                                                                               | Weakens a guarantee?                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A — lint-staged sandbox**                                                                                               | No — `walk`/`read`/`apiSurface`/`diffApiSurface` unmodified                                                    | `HEAD` + staged (exactly the commit being made)                                                                                                                                                                                                                                 | **No.** Today's tree (full working directory) is a superset containing unrelated noise; scoping to exactly the commit's own resulting state is the textbook-correct scope, strictly _more_ accurate, not weaker. Proof: any export the commit itself removes/changes is still present in this tree and still caught; nothing the commit doesn't touch is newly exempted, because unrelated files are simply matching their `HEAD` state either way.                                                                                                                                                                                                                                                                            |
| **B — `governance:update` per milestone**                                                                                 | No — this is the script's own pre-existing, documented "approval act"                                          | Whatever tree exists when `--update` is run                                                                                                                                                                                                                                     | **No, conditional on A already being in effect.** Re-baselining is not bypassing the gate, it _is_ the gate's designed reviewed-approval path. **Proof this must follow A:** without A, `--update` would run against the full live tree (750+ uncommitted files), silently pre-approving every future tier's API surface under the current commit's name — a real weakening, since later milestones would then land with zero API-diff scrutiny (this is the "B without A is unsound" finding from §4, reaffirmed here). ## 9. Can recovery be completed without modifying the hook at all?

**Yes.** Five techniques were evaluated; two are real solutions, two are necessary ingredients of
those solutions (not standalone answers), and one is a false solution (previous section).

**Git worktree (primary recommendation).** `git worktree add <path> <branch>` creates a second
working directory backed by the same repository, with its own independent checkout and index.
Checked out from the current `main` tip (`830138a`), that directory contains **only what's actually
committed** — none of the 750+ uncommitted files exist there unless deliberately copied in. Two
consequences, both confirmed by the evidence in §7 rather than assumed:

1. **Corrected 2026-07-27** (`RECOVERY_DOCUMENT_CORRECTIONS.md` Discrepancies 3–4): since
   `.husky/pre-commit` and `.husky/commit-msg` **have** been committed since `ed3654d` (Sprint 0.2) —
   not "never," as this section previously and incorrectly stated — a worktree checked out at `HEAD`
   (or at any commit from `ed3654d` onward) already has a real, committed, `pnpm lint-staged`-only
   hook that **will run on every commit from the first reconstructed milestone onward**. This is
   still historically correct (it matches real history exactly, rather than approximating "no
   enforcement"): early commits in this repository's real lifetime were genuinely checked by
   `lint-staged` (auto-formatting staged files, already observed behaving correctly in the Tier 9
   staging attempt cited in §1), just not by _governance_. The prior claim — "no hook file exists at
   all that early, so nothing runs" — is false and should not be used to justify the worktree
   strategy; the correct justification is narrower: no _governance_ enforcement exists that early,
   base lint-staged enforcement does.
2. Once "Governance Suite" (§7's recommended milestone) is itself committed _within this same
   reconstructed branch_, every subsequent commit in that worktree starts being gated by exactly the
   hook content that milestone introduced (the governance line added on top of the pre-existing
   lint-staged line) — again matching real history, not approximating it.

Practical cost: each worktree needs its own `pnpm install` (disk + time), and milestone files must be
deliberately copied in per the plan's own file lists rather than bulk-copied — which is actually a
_safety improvement_ over `git add <list>` in the shared tree, since a file that was never copied in
cannot accidentally be staged.

**Temporary recovery branch (safety wrapper, not itself an isolation technique).** `git branch
recovery/history-reconstruction` at current `HEAD`, with all sequenced commits landing there instead
of directly on `main`. This doesn't solve tree-scoping by itself (a bare branch checked out in the
_same_ directory still has the same pile of uncommitted files present) — its value is reversibility:
the real `main` stays untouched and reviewable until the whole sequence is complete, matching this
system's general guidance to prefer reversible steps for git history operations. Recommended
_alongside_ the worktree, not instead of it.

**Detached HEAD** is an ingredient, not a standalone technique — it's simply what a worktree/branch
checkout looks like structurally. On its own, checking out `830138a` detached in the _same_ directory
does not remove the uncommitted pile from disk, so it doesn't solve anything by itself.

**Staged-snapshot execution via `git stash --keep-index`** (performed as an external procedure around
`git commit`, not as an edit to any tracked file) is a real, zero-modification alternative to the
worktree, with the anachronism caveat noted in §8's table. Lower setup cost (no second `pnpm
install`), but slightly higher operational risk per commit (must reliably `stash pop` even on hook
failure) and less historically faithful (§8).

**Index-based/plumbing bypass** — not a real solution; see §8's last row.

**Conclusion: yes, the full recovery sequence can be completed with zero changes to Husky, lint-staged
config, the governance script, or the baseline files**, using a temporary recovery branch plus a
linked worktree per commit (or, as a lighter-weight but less historically faithful fallback, the
stash-snapshot dance in the current tree).
